# 发现合约论述

发现合约是宿主 agent 会话启动时自动获得的一段注入文本或一项注入机制，它让 agent 在启动的那一刻就知道 journal 在哪里、什么时候必须读它。

agent 是无状态的：上一个 session 知道的一切，下一个 session 启动时都不存在。journal-root 若不在启动时自动进入上下文，已经写好的 journal 就等于不存在——文件就位而 agent 找不到 = 没有 journal。跨 session 记忆被真正采用的前提只有一个：它先被发现。

---

## 有效合约的条件

一个有效的发现合约必须同时满足：

1. **每次启动自动注入**——agent 不需要搜索、回忆或猜测
2. **包含 journal-root 具体值**——不能是变量或待替换占位符
3. **强制要求无条件加载 INDEX.md**——不能是可选的"建议阅读"

设计新合约与评估已有合约，都用「要素覆盖检查」逐项过一遍。

### 要素覆盖检查

| 覆盖要素 | 检查内容 |
|---------|---------|
| journal-root 声明 | 具体值出现，不是变量或占位符 |
| 定位立场 | journal 是什么、是谁的、为什么值得维护 |
| 价值裁量 | 什么值得记的判据出现 |
| 读取路由（强制底线） | 「会话开始时读取 INDEX」指令存在且为强制表述（快照宿主为等效的快照说明）；读写不对称表述在（读取 INDEX 不需加载技能） |
| 加载触发与操作边界 | 改变 journal 状态的操作前加载技能的触发明确，举例覆盖移动/删除等；使用边界出现（不得以 journal 内容为与用户交流的共同背景） |
| 与其他记忆机制的分工 | journal 与宿主其他记忆机制（记忆工具等）的边界（宿主无此类机制时此要素可缺省） |

全部要素就绪后做一次校对：无明显拼写或语法错误——这是呈报前的校对项，不属于合约的内容要素。「注入文本模板」与「要素框架」都是本表要素的表达；核对已有合约时以本表为准。

---

## 已有合约的检测

动手设计之前先查当前环境是否已有一份合约。找到不等于最新——合约可能已随技能版本迭代而过期，必须逐项比对。

1. **搜索已有合约**：在常见载体路径下用 grep 搜索合约特征文本（不区分大小写）：
   `index\.md|journal-root|写入操作.*journaling|读取.*INDEX`
   搜索范围按注入优先级从高到低：agent 运行时配置文件（如 AGENTS.md 等宿主配置）> 项目根配置文件 > 用户级配置目录 > 全局默认路径。由近及远——注入优先级越高的载体越优先。

2. **找到合约内容** → 用「要素覆盖检查」逐项比对：
   - 有差异 → 输出差异清单 + 每条差异对应的更新建议。更新策略：**内容升级而非格式替换**——保留载体已有结构和格式，仅升级内容要素
   - 完全匹配 → 报告「合约已是最新版本」，无需更新

3. **未找到合约** → 进入载体清查与全新设计

## 载体清查

清查当前运行环境里一切可能承载注入文本的位置，按三类逐项检查，并确认自己对这些位置拥有读取与写入权限：

**A. 项目级配置文件**——注入到 agent 上下文的文件
- 检查当前工作目录（及父目录）是否存在以下文件：`AGENTS.md`、`CLAUDE.md`、`.cursorrules`、`CONTEXT.md` 等自动加载文件
- 确认哪些文件你拥有读取和写入权限

**B. 运行时配置机制**
- 检查是否有持久化的环境变量机制
- 检查是否有启动脚本（Hook）、初始化文件或配置模板

**C. 环境内置约定**
- 检查当前运行时是否有已知的约定加载路径
- 检查是否已有其他配置文件中包含了 session 启动时自动执行的指令

---

## 评估候选载体

对每个候选载体，用三个过滤性问题做评估：

| # | 问题 | 通过条件 | 检查方法 |
|---|------|---------|---------|
| 1 | 是否每次启动自动注入？ | 载体内容在 session 启动时自动成为上下文的一部分 | 根据运行时经验或文档判断 |
| 2 | 我能否写入？ | 文件路径在写入权限范围内，且不是运行时只读 | 尝试打开文件检查权限 |
| 3 | 是否跨 session 持久？ | 写入后不会在 session 结束时自动清理 | 根据文件生命周期判断 |

三个问题都是"是" → 候选。有任何一个是"否" → 排除。「能否写入」是载体的能力判别（该载体是否允许写入），与执行授权分开——写入由谁执行见「更改宿主提示词的权限」。

---

## 推荐与呈报

从通过过滤的候选中选择方案：**自动注入范围最广、维护成本最低的载体优先**。方案包含三样东西——载体路径（确切的文件路径或机制名称）、合约文本（见「注入文本模板」）、写入方式（用哪个工具或命令写入）。

向用户呈报时说明以下内容，由用户决定是否执行：

1. **推荐的载体**和选择理由（为什么用它而不是其他选项）
2. **合约内容**——即将注入的文本
3. **风险说明**——是否影响现有上下文结构、是否覆盖已有内容
4. **备选方案**——如不同意推荐方案，是否有其他可接受选项

用户确认后执行写入——默认由用户或后续 session 执行；agent 仅在用户显式批准自己动手时例外（见「更改宿主提示词的权限」）。

无候选通过过滤时改走回退方案——见 `protocol-init.md` P3 的「回退触发」。

## 注入文本模板

```
> Journal root: <journal-root>
> journal 是你自己的跨 session 长期记忆——经验、决策、调研与方法的沉淀；你为未来的自己写它、维护它
> 什么值得记：长期仍然有效、脱离具体版本与环境细节仍然可复用的经验、判断与结论
> ⚠️ 会话开始时读取 <journal-root>/INDEX.md。INDEX 是 journal 的唯一入口，包含当前状态与关键上下文——跳过意味着在信息盲区中操作
> 读取 INDEX.md 不需要加载 journaling skill
> 向 <journal-root> 目录中进行任何写入操作（移动、修改、编写、删除等）时，必须加载 journaling 技能并按其指令操作
> journal 只服务于你自己：不得以 journal 内容为与用户交流的共同背景；客观事实走宿主记忆工具，经验与洞察走 journal
```

代码块中的 `>` 前缀是模板自身的展示格式（适合直接注入系统提示词 generic-rules 段的场景），不是对载体格式的强制要求。写入时适配载体的已有格式：载体用 Markdown 标题和列表（如 RULES.md），合约文本的要素不变，表达转为标题加列表。格式与载体一致，可降低 agent 把合约当作「外来片段」跳过的概率；全新载体（无已有格式参考）直接用模板的 `>` 引用块——它在系统提示词注入场景中最可移植。

---

## 宿主适配

模板给的是底线，不是上限——注入文本的表述按宿主实际机制适配。

### 要素框架

- **立场**——journal 是什么（agent 自己的跨 session 长期记忆）、是谁的（服务于 agent 自己，不为用户或其他 agent 写）、为什么值得维护（跨 session 接续工作、避免重蹈覆辙）、什么值得记（长期有效、脱离版本与环境细节仍然可复用的经验与判断）
- **路由**——读什么（INDEX 为唯一入口，会话开始时读取）、何时加载 journaling 技能（改变 `<journal-root>` 中 journal 状态的操作前）、不可做什么（不得以 journal 内容为与用户交流的共同背景）
- **规程不进注入**——操作流程与规则细节不进注入文本，留给按需加载的技能内容与 journal 规则文档；注入只承载立场与路由

### 写作原则

- **立场先于动作**——动作指令的失败模式是被挤掉；立场完整的注入可推导出动作，并覆盖设计时未预见的场景
- **机制适配**——注入描述宿主的实际机制，同一要素在不同宿主形态不同

宿主具备 INDEX 快照注入机制（INDEX 内容随会话自动可见）时，读取动作表述调整为等效的快照说明（如「INDEX 快照已随会话注入，以快照为线索主动读取相关条目」）——「会话开始时读取 INDEX」的义务不变，表述随宿主机制适配。要素覆盖不因适配而缺项，鼓励按宿主环境发挥要素框架、调整表述，不逐字照搬模板。

---

## 更改宿主提示词的权限

agent 对宿主提示词（注入文本所在的载体）只能提案、提醒、编写草稿——写入或更改由用户执行，或经用户批准后执行。这是注入文本维护的常态原则——不限初始化阶段，任何时候调整注入文本都适用。
