# 发现合约设计参考

> 本文件提供系统化的发现合约设计方法——从载体清查、过滤评估、方案推荐到用户呈报的完整流程。
> 配合 `protocal-init.md` Phase 3 的"方案讨论"节使用，在该节识别出可行方向后，按此流程细化方案。

---

## 合约发现流程

### 已有合约的检测（先于 Step 1 执行）

在开始载体清查之前，先检查当前环境是否已部署发现合约：

1. **搜索已有合约**：在以下常见载体路径下用 grep 搜索合约特征文本（不区分大小写 `case: false`）：
   `index\.md|journal-root|写入操作.*journaling|读取.*INDEX`
   搜索范围：agent 运行时配置文件（如 AGENTS.md、RULES.md 等，按注入优先级从高到低）> 项目根配置文件 > 用户级配置目录 > 全局默认路径。由近及远——注入优先级越高的载体越优先。

2. **如果找到合约内容** → 读取并与本文件 Step 3 的最新合约模板做要素覆盖比对：

| 覆盖要素 | 检查内容 |
|---------|---------|
| journal-root 声明 | 具体值出现，不是变量或占位符 |
| 定位立场 | journal 是什么、是谁的、为什么值得维护 |
| 价值裁量 | 什么值得记的判据出现 |
| 读取路由（强制底线） | 「会话开始时读取 INDEX」指令存在且为强制表述（快照宿主为等效的快照说明） |
| 加载触发与操作边界 | 非只读操作前加载技能的触发明确，举例覆盖移动/删除等 |
| 与其他记忆机制的分工 | journal 与宿主其他记忆机制的边界（宿主无此类机制时此要素可缺省） |
| 拼写与语法 | 无明显拼写或语法错误 |

3. **判断结果**：
   +- 有差异 → 输出差异清单 + 每条差异对应的更新建议。更新策略：**内容升级而非格式替换**——保留载体已有结构和格式，仅升级内容要素
   +- 完全匹配 → 报告「合约已是最新版本」，继续正常 Step 1 流程

4. **如果未找到合约** → 继续正常的 Step 1 流程（载体清查和全新设计）


### Step 1: 清查可用注入机制

清查当前运行环境中的所有可能载体。按以下分类逐项检查：

**A. 项目级配置文件**——注入到 agent 上下文的文件
- 检查当前工作目录（及父目录）是否存在以下文件：`AGENTS.md`、`CLAUDE.md`、`.cursorrules`、`CONTEXT.md` 等自动加载文件
- 确认哪些文件你拥有读取和写入权限

**B. 运行时配置机制**
- 检查是否有持久化的环境变量机制
- 检查是否有启动脚本（Hook）、初始化文件或配置模板

**C. 环境内置约定**
- 检查当前运行时是否有已知的约定加载路径
- 检查是否已有其他配置文件中包含了 session 启动时自动执行的指令

### Step 2: 逐项评估

对每个候选载体，用三个过滤性问题做评估：

| # | 问题 | 通过条件 | 检查方法 |
|---|------|---------|---------|
| 1 | 是否每次启动自动注入？ | 载体内容在 session 启动时自动成为上下文的一部分 | 根据运行时经验或文档判断 |
| 2 | 我能否写入？ | 文件路径在写入权限范围内，且不是运行时只读 | 尝试打开文件检查权限 |
| 3 | 是否跨 session 持久？ | 写入后不会在 session 结束时自动清理 | 根据文件生命周期判断 |

三个问题都是"是" → 候选。有任何一个是"否" → 排除。

**评估示例**（仅作格式参考，实际结果取决于当前环境）：

| 候选载体 | 自动注入 | 可写入 | 持久 | 结果 |
|---------|---------|-------|------|------|
| AGENTS.md（全局路径） | ✅ 每次 session 自动加载 | ✅ | ✅ | **候选** |
| 项目本地 AGENTS.md | ❌ 非本次 session 工作目录则不加载 | ✅ | ✅ | 排除 |
| 环境变量 | ❌ 仅读取，无写入接口 | ❌ | ❌ | 排除 |

> 此表仅用作格式参考。每次执行时必须基于实际运行时环境重新清查和评估，不得照搬示例。

### Step 3: 推荐方案

从通过过滤的候选中选择最佳方案：

- **优先级原则**：自动注入范围最广、维护成本最低的载体优先
- 如果无候选通过过滤 → 参照 `protocal-init.md` Phase 3 的"回退方案"节

推荐方案应包含：
1. **载体路径**——确切的文件路径或机制名称
2. **合约文本**——需要注入的具体内容。建议包含以下信息：

下方代码块中的 `>` 前缀是模板自身的展示格式（适合直接注入系统提示词 generic-rules 段的场景），不是对载体格式的强制要求。实际写入时须适配载体的已有格式：如载体使用 Markdown 标题和列表（如 RULES.md），合约文本的要素（journal-root 声明、定位立场、价值裁量、读取路由、加载触发、与其他记忆机制的分工）不变，但需转换为标题+列表格式。格式一致可降低 Agent 将合约识别为「外来片段」而跳过的概率。如果是全新载体（无已有格式参考），使用模板的 `>` 引用块格式——它在系统提示词注入场景中最可移植。

   ```
   > Journal root: <journal-root>
   > journal 是你自己的跨 session 长期记忆——经验、决策、调研与方法的沉淀；你为未来的自己写它、维护它
   > 什么值得记：长期仍然有效、脱离具体版本与环境细节仍然可复用的经验、判断与结论
   > ⚠️ 会话开始时读取 <journal-root>/INDEX.md。INDEX 是 journal 的唯一入口，包含当前状态与关键上下文——跳过意味着在信息盲区中操作
   > 读取 INDEX.md 不需要加载 journaling skill
   > 向 <journal-root> 目录中进行任何写入操作（移动、修改、编写、删除等）时，必须加载 journaling 技能并按其指令操作
   > journal 只服务于你自己：不得以 journal 内容为与用户交流的共同背景；客观事实走宿主记忆工具，经验与洞察走 journal
   ```

合约中「读取 INDEX.md 不需要加载 skill」和「写入前需加载 journaling」与 INDEX.md 协议声明节中的读写规则内容重复。这是有意冗余——两层防线各自独立生效，即使一层被忽略另一层仍生效。合约设计时保留此重复。

宿主具备 INDEX 快照注入机制（INDEX 内容随会话自动可见）时，读取动作表述调整为等效的快照说明（如「INDEX 快照已随会话注入，以快照为线索主动读取相关条目」）——「会话开始时读取 INDEX」的义务不变，表述随宿主机制适配，方法见文末「注入文本的设计方法」。

3. **写入方式**——使用哪个工具或命令写入

### Step 4: 呈报用户

向用户说明以下内容，征得同意后再执行：

1. **推荐的载体**和选择理由（为什么用它而不是其他选项）
2. **合约内容**——即将注入的文本
3. **风险说明**——是否影响现有上下文结构、是否覆盖已有内容
4. **备选方案**——如不同意推荐方案，是否有其他可接受选项

用户确认后，由用户或后续 session 执行写入。**Agent 在此阶段不执行任何写入操作。**

## 注入文本的设计方法

模板给的是底线，不是上限——注入文本的表述按宿主实际机制适配；成品模板跨不过环境差异，只有设计方法可移植。

### 要素框架

- **立场**——journal 是什么（agent 自己的跨 session 长期记忆）、是谁的（服务于 agent 自己，不为用户或其他 agent 写）、为什么值得维护（跨 session 接续工作、避免重蹈覆辙）、什么值得记（长期有效、脱离版本与环境细节仍然可复用的经验与判断）
- **路由**——读什么（INDEX 为唯一入口，会话开始时读取）、何时加载 journaling 技能（对 `<journal-root>` 的非只读操作前）、不可做什么（不得以 journal 内容为与用户交流的共同背景）
- **规程不进注入**——操作流程与规则细节不进注入文本，留给按需加载的技能内容与 journal 规则文档；注入只承载立场与路由

「会话开始时读取 INDEX」是强制底线，快照宿主以等效的快照说明表述；要素覆盖不因适配而缺项。

### 写作原则

- **立场先于动作**——动作指令的失败模式是被挤掉；立场完整的注入可推导出动作，并覆盖设计时未预见的场景
- **机制适配**——注入描述宿主的实际机制，同一要素在不同宿主形态不同（如快照宿主把读取动作表述为快照说明）

鼓励按宿主环境发挥要素框架、调整表述——不逐字照搬模板。

### 宿主提示词的更改权限

agent 对宿主提示词（注入文本所在的载体）只能提案、提醒、编写草稿——写入或更改由用户执行，或经用户批准后执行。这是注入文本维护的常态原则，与 `protocal-init.md` Phase 3 的禁令同构。
