# 让技能包合规

技能包要先合法，才谈得上好用：字段缺一个、目录越出白名单、引用断一条，技能都到不了读者眼前。这里收两样东西——开放标准与运行环境各自要求什么（逐条转述，按来源标注），以及交付前怎么核对（机械检查与机器校验）。

两个时机，用法不同：正在摆放文件、想确认某个目录或字段的要求时，从「目录结构」读起逐条比照；交付前核对合规、或核对一个已有技能的结构时，跳到「校验」交给机器跑一遍，再回来看失败项。

## 两套约束

- 结构上的约束来自两个出处，混在一起会让人把环境规定当成通用标准，或反过来。分法：
  - **开放标准**（地板）——不满足就不是合法技能包。字段约束、渐进式披露、引用规范都出自这里。
  - **运行环境追加**——目标环境在标准之上加的要求。例如本仓库要求 `content/` 只含白名单条目、frontmatter 必带 `metadata` 的四个子字段、自定义许可证要附 `LICENSE` 原文。这类要求不出现在标准里，以环境的规则文件为权威。
- 判断一条约束值不值得为它改结构，先看它属于哪侧：地板侧没有讨论空间；环境侧按环境规则执行，且**换环境要重新确认**——方法是读目标环境的规则文件，找技能规范那一节。
- 这里转述标准约束（表内标「标准」），只转述与结构直接相关的环境约束（标「环境」）。分支策略、发布流程这类环境纪律由环境规则提供，不进本文件。
- 目录树从技能根开始画（如 `my-skill/`），不含仓库或磁盘上的上层路径——上层路径是放置细节，不属于技能身份，技能每搬一次家就得改一次树。

## 目录结构

- 一个技能是一个目录，最小合法形态只有一个 `SKILL.md`：加载器按目录发现技能，没有目录就没有技能。
- `SKILL.md` 正文建议不超过 500 行（标准建议值；这是按英文散文密度估的代理指标，中文技能按词元预算折算，见[设计一个技能的结构](structure.md)的分层节）。

| 目录 / 文件 | 装什么 | 装载约定 | 来源 |
|---|---|---|---|
| `SKILL.md` | 元数据 + 指令 | 必须；命中后全量加载 | 标准 |
| `references/` | 按需阅读的文档 | 每份聚焦单一主题、尽量小——文件越小，按需读一次的代价越低 | 标准推荐 |
| `scripts/` | 可执行代码 | 自包含或显式写出依赖；报错信息要有用；边界情形优雅处理 | 标准推荐 |
| `assets/` | 静态资源：模板、图片、查表数据 | 供查阅，不是主阅读路径 | 标准推荐（有的环境白名单不含，用前查目标环境） |
| `templates/` | 提示词或文档模板 | 按需读取 | 环境 |
| `examples/` | 参考示例 | 每个文件以摘要头开始 | 环境 |
| `LICENSE` | 许可证原文 | 仅当采用自定义或非公开引用的许可证时 | 环境（条件性） |

- 标准允许技能目录里出现任意其他文件与目录，上面三个推荐目录只是约定。真正的约束不是目录名单，是**可达性**：一个文件只有在某处有指针指向它时才会被读到。用了非约定目录名，等于放弃「读者会习惯性地往这里找」这份预期，指针一旦漏写，那里的内容对读者就不存在。
- **放静态资源之前先查目标环境允许哪些目录**。标准推荐 `assets/`，但有的环境对 `content/` 的白名单是闭集，只允许固定几个条目——例如本技能的开发环境只允许 `SKILL.md`、`references/`、`templates/`、`examples/`、`scripts/`（加条件性的 `LICENSE`），建 `assets/` 就会超出白名单。换环境按同一问法重判：这个环境允许哪些目录，静态资源在其中对应哪一个。白名单不含静态资源目录的环境，查表数据并入 `references/` 下的查阅型参考或 `examples/` 下的示例，不为此扩目录。
- 放哪个目录与按什么方法写是两回事。模板、工作流、脚本各有各的写法（见 `references/documents/` 与 `references/scripts/` 下的写法参考），不因为落在哪个目录而改变——同一份模板进 `templates/` 还是 `examples/`，写法都一样。按打包位置去翻编写方法是常见的错路。

## frontmatter

`SKILL.md` = YAML frontmatter + Markdown 正文。标准只约束 frontmatter；正文写什么、怎么排版不设限（只给建议：分步指令、输入输出示例、常见边界情形）。

| 字段 | 必须 | 约束 | 来源 |
|---|---|---|---|
| `name` | 是 | 1–64 字符；仅小写字母、数字、连字符；不得以连字符开头或结尾；不得含连续连字符；须等于父目录名 | 标准 |
| `description` | 是 | 1–1024 字符，非空；说明技能做什么与何时用；含帮助识别任务的具体关键词 | 标准 |
| `license` | 否 | 许可证名，或对包内许可证文件的引用 | 标准 |
| `compatibility` | 否 | 1–500 字符；环境需求（目标产品、系统包、网络访问等）；多数技能不需要 | 标准 |
| `metadata` | 标准可选，环境可能定为必填 | 字符串到字符串的键值映射，容纳标准未定义的附加属性 | 标准 + 环境 |
| `allowed-tools` | 否 | 空格分隔的预批准工具列表；标注为实验性，各实现支持度不一 | 标准 |

- `name` 是双重身份：加载器标识 + 用户称呼。改名要同时动目录、`name` 字段、正文称呼与其他技能对它的提及，涟漪比任何一次正文编辑都大——命名要在写 `description` 之前定稳，方法见[让技能被正确命中](disclosure.md)。
- `description` 的字段级约束（长度、必须同时说明做什么与何时用）到此为止；措辞怎么命中匹配面是另一套方法论，见[写入口文件](../documents/skill-md-writing.md)。
- `metadata` 在标准里是附加属性位：识别只看 `name` 与 `description`，加载器不读 `metadata` 做匹配，把版本、作者、更新日期放这里是为了人与工具查阅。环境可能把它升为必填并规定子字段——例如要求 `version`、`last_updated`、`author`、`license` 四个子字段，值在 YAML 里一律加双引号：`version: 1.0.0` 会被解析成浮点数、`last_updated: 2026-06-27` 会被解析成日期对象，加引号强制为字符串，保证读取时类型一致。你的环境定了几项，以环境规则文件为准。

## 校验

- 结构合规是机械问题，可检查三类：frontmatter 完整性（必填字段齐全、`name` 合规且与目录名一致、环境要求的子字段齐全）；引用无断链（正文指向技能内文件的相对路径目标确实存在）；目录与文件都在环境允许的条目内（不在白名单里的目录，换环境时第一处就报错）。
- 标准生态提供参考实现 `skills-ref` 做机器校验（`skills-ref validate ./my-skill`），机械检查 frontmatter 合法性与命名约定。交付前跑一遍，不靠自觉——设计过程靠判断，越接近交付越该让机器兜底。
- 断链的失效形态是静默的：技能照常加载，指向不存在文件的那部分知识在需要时取不到，作者收不到任何报错信号。机器校验是交付前发现它的可靠手段，也是找出问题时唯一不需要判断力就能拿满分的一项。
