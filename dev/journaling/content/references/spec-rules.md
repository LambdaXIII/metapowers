# Rules Specification

> RULES 机制规范层——规则编写的原则与规则设计的提醒。规则文档（RULES.md）是 journal 侧文件，技能强制的唯一规则入口；本文定义"规则文档怎么写"与"设计规则时值得系统化考量的维度"。
> 设计方法（怎么设计分类/标签/约定）见 `design-rules.md`；本文只给提醒与启发，不承载方法。

---

## 规则编写的原则

以下原则在编写或修订规则文档时始终适用：

- **不重复**：技能已有的规范不重复记录——规则文档只记录与默认行为不同或额外的事情
- **允许偏离需理由**：规则可以与技能默认行为不同；偏离时说明偏离了什么、为什么、预期收益
- **规则与笔记分离**：规则文档是规则、条目是条目，检索不互相污染
- **规范变化必须落地**：规则调整后同步到规则文档，不留口头约定
- **自包含且完备**：规则内容应当自包含且完备——不能引用笔记条目、技能内容等不稳定的外部来源（技能升级或条目变化会使规则失效或不可读）

## 规则设计的提醒

规则设计不仅仅是"编写 RULES 文件"，它实际上是**设计一整套系统化的组织方式**，并将其完备的可操作规则等落入 RULES 文件。技能强制的只有最小义务（规则文档是唯一规则入口、写入/导入前必读）——组织方式怎么设计，由 journal 自己决定。以下维度是设计时值得系统化考量的方向，每个维度的取舍取决于笔记库自身的规模与使用方式。

### 放置与检索

笔记库始终要回答两个问题：内容放在哪里、内容如何被找到。放置方式（目录、命名）与检索方式（元数据、标签、索引）是配套的——放置越简单，检索机制越重要；放置越精细，写入判断成本越高。技能种子预置的分类与元数据板块只是简单起点，是否采用、如何调整由 journal 决定：内容很少时可能不需要分类，检索需求低时可能不需要标签。设计时应想清楚：一条新笔记应该被放在哪里？一个旧笔记要靠什么被找到？

### INDEX 的结构

INDEX 是整个笔记库的入口，读取笔记库时，它应该可以起到引导内容检索的作用。

在规则设计中，应考虑：它应该包含哪些信息/板块？哪些内容变动时应实时变更？哪些改动无需调整它？应该谨慎设计 INDEX 的相关规则，平衡其信息丰富/时效性和读写操作时的效率性——信息越全，维护越贵；越简，引导越弱。规则要明确这个平衡点落在哪里。

### 约定

放置与检索机制之外的规则都归入约定：命名习惯、需要特殊处理的 scope、写作流程等。这些约定根据其具体内容，应当有条理地组织——不散落、不互相矛盾。当规则很多时，可以考虑将规则拆分为多文件组织，并通过规则文档（入口）引导到各文件。约定是活的，必要时可随时动态调整。
