# 提示词/指令集推演
> 场景文档 — 配合推演通用论述参考使用。

将 rehearsal（推演）方法应用于提示词、系统指令、任务指令的质量验证。适用于：
- 给 AI 模型的系统提示词或任务指令
- 给人类执行者的操作指令或规范文档
- 任何"按文字指令执行"的场景

与其它推演的核心区别：提示词推演横跨两个维度——
- **内容表达层**：措辞是否准确、表述是否清晰、是否会引起过拟合/欠理解/误解
- **逻辑执行层**：按指令链路走下去，模型/执行者会得到什么结果

两个维度同等重要。大多数载体只关注其中一个，但提示词必须两个同时推演。

---

## 推演者的双重定位

推演提示词时需要一个清醒的"第三者"：不是作者（你知道意图），也不是模型（你正在模拟它），而是**站在中间评估这次通信的观察者**。

- 不要变成作者：你已扔掉设计意图——你看到的只是文本本身
- 不要变成模型：你在观察模型的"理解过程"，不是在真的理解并执行
- 保持评估者位置：每一帧同时问自己——"写得好吗？"和"按这个走会怎样？"
- 尽量客观：推演者的理解和判断能力直接影响推演质量——理解能力不足会导致误判

这条原则参照 通用论述「推演者定位」节的通用论述，提示词场景是它最严格的检验场。

## 客体定位

AI 模型（LLM 或其它指令执行系统）。已知系统提示词和工具定义（如有），无人类常识——只按指令文字执行，没有设计者的隐含假设。

初始状态：
- 只有被注入的提示词和工具定义
- 没有设计意图、没有上下文暗示
- 按字面理解约束——"不要做 X"只看是否说了，不猜作者"应该指的是"


## 推演前：锁定作者视角

在进入推演流程之前，先以作者身份写下以下信息。**不写下来 = 还没想清楚**：

1. **这条提示词/指令是给谁的？** 模型类型（大模型/小模型/代码模型）？执行语境（独立会话/工具链一环）？已知约束（上下文长度、工具集、输出格式要求）？
2. **期望的执行效果是什么？** 正常路径下，模型读完这条指令后应该做什么？输出什么？**不**做什么？
3. **你做的隐含假设是什么？** 你假设模型已经理解了哪些概念？你假设哪些信息会从其他渠道（系统提示词、工具定义、上下文）进入？

写完后再进入推演。推演结束时的评估整理对比的就是这份「作者视角」记录——不是和「你觉得应该怎么样」对比，是和「你当时写的期望」对比。如果推演结果偏离了期望，两个方向都可能是问题：
- 推演路径暴露了指令的模糊或遗漏 → 指令需要改
- 推演结果更优，但偏离了你原来的期望 → 你的设计意图本身可能有问题

不要偷偷修改作者的期望来让推演结果「合格」——推演的价值恰恰在于发现你没想到的路径。
## 四步流程适配

### 1. 准备与清空

清空不是「脑子里告诉自己忘了」——是显式操作。

**第一步：设定阅读身份**

用一段话精确描述你现在的身份。不是「我是一个 LLM」，而是：
> 我是一个被注入以下系统提示词的 LLM。我只有被注入的提示词和工具定义，没有其他上下文。我不猜测作者的意图，不填补文档中的空白。我按字面理解每一条指令。

**第二步：清空不该有的信息**

显式列出你**不拥有**的东西，写在推演记录的开头：

- 我不理解作者的「本意」——我只看到文字
- 我不会「应该能猜到」——没写的约束 = 不存在
- 我没有这段提示词之外的任何背景
- 我不会自动纠正措辞矛盾——我按字面执行

**第三步：锁定评估者位置**

清空完成后，确认你在推演全程中的角色：**你是观察者，不是执行者**。你在观察「如果这个身份的人读到这段文字，会怎么理解、怎么做」，不是在真的执行。每走一步之前自问：我现在是「评估这条指令的人」还是「在执行这条指令的人」？

将这三点写入推演记录开头，作为后续逐帧跟的锚定参照。


### 委派推演（推荐）

自我模拟有一个上限：你作为推演者同时也是作者的同体——你们的推理结构相似。你「清空」掉的假设，你的推理结构会自动补回来。这就是为什么提示词推演中最常见的失败是「滑入模型角色」——你读着读着就真的按你（作者）的意图去理解了。

**将阅读委派给子代理**可以突破这个上限。子代理和你是不同的推理实例——它没有你的上下文，没有你的隐含假设。你给它什么，它就只能从什么出发。

#### 子代理提示词原则

给子代理的提示词必须遵循以下约束：

1. **不透露推演目的**：不要说「帮我检查这条指令有没有问题」「帮我找盲区」——这会让子代理进入评审模式，而不是接收模式。
2. **不透露侧重和倾向**：不要说「重点看约束部分」「注意检查措辞精确性」——这等于提前告诉它哪里有坑。
3. **设定阅读身份而非评估身份**：告诉它「你是 X，你要读 Y」，不是「你是评估者，你要评估 Y」。
4. **只读不执行**：明确指示「只逐段阅读并记录你的理解，不要实际执行任何操作」。
5. **逐段记录而非总结性评价**：要求子代理「每读完一段就写下：你理解这段在说什么？你认为接下来应该做什么？」——不要让它给整体评价。

#### 委派提示词模板

以下是给子代理的提示词模板。使用时只替换 `[ ]` 中的内容：

```
你现在的身份是：[ 客体描述，如"一个被注入了系统提示词的 LLM" ]

你的任务：逐段阅读以下提示词/指令，每读完一段（一个自然段或一个逻辑单元）就写下：

1. 这段在说什么？（你的理解）
2. 读完这段后，你认为你应该做什么？（你的行为倾向）
3. 这段和前文有什么关联或矛盾？

不要给整体评价。不要跳到结论。不要实际执行任何操作。
只阅读、理解、记录。

以下是你要阅读的内容：

---
[ 待推演的提示词/指令全文 ]
---
```

子代理的输出就是一份逐帧阅读记录。你（推演者）的工作是分析这份记录——对比「作者视角」中写下的期望，找出偏离和盲区。

#### 为什么不总是委派

子代理的推理结构和你仍然相似（同模型族）。对于非同构客体（7B 小模型、特定领域专家），委派推演的准确性同样受限。但对同构客体场景（你推演自己的系统提示词、你的 prompt 将被同级别模型消费），委派推演远优于自我模拟——它至少隔离了你的隐含假设。
### 2. 逐帧跟

按阅读顺序逐段走。**每帧记录两列信号**：

**内容表达信号（措辞层）：**

| 信号 | 含义 |
|------|------|
| "这句有歧义" | 可能被理解为多种不同的约束 |
| "这个词太绝对" | 过拟合风险——"永远""必须所有" |
| "这个概念没定义" | 模型不知道具体指什么 |
| "这里跳得太快" | 缺少中间推理步骤，模型跳跃式执行 |

**逻辑执行信号（执行层）：**

| 信号 | 含义 |
|------|------|
| "这条约束和上一条冲突" | 模型选哪条？会不会都违反？ |
| "这个步骤缺失" | 按指令走到了这一步，然后该做什么？ |
| "这个判断条件不完整" | 有些情况没有被条件覆盖 |
| "这个后果描述不够强" | 模型可能忽略约束，因为没有感受到后果 |

### 3. 边界刨

提示词特有的边界场景：

| 场景 | 操作 |
|------|------|
| 缺失前提 | 缺少一条关键上下文，模型是否就偏离了？ |
| 误导性措辞 | 某句话被模型理解为相反的意思——措辞是否足够精确？ |
| 冲突指令 | 两条约束在某个输入下同时触发且互斥——优先级的说明是否清晰？ |
| 过拟合陷阱 | 例子/约束描述了一个具体模式，模型是否误以为只能用这个模式？ |
| 欠覆盖 | 一种常见违规模式没有被任何约束覆盖 |
| 注入攻击 | 用户输入中包含了类似系统指令的措辞——是否防注入？ |

### 4. 评估整理

参照通用论述的 4a-4e 流程。本载体特定要求：

**严重程度格式：** 阻塞/缺陷/建议。三级定义：
- **阻塞**：模型产生错误/不可控输出（如约束冲突、措辞歧义）
- **缺陷**：模型输出质量受影响（如边界未覆盖）
- **建议**：措辞可进一步精确

**评估维度：**

| 评估维度 | 含义 |
|------|------|
| 因果方向清晰度 | 约束的"因此""否则"链路是否明确——模型知道为什么不能这样做 |
| 违规模式覆盖 | 常见的违规行为是否都被约束覆盖了 |
| 自检可执行性 | 检查和判决是否可执行——模型能否自行判断是否违规 |
| 后果说服力 | 违规的后果描述是否有力量——"会出大问题"比"不建议"有效 |
| 边界覆盖 | 边界输入下是否有未定义的约束行为 |
| 过拟合抵抗力 | 例子和约束是否足够通用——不会让模型误解为"只有一个模式" |
| 措辞精确性 | 指令措辞是否精确——不会产生误解或多解释 |

**意图对照注意：** 回到「推演前：锁定作者视角」中写下的三条期望。提示词场景的特殊性：推演结果偏离期望时，两个方向都可能是问题——指令需要改，或设计意图本身有问题。

**修复优先级：** 措辞歧义/约束冲突最先修（直接导致模型行为不可控）。检查七个维度是否均有记录，内容表达层和逻辑执行层是否都覆盖了。

**4e 错误模式搜索候选：**
- **过拟合陷阱** — 例子太具体导致模型误解为「只能用这个模式」
- **约束冲突** — 两条约束在某个输入下同时触发且互斥，优先级未说明
- **后果说服力不足** — 「不建议」比「会导致 X 问题」弱得多，模型可能忽略

## 与逻辑链路推演的关系

提示词推演和逻辑链路推演（`logic-chain-rehearsal.md`）都涉及"按链路跟踪执行结果"。提示词推演中的逻辑执行层面本质上就是一次逻辑链路推演，但叠加在模糊语义之上。关键区别：

- 逻辑链路推演的客体是确定性的**执行引擎**（计算机/解释器），行为可精确预测
- 提示词推演的客体是**AI 模型**，行为不确定、受措辞影响、存在过拟合/欠理解

推演提示词时如果发现执行链路上的缺点，可以引用 `logic-chain-rehearsal.md` 的方法分别推演"被理解的逻辑本身"是否有漏洞。两个独立的推演，各自有各自的载体。

## 常见陷阱

- **滑入模型角色**：读着读着真的去执行了。每步必问自己"我现在是评估者"。
- **忽略内容层**：只跟踪了逻辑没有评估措辞。一个措辞不当的完美逻辑在模型手中就是随机逻辑。
- **忽略逻辑层**：只看了措辞没跟踪执行。一个表达精美但逻辑模糊的指令在模型手中也会执行，但不受控。
- **用作者知识补洞**：某步骤缺失但作者心想"模型应该理解这里"。这就是推演失效——模型没有你的暗示。
- **混淆客体**：把给开发者看的文档当成给模型看的指令来推演，或反之。推演前确认——这份材料的读者是 AI 模型还是人类开发者？开发者内部的组织代号和速记（如层级编号、项目缩写）对 AI 模型而言不传达任何语义，模型只理解自然语言描述；对开发者在讨论中使用这些代号效率更高。推演时用错了读者身份，等于用错误的语言测试理解。
- **跳过作者视角直接清空**：没写下设计意图就开始推演，等于没有对比基线。推演结束后你说「这里有问题」，但和什么比？和你脑子里模糊的「应该」比？写出具体的期望，每一条期望对照推演结果——没对照到的地方就是盲区。
