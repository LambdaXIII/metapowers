# 可读性强化（启发库）

> 通用论述只承诺"以人类可读的说明文形式呈现"这一效果（§5 行文效果提及），具体行文由 agent 自行发挥。本文是**行文级启发材料**——技巧清单与正反例，遇到需要时就地选用，不构成行文规范。注意：语体残留的**认知面**（把"教人理解"做成了"转述指令"）由通用论述 3.4 与 [traps.md](traps.md) 负责，这里只涉及句法层的调整手段。

## 1. 指令 → 说明的语体转换

说明文由指令形态重组而来（转化是形式操作，内容一个不丢）。下面五种转换模式覆盖最常见的指令形态；源中已清晰可读的内容直接摘取，不必强行转换。

### 1.1 祈使句 → 陈述句

| ❌ 指令型 | ✅ 说明型 |
|-----------|-----------|
| 读取 SKILL.md 了解技能功能 | 技能首先读取 SKILL.md 以了解其核心功能 |
| 禁止修改原文件 | 技能仅读取文件，不执行任何修改操作 |
| 使用 SubAgent 执行测试 | 测试通过独立的 SubAgent 执行，以保证隔离性 |

### 1.2 步骤清单 → 流程说明

| ❌ 指令型 | ✅ 说明型 |
|-----------|-----------|
| 第一步：制定方案；第二步：执行测试；第三步：评估结果 | 测试流程分为三个阶段：首先制定测试方案，然后执行测试，最后评估结果 |

### 1.3 约束声明 → 设计理由

| ❌ 指令型 | ✅ 说明型 |
|-----------|-----------|
| 测试 SubAgent 不可读取 eval_metadata.json | 为保证测试的客观性，测试执行者不应提前了解预期结果 |

注意：理由来自源则直接呈现；源没有而可推断的，按通用论述 3.3 标注 `[推断: 依据]`。

### 1.4 检查清单 → 定义 + 检测方法

| ❌ 指令型 | ✅ 说明型 |
|-----------|-----------|
| 检查 SQL 注入 | SQL 注入是通过用户输入拼接 SQL 的攻击方式。技能通过搜索字符串拼接模式来识别此类风险 |
| 检查硬编码密钥 | 硬编码密钥是将 API 密钥、密码等敏感信息直接写入源代码的安全隐患。技能通过搜索 API_KEY、SECRET 等关键词来检测 |

转换公式：检查项 → 问题/威胁定义 + 检测方法说明。

### 1.5 决策规则表 → 场景-行为-理由表

| ❌ 条件 → 动作 | ✅ 场景 → 行为 → 理由 |
|----------------|------------------------|
| 文件 > 500 行 → 标记大文件警告 | 文件超过 500 行 → 标记大文件警告并建议拆分 → 大文件通常意味着职责不单一，维护成本高 [推断: 基于约束反推] |

理由列同样遵循推断纪律：源中有则直接呈现，推断必须标注。

### 何时保留指令型表达

以下情况保留指令型是合理的：**快速开始**（指导读者立即使用）、**操作步骤**（读者需要按步骤执行）、**注意事项**（必须遵守的约束）。判断标准是读者意图：需要读者行动的地方可以指令化，解释机制的地方必须说明化。

## 2. 金字塔原则（任何组织内部适用）

金字塔四原则是横切行文原则：无论说明文选用哪种组织模式（structure/ 模式手册 8 种），章节内部、段落内部都适用。

| 原则 | 含义 | ❌ 反例 | ✅ 正例 |
|------|------|---------|---------|
| 结论先行 | 先说核心观点，再说支撑论据 | 先罗列机制细节，最后才说"总之，这个技能用于安全检查" | 开篇一句话定义技能并说明解决什么问题，再展开机制 |
| 以上统下 | 上层是下层的概括，下层是上层的支撑 | 标题"关于流程的一些说明"下面装的是决策规则 | 标题概括下属全部内容，子项都支撑标题 |
| 归类分组 | 同组内容属于同一范畴 | 触发条件、输出格式、术语混在同一个列表里 | 触发条件、输出格式、术语各自成组 |
| 逻辑递进 | 按时间、结构、重要性等顺序排列 | 步骤乱序，读者不知道先后依赖 | 按流程先后、或按从重要到次要排列 |

示例——先结论后支撑：

> 这个技能把指令形态的技能内容转化为说明文教学材料，让人类可以通过阅读学会这项技能。（结论）
> 转化是形式操作：内容一个不丢，只重组呈现方式。（支撑一）
> 重组的目标是利于学习：先概览后细节，术语先定义后使用。（支撑二）

自查：每段开头有结论句吗？上层能概括下层吗？同组内容同范畴吗？排列有明确顺序吗？

## 3. 清晰与简洁

### 3.1 清晰：具体化模糊词

模糊词让读者无法确定含义，说明文必须落到可执行、可验证的具体表达：

| ❌ 模糊 | ✅ 具体 |
|---------|--------|
| 适当处理 | 保留核心原则、关键步骤、检查清单 |
| 根据需要 | 当用户要求测试技能时触发 |
| 相关文件 | SKILL.md、references/ 目录下的文件 |

### 3.2 简洁：删冗余

| ❌ 冗余 | ✅ 简洁 |
|---------|--------|
| 为了确保测试的准确性和可靠性，我们需要在执行测试之前制定一个详细的测试方案 | 执行测试前制定方案 |
| 通过使用这种方法，我们可以有效地提高效率 | 提高效率 |

### 3.3 一致：术语与格式统一

- 同一概念始终用同一词汇——一个概念一个术语，不换花样
- 标题层级、列表样式全文统一
- 语态、时态统一：优先主动语态与现在时——"技能读取文件"而非"文件被技能读取"；"技能提供……"而非"技能提供了……"

一致性直接服务于可读性：读者不用猜测"这个词和前面那个是不是同一个意思"。

## 选用原则

- 以上技巧按需选用，不是检查流程：遇到具体行文问题再回来翻对应小节
- 转换服务于"教会读者"，不为转换而转换——源中已清晰的说明型内容直接摘取（通用论述 2.3 提取要素：清晰内容保留）
- 句法调整永远不能替代内容判断：一段话即使句式漂亮，若踩了陷阱（失真 / 漂移 / 推断未标注），仍需按 [traps.md](traps.md) 修正
