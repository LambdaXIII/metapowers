# 逻辑链路推演
> 场景文档 — 载体符合时必读。按 `../rehearsal-guide.md` 的路由指引加载。

将 rehearsal（推演）方法应用于任何**预定逻辑流程**的验证。适用于：
- 代码运行时逻辑：程序按语句逐行执行的结果
- 配置规则：多层配置的优先级、合并、覆盖行为
- 决策树/规则引擎：输入数据按规则匹配后到达的叶子节点
- 数据转换管道：数据从源头经多步变换后的输出
- 工作流编排：步骤的分支流转和条件判断

不适用：文档内容 → `doc-guide-rehearsal.md`、交互体验 → `interaction-rehearsal.md`、接口契约 → `api-design-rehearsal.md`。

---

## 客体定位

执行引擎——对给定的逻辑/规则/代码进行**机械执行**的实体。它没有判断、不会纠错、不理解意图——只执行定义，不看注释。

特征：
- 精确执行：每一步按语义定义走，从不断章取义
- 不填补缺口：未定义的路径就是真正未定义的行为
- 不宽容：输入格式偏差、类型错误、除零立刻抛出
- 无上下文暗示：不会因为一个值在语义上"不应为负数"就自动纠正

## 与其它推演的区别

| | 逻辑链路 | API 设计 | 交互流程 |
|---|---|---|---|
| 客体 | 执行引擎 | 调用者 | 操作者 |
| 发现 | 行为与意图的偏差 | 契约覆盖/命名/可操作性 | 体验障碍 |
| 关注点 | 控制流、状态、资源 | 接口表面 | 困惑点、放弃率 |
| 粒度 | 语句/规则级 | endpoint 级 | 步骤/操作级 |

逻辑链路推演是唯一客体非"人"的 场景文档——推演时不需要模拟"这个人物会怎么想"，而是模拟"这段定义会怎么执行"。正因为如此，逻辑链路通常可以更客观、更可重复。

## 四步流程

> 推演前先完成通用论述中的「作者视角」和「清空」步骤。

### 1. 清空

参照通用论述的「作者视角」和「清空」步骤：

1. **回看作者视角**：确认你在推演前已写下「这段逻辑的目标是什么、边界在哪里」。
2. **设定阅读身份**：你是执行引擎——你不会说「也许设计者的意思是...」，你只按照代码/规则/配置的**字面定义**机械执行。
3. **显式清空**：扔掉设计意图。不知道「这个值在这里永远是正数」、不知道「这个分支之后会加处理」、不知道「注释说返回非 null 所以肯定是非 null」。只看定义，不猜意图。

### 2. 逐帧跟

按执行顺序逐语句/逐规则跟踪。每步记录：

| 信号 | 含义 |
|------|------|
| "条件未完整覆盖" | 某些输入走入了未预期的分支——条件逻辑有空洞 |
| "状态修改打破后续假设" | 某处修改了变量/字段，后面代码仍假设旧值 |
| "隐式依赖未满足" | 依赖的变量在上面的分支中没有初始化——某些路径下崩溃 |
| "类型转换丢失信息" | 截断、舍入、精度丢失——数据已损坏 |
| "资源不对称管理" | 获取和释放不在同一层次——有的路径泄漏 |
| "时序不确定性" | 并发操作的不确定顺序——结果依赖调度 |

记录格式不是"客体感到困惑"（客体不是人），而是"执行引擎在这个输入下的行为与设计意图偏差在于..."。推演者自己对比"定义会导致什么"与"设计意图应该是什么"。

### 3. 边界刨

逻辑链路的边界场景：

| 场景 | 检查目标 |
|------|---------|
| 零值、最大值、负值 | 边界输入下行为是否合理——除零、溢出、负数表示 |
| 空集合、单元素集合、巨型集合 | 极端规模下的性能和正确性 |
| 并发/交错的时序变化 | 竞态条件下不变量是否保持 |
| 异常路径中的状态 | 异常抛出那一刻调用栈各层的状态是否一致 |
| 资源耗尽 | 文件句柄耗尽、内存耗尽、超时——降级行为是否存在 |
| 类型边界 | 浮点精度边缘、整数溢出、字符编码问题 |

### 4. 打分

| 维度 | 含义 |
|------|------|
| 控制流正确性 | 在给定输入范围内，执行是否按预期走正确的分支 |
| 边界条件覆盖 | 边界/极端值输入下是否有未处理或未预期的行为 |
| 状态一致性 | 数据/状态在操作序列中始终满足不变量 |
| 资源生命周期 | 资源（内存、文件句柄、连接、锁）的获取/使用/释放是否完全配对 |
| 异常安全 | 异常路径中是否有状态腐败或资源泄漏 |
| 隐式假设可见性 | 依赖的前提（如"这个值一定不为 null"）是否被显式声明或验证 |


## 与提示词推演的逻辑层关系

提示词推演（`prompt-instruction-rehearsal.md`）的「逻辑执行层」本质上就是一次逻辑链路推演——将模型理解的指令作为"定义"，跟踪其执行链路。关键区别是逻辑链路推演的"定义"是精确的（代码/规则），而提示词推演的"定义"是模糊语义——模型可能理解错误。

如果推演提示词时发现了逻辑链路层面的缺陷，可以引用本文件的方法分别推演"被理解的逻辑本身"是否有实锤漏洞。两个推演分开执行——先确定表达层的问题，再确定逻辑层的问题。

## 常见陷阱

- **带入意图而非只看定义**：代码写着 `if x > 0`，但你知道"x 在这里永远是正数"所以跳过验证——盲区
- **只走正常路径**：最高频的 bug 在"从未想过会发生"的路径
- **忽略时序/并发**：单线程逻辑完美，两个并发操作在同一数据上就是随机结果
- **把注释当契约**：注释说"返回非 null"，某个分支返回了 null——执行引擎只看代码
