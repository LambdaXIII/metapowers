# 设计一个技能的结构

内容写完之后要落到文件里：进哪个目录、叫什么名字、读者从入口怎么走到它。开放标准与环境划定地板（各自要求什么见[让技能包合规](standards.md)）；地板之上，结构按内容灵活组织，没有统一的目录配方。这里讲怎么取舍，判据是四条原则：**清晰、有条理、便于查看、便于维护**。下面先看清文档集合的整体形状，之后每一条具体建议，都是这四条原则在它上面的应用。

## 先看清文档集合的整体形状

一个技能的全部文档连起来是一张以 `SKILL.md` 为唯一根的有向图：一条引用就是一条从这份文档指向那份文档的边。这张图的合法形状有四条要点；同一张图怎么按成本组织，是下一节的事。

- **根不被指向。** `SKILL.md` 是唯一入口，读者永远从它进来，其它任何文档都不指向它。理由：回指入口是一句冗余指针——读者读到它时手里正拿着入口，它不提供任何新内容，只让阅读路径绕回起点。场景：支撑文档结尾那句「先读 `SKILL.md`」删掉；「某形态的完整写法见 `references/...`」保留。
- **树干按领域、话题递归切分。** 根以下的每份文档都由一次切分得到：先按领域或话题分成组，组内再按需要继续切——组内按什么轴继续切，后文「references 内部是分层的」讲的就是这条边的局部。理由：切分让读者在需要的时机找得到要找的那份。场景：文本类编写方法与脚本编写方法各成一组，找写作方法的人不必翻脚本内容。切分同时产生深浅：从根往下每切一次就深一层，这条深浅定出先后——后文说的上移（往根的方向）与下沉（往深的方向）就是沿它移动。
- **横向互指成网。** 参考文档之间允许互相指向，合法的方向是展开与参照：一份把某个点讲透，另一份在需要时指过去。理由：这样的互指各有真实落点——被展开的对象就在被指向的那一份里。判断一条互指是否合法，问「它在展开什么」——有明确的被展开、被参照对象，这条边就合法。反过来，两份文档互相引用、各自不完整、靠对方补自己缺的那一块，不是网，是硬拆的症状（见[设计一个技能](../skill-design.md)）。场景：一份讲判断依据、另一份展开某形态的完整写法，两边互指合法；两份文档各写半截、互相指过去凑完整，不合法。
- **单链合法，环不合法。** 单链（A→B→C，无分叉）就是不带分叉的树，完全合法——顺序展开的内容天然成链。无环约束落在实质论述依赖上：「做 A 要依 B 的要求、B 的做法在 C、C 又说该话题的论述在 A」（A←B←C←A）这样的循环依赖不合法——它让读者绕圈，而且每处看上去都有道理。纯导航与回访类指向（「所属工作」「返回上一层」这类）不承载论述依赖，不在无环约束之列；回指 `SKILL.md` 是另一回事——「根不被指向」已经把它排除了。场景：两份文档一份承接另一份的结论顺序读下去，合法；三份文档各自把做法推给对方、绕成一圈，不合法。

## 按加载成本分层

这张图的形状定了之后，三层是它在加载成本上的一种推荐配置，不是结构本身——成本只解释纵深方向的取舍（一份内容放多深），解释不了横向切分（按什么轴分成几组）。

| 层 | 内容 | 成本形态 |
|---|---|---|
| 元数据 | 全部已发现技能的 `name` + `description` | 约 100 词元；常驻，每次会话全程付费 |
| 指令 | 被命中的技能的 `SKILL.md` 正文 | 建议 5000 词元以内；命中后一次性全量加载 |
| 资源 | `references/`、`scripts/`、`templates/`、`examples/` 中被链接的文件 | 按需付费，不读不花 |

- 三层成本形态不同，推荐的组织方向也随之定下：匹配信号留在元数据层，决策依据放指令层，长论述后置到资源层。把长论述写进 `SKILL.md`，等于让它在每次命中时都被全额支付，无论这次任务用不用得上。
- **预算按词元算，不按行数算。** 开放标准建议的「正文不超过 500 行」（转述见[让技能包合规](standards.md)）是按英文散文的字符密度估的代理指标；中文每单位信息的词元开销高于英文，同样 500 行中文正文的词元数通常是英文的两倍以上。写中文技能把 5000 词元换算成字数（约两三千汉字）当预算，别拿行数当安全线。拿不准就在你的环境里实测一次正文的词元数，这个数字比任何经验值都可靠。

### 入口只留每次命中都要用的

- 三层里只有指令层是每次命中全额支付的，所以 `SKILL.md` 只承担被命中、触发决策、路由三件事。完整的方法论述、执行流程细节、检查清单展开都不进 `SKILL.md`，后置到资源层。判据就是那句：**这一句每次命中都要用到吗**——不是，就后置。
- 极简不是越短越好。太薄会退化成一张纯目录：读者在路由处看不出该选哪条，只能全扫一遍。留多长的判据是——读者读完路由，能否不看支撑文件就判断「我该读哪一份」。
- 主文档自己要独立站住，不假设读者先读过 `SKILL.md` 的其他段落或别的支撑文件。特化文档是补充不是替代：它只承担某一类情形的展开，主干里该有的判断依据不能只存在于特化文档里——那样按主干走的读者会缺一块。
- 入口文件的具体写法（前提节怎么产生、路由按什么轴组织、索引与路由怎么合一、不触发条件放哪里）见[写入口文件](../documents/skill-md-writing.md)。

### references 内部是分层的

- 资源层不是一堆平铺的文件，它有自己的层级：顶层一份**主文档**（`SKILL.md` 直接路由到它，承载这个方法的主干），其余按一个切分轴分成组。
- 分组有两种实现，二者等价，按组的体量选：
  - **子目录** —— 组内文件多且分组稳定时用，如 `references/scenarios/`、`references/quick-test/`。
  - **文件名前缀** —— 每组只有两三份、平铺就能看清全貌时用，如 `design-*.md`、`spec-*.md`。
- **目录名与文件名共同承担路由信息**，这是分层最大的收益：读者看到 `references/structure/pattern-iceberg.md`，路径本身已经说了「结构类 / 模式 / 冰山模型」；看到 `scenarios/api-design-rehearsal.md`，就知道「场景类 / API 设计」。路由表因此不必为每个文件重述它属于哪一类，而平铺的文件名做不到这一点，只能靠文件名里的主题词去猜。
- 分组的轴按**读者需要的时机**选：同一主题下的内容常常在不同时机被需要，混进一个目录会让读者在错误的时机读到它、在需要的时机找不到它。至于按什么轴切——载体类型、使用情境、工作阶段——由内容决定；判据始终是读者在需要的时机找得到它，且维护者不看内容也能从目录名猜到里面装什么。
- 链上每多一跳，就多一次「要不要追读」的决策，也多一个断链点；子目录不消耗跳数（路径深不等于链长）。层级按这个代价权衡，不为层数立数；新增的文件必须挂在一条真实的阅读路径上——读者任何真实路径都走不到的内容，对读者不存在。
- 引用一律写从技能根出发的相对路径（`references/structure/pattern-iceberg.md`），不写绝对路径、不带上层目录。绝对路径只在作者机器上成立，上层目录一换就断。

## 内容该放哪一层

- **留在 `SKILL.md`**：每次命中都要用到的判断依据——这次该走哪条路、什么情况下不该用这个技能、各文件的分工。
- **下沉到资源层**：只在某个分支上用到的展开——某形态的完整写法、某类场景的处理、供查阅的资料。
- 下沉不是免费的。后置内容的到达率完全押在指向它的那句指针上（指针三要素见[打磨技能文字](../documents/writing-craft.md)），而且断链是静默的——技能照常加载，取不到内容时没有任何报错。下沉前先算这笔账：省下的常驻成本，是否抵得过到达率上的风险。
- 过度下沉的症状有两种：入口只剩一堆链接，读者在路由处无从选择；或某个判断依据只存在于深处，读者在入口层做决定时手里没有它。修法都是把那一句上移，不是把深处的内容复制上来——复制会让两处从此不一致。
- 一小节能不能独立成一份文件，看两条：它会被读者单独进入吗（有没有读者只找它、不需要先读别的），以及内容重量撑不撑得起一份文件（只有两三句的小节切出去，多一次跳转却省不下阅读量）。
