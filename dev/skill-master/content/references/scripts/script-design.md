# 技能脚本的取舍与设计

## 真工具判据

- 「配个脚本」的诉求不是答案，先诊断属于哪种情形：真工具、信息缺口、手段
  固化。三种修法完全不同。
- 先查最简单的可能：缺的是不是知识。工具已存在、入口已引用而提交者没读到
  ——病根是信息缺口，修法是在引用处写提醒，不是再造工具。
- 再看诉求固化的是「要做什么」还是「用什么做」：前者是知识，写进正文；
  后者是手段，属于启发层。手段固化后读者照脚本机械执行，不再现场判断——
  每轮要验证的面并不相同，灵活性正是在这里丢掉的。
- 只有动作本身是任务才是真工具。判断信号：跨文件的组合关系、内容不变的
  机械重复、输出要结构化供下游处理——信号越齐越值得写。

## 脚本是便利设施

- 脚本优化的是力气不是能力：把文档里已写明的动作跑得更快更稳，不承载读者
  在文档里读不到的知识。技能对脚本无硬性依赖——脚本不可用，技能仍须可用。
- 校验方法：把脚本删掉，零上下文读者还能不能只靠文档完成同一件事——慢
  一点但能完成？不能，说明脚本在偷偷承载知识，搬回文档。
- 引用写法：凡提到脚本的地方，手动做法必须写全，脚本只是附加提示；「运行
  脚本 X」式的句子在脚本不可用时把读者断在半路。

## 三层披露

- 引用脚本的文档在同一处交代三层，少交代一层读者就卡在哪一层：
  - 做什么——一句话说清任务与适用场景，读者据此判断值不值得跑；
  - 怎么用——最常用场景的用法示例，一两个就够；完整命令参考交给 --help
    或脚本旁的参考文档；
  - 失败时的表现与处置——报错长什么样、通常意味着什么、下一步做什么。
    这层最容易被省也最伤人：读者分不清是自己用错还是脚本出错。

## 与知识的边界

- 内容进脚本还是进文档，看执行时还要不要现场判断：判断依据（标准是什么、
  这次查哪些、结果怎么解读）是知识，写文档；判定已定、剩下的是机械重复
  动作（遍历、比对、按固定规则转换），才进脚本。
- 脚本替不了读者回答「这结果意味着什么、下一步怎么决定」；硬塞进去等于
  把判断冻结在写脚本那一刻的场景里。
- 划界与改动以功能角色为单位，不以主题词为单位：同主题内容可能服务完全
  不同的场景。收到合并、简化脚本的诉求先做角色分离，只动真正冗余的目标；
  说不清某部分被哪个场景验证过，就不该顺手圈进改动。
