# 打包一个技能

技能包能不能被加载器认出来，与你把它写得多好是两件事：结构不合规，文字再精确也到不了读者眼前。本册把「标准规定了什么」收在一处，好让设计、修改、审查三种工作不必各自重述一遍约束。

读本册的两个典型时机，对应的用法不同：

- 正在摆放文件结构、决定内容放哪个目录时 —— 从「目录结构」读起，逐条比照。
- 交付前核对合规，或审查他人技能的结构维度时 —— 直接跳到「校验」，交给机器跑一遍再回来看失败项。

## 基线与基线之上

- 标准的规定是地板，不是建议：不满足就不是合法技能包。判断是否值得为一条约束改结构，先看它属于哪一侧——地板侧没有讨论空间，基线之上的组织方式（几个文件、怎么切、标题叫什么）完全是作者的事。
- 一份技能包常常要同时满足两套约束：开放标准的基线，加上目标运行环境的追加要求（例如某个环境要求 frontmatter 携带版本与作者、某个仓库要求正文不超过特定长度）。两套各有出处，追加约束不出现在标准里，本册也不转述任何具体环境的追加要求——以各自规则为权威。
- 基线之上如何把内容写好，不在本册：打包位置（本册）与编写方法（[documents/ 与 scripts/ 各册](../documents/writing-craft.md)）是两回事。工作流文档即便放进 `assets/`，写法仍按工作流册——按打包位置找编写方法是常见的错路。

## 目录结构

- 技能是一个目录，最小合法形态只有一个 `SKILL.md`。加载器按目录发现技能，没有目录就没有技能。
- 标准推荐三个可选目录，各自的约定与用途：

| 目录 | 装什么 | 装载约定 |
|---|---|---|
| `scripts/` | 可执行代码 | 自包含或显式写出依赖；报错信息要有用；边界情形优雅处理 |
| `references/` | 按需阅读的文档 | 每份聚焦单一主题、尽量小——文件越小，按需读一次的代价越低 |
| `assets/` | 静态资源 | 模板、图片、查表数据等供查阅的资料，不是主阅读路径 |

- 标准允许技能目录里出现任意其他文件与目录，上面三个只是推荐约定。真正的约束不是「目录名单」，而是**可达性**：一个文件只有在某处有指针指向它时才会被读到。用了非约定目录名，等于放弃「读者会习惯性地往这里找」这份预期，指针一旦漏写，那里的内容对读者就不存在。
- 目录树从技能根开始画（如 `my-skill/`），不含仓库或磁盘上的上层路径。上层路径是放置细节，不属于技能身份；技能每搬一次家就得改一次树，是纯维护噪音。

## frontmatter

`SKILL.md` = YAML frontmatter + Markdown 正文。标准只约束 frontmatter；正文写什么、怎么排版，标准不设限（只给建议：分步指令、输入输出示例、常见边界情形）。

| 字段 | 必须 | 约束 |
|---|---|---|
| `name` | 是 | 1–64 字符；仅 ASCII 小写字母、数字、连字符；不得以连字符开头或结尾；不得含连续连字符；须等于父目录名 |
| `description` | 是 | 1–1024 字符，非空；说明技能做什么与何时用；含帮助识别任务的具体关键词 |
| `license` | 否 | 许可证名，或对包内许可证文件的引用 |
| `compatibility` | 否 | 1–500 字符；环境需求（目标产品、系统包、网络访问等）；多数技能不需要 |
| `metadata` | 否 | 字符串到字符串的键值映射，容纳标准未定义的附加属性 |
| `allowed-tools` | 否 | 空格分隔的预批准工具列表；标注为实验性，各实现支持度不一 |

- `name` 与目录名双向一致，且它是双重身份：加载器标识 + 用户称呼。改名要同时动目录、`name` 字段、正文称呼与其他技能对它的提及，涟漪比任何一次正文编辑都大——技能一旦交付，改名就是结构性变更，命名要在写 `description` 之前定稳。命名方法见[设计技能的披露](disclosure.md)。
- `description` 的字段级约束（长度、必须同时说明做什么与何时用）到此为止；措辞怎么命中匹配面是另一套方法论，见[设计技能的披露](disclosure.md)。标准规定这个字段必须有什么，披露论述规定怎么写才命中。
- 标准未定义的附加属性走 `metadata`。识别只看 `name` 与 `description`，加载器不读 `metadata` 做匹配——把版本、作者、更新日期放这里是为了人与工具查阅，不是为了让技能更容易被命中。

## 渐进式披露

标准按上下文成本把技能内容分成三层，组织必须与加载行为对齐：

| 层 | 内容 | 成本形态 |
|---|---|---|
| 元数据 | 全部已发现技能的 `name` + `description` | 约 100 词元；常驻，每次会话全程付费 |
| 指令 | 被命中的技能的 `SKILL.md` 正文 | 建议 5000 词元以内；命中后一次性全量加载 |
| 资源 | `references/`、`scripts/`、`assets/` 中被链接的文件 | 按需付费，不读不花 |

- 三层成本形态不同，组织方向因此确定：匹配信号留在元数据层，决策依据放指令层，长论述后置到资源层。把长论述写进 `SKILL.md`，等于让它在每次命中时都被全额支付，无论这次任务用不用得上。
- **预算按词元算，不按行数算。** 标准给的「正文不超过 500 行」是按英文散文的字符密度估的代理指标；中文每单位信息的词元开销高于英文，同样 500 行中文正文的词元数通常是英文的两倍以上。写中文技能时把 5000 词元换算成字数（约两三千汉字）当预算，别拿行数当安全线。拿不准就在你的环境里实测一次正文的词元数，这个数字比任何经验值都可靠。
- 引用纪律：技能内引用一律从技能根写相对路径；深度保持一层（`SKILL.md` → 支撑文件）。每多一层链就多一次「要不要追读」的决策，也多一个断链点。

## 校验

- 结构合规是机械问题，可检查项三类：frontmatter 完整性（必填字段齐全、`name` 合规且与目录名一致）；引用无断链（正文指向技能内文件的相对路径目标确实存在）；目录与文件都在约定位置（不在，就要有指针指过去）。
- 标准生态提供参考实现 `skills-ref` 做机器校验（`skills-ref validate ./my-skill`），机械检查 frontmatter 合法性与命名约定。交付前跑一遍，不靠自觉——设计过程靠判断，越接近交付越该让机器兜底。
- 断链的失效形态是静默的：技能照常加载，指向不存在文件的那部分知识在需要时取不到，作者收不到任何报错信号。机器校验是交付前发现它的可靠手段，也是审查时唯一不需要判断力就能拿满分的一维。
