# 计划文档推演
> 场景文档 — 配合推演通用论述（`../rehearsal-guide.md`）参考使用，补充计划文档载体的特化内容。

将推演方法应用于计划文档的质量验证。适用于：

- 实现计划、实施方案
- 项目路线图、迭代/冲刺任务拆解
- 迁移计划、发布计划
- 任何「告知执行者按指定步骤达成某目标」的文档

## 本载体的核心差异：执行通路

这类载体的核心差异：推演的终点不是「执行者能否理解」，而是「执行者理解后能否正确执行」。计划文档的执行者在执行过程中会面对现实世界的意外（依赖不可用、中间结果不符预期、外部变化），因此推演需要评估的不仅是理解通路——还有执行通路。

计划文档的消费方式也不同于纯文档：不是一次性读完，而是**边读边执行**——执行者会在不同步骤之间反复回到文档查阅。因此每个步骤节点都要能独立地为执行者提供指引（做什么、如何判定完成），不依赖前文的上下文（这是 P1S1 被消费情境在本载体的具体化）。

## 执行者定位（P2 身份设定的要点）

执行者可以是**人**（如一位不熟悉该上下文的开发者）或**新 agent**（如一个新的 LLM 会话）。两种执行者共享以下初始状态：

- 知道项目的**背景和目标**（从计划文档的背景段得知）
- 但**不知道计划的制定者当时的设计思考**——不知道取舍理由、不知道排除过哪些方向、不知道哪些部分是核心不可改、哪些是建议可发挥
- 手头有这份计划文档（可能还有配套的上下文参考资料）
- 目标是「执行完这套步骤，达成预期的效果」

人和 agent 在执行时的差异在推演中需要区分对待：

| 差异点 | 人 | 新 agent |
|--------|----|----------|
| 歧义容忍度 | 能凭经验推断模糊表述 | 按字面执行，不推断 |
| 常识填充 | 会用自己的知识填空缺 | 只使用上下文内的信息 |
| 边界感知 | 知道哪些是「不合理的」操作 | 不知道边界——需明确告知范围 |
| 专注度 | 可能跳读、疲劳 | 逐项执行，不漏 |

对 agent 更苛刻的条件（歧义零容忍、边界不知）往往也能覆盖人可能遇到的问题；反之，仅对人优化的计划可能对 agent 不充分。推演时可以选定一种执行者类型作为主要视角，然后在边界场景阶段检查另一类型的适配性。

## 身份转换的补充（P2 划掉清单）

计划文档的作者在写计划时知道的但执行者不知道的内容，特别需要显式划掉：

- **取舍谱系**：「当时在 A、B、C 三个方案中选了 A」——划掉。执行者只看到 A，不知道 B 和 C 为什么被排除
- **隐性并行空间**：「步骤 2 和步骤 3 可以同时做」——如果没写，就是隐含知识。执行者会串行执行，浪费并行窗口
- **完成标准直觉**：「步骤 4 做完就是 '完成了'」——作者心里有完成标准但没写成文字。执行者不知道做到什么程度算「做好」
- **弹性标记**：「这里的 3 天是宽松估算」——作者知道某步的弹性，但执行者看到 3 天就当作硬性的 3 天
- **状态传递假设**：「步骤 3 做完后自然进入步骤 4」——划掉。作者默认步骤间的输出会自动传递，但执行者需要知道输出放在哪里——文件路径、环境变量、数据库，还是「刚做过」的隐含状态。不指定存放位置，下一步无法正确开始

## 模拟阅读的补充（P3）

在通用论述的信号之外，计划文档推演需特别关注以下信号：

| 信号 | 含义 |
|------|------|
| 「这里不知道什么算完成」 | 缺少 Definition of Done——步骤完成后如何判定「做好了」 |
| 「这里不知道为什么这么做」 | 缺少目标解说——只有操作，没有预期效果。执行者在遇到意外时将僵化执行或判停 |
| 「这里不知道能不能并行」 | 依赖关系不显式——执行者无法判断该步骤与前后步的先后/并行/阻塞关系 |
| 「这里不知道意外怎么办」 | 缺少异常分支——只覆盖了顺利路径，无失败/跳步/外部变化预案 |
| 「这里知道要做什么但不知道不做什么」 | 仅有推荐做法，无禁止做法——执行者可能过度发挥或走向错误方向 |
| 「这里不知道范围到哪」 | 缺少边界声明——执行者不知道什么在计划范围内、什么在范围外 |
| 「这里不确定是不是另有方案被排除」 | 正向理由充分但无逆向排除——执行者无法判断「选 A」是因为 A 最优还是只是没考虑别的 |

**节点独立性验证**：随机选一个非起始步骤，只从该步开始模拟阅读——如果缺少前置信息导致无法理解该步，说明节点的独立性不足，需要补充上下文。

## 边界与异常场景（P4 补充）

计划文档推演值得覆盖的异常路径。每个场景推演时检查：当该场景发生时，按现有计划文档能否得到明确的应对指引？

| 异常场景 | 推演检查 |
|---------|---------|
| **步骤执行失败** | 某一步失败了（工具报错、构建失败、API 返回异常）——计划是否有降级/重试/跳过策略？执行者是否能独立判断用哪个策略？ |
| **中间结果不符预期** | 某一步正常完成但产出不合预期（如生成了错数据、选择了错误的分支）——计划是否提供检查点和回退路径？ |
| **资源/权限不可用** | 需要的工具/环境/API key/访问权限在第一步才发现没有——计划是否前置声明了所需资源？ |
| **跳过某步** | 执行者因某种原因跳过了某步（误读/意外跳过/简化）——后续步骤仍可执行吗？状态缺失是否会引发串联错误？ |
| **突发外部变化** | 执行过程中外部条件变化（依赖版本更新、API 废弃、人员变动等）——计划是否有「重新评估截止点」（计划中设定的定期/触发式重新评估外部条件的检查节点）？ |
| **跨粒度跳跃** | 大型步骤内部隐藏了小型决策（如步骤 3「优化模块 A」实际包含调研、改代码、测试等多个子步骤——这些子步骤应有自己的说明） |

**推演检查动作**（不是异常事件，是推演者自己的检查）：若选定的主体视角是「人」，在「这里不知道为什么这么做」信号处检查：如果 agent 读到同样内容，会不会更严重？反之亦然。

## 评估整理（P5 的要点）

**严重程度格式：** 阻塞/缺陷/建议。三级定义：

- **阻塞**：执行者无法按计划完成目标（如关键步骤不可执行、依赖未声明、完成标准缺失导致无法判定终点）
- **缺陷**：执行者能完成但效率或效果受影响（如缺少目标解说导致遇到意外时僵化、推荐/禁止未分离导致轻度误操作）
- **建议**：可读性或组织优化（如编号系统不统一、步骤顺序可优化）

**评估维度提示（额外提示，非硬性指标）：**

| 评估维度 | 含义 |
|---------|------|
| 背景充分性 | 执行者读完背景段，能否理解「为什么制定这个计划」——触发条件、约束、动机三者是否完整 |
| 意图完整性 | 整体和各阶段是否有目标解说（预期效果），不仅是操作指令。遇到意外时执行者能否根据意图决定如何灵活调整 |
| 逆向排除度 | 决策点是否有「为什么不」——排除了什么方向/方案、为何排除。执行者不会误以为选择是唯一偶然 |
| 步骤可判定性 | 每条步骤的完成是否可以客观判定（Definition of Done 是否明确、可验证） |
| 粒度一致性 | 步骤之间的复杂度是否在同一量级。大型步骤内部是否组织了子结构（阶段/步骤两级） |
| 依赖可见性 | 先后/并行/阻塞关系是否显式标注，而非隐藏在叙述文本中。执行者能据此设计并行执行策略 |
| 边界清晰度 | 「推荐」和「禁止」是否分离——哪些是硬约束不可改动、哪些是建议可发挥 |
| 异常覆盖 | 是否有非顺利路径的预案——失败/跳过/外部变化/资源缺失类场景的覆盖情况 |
| 执行策略充分性 | 是否主动给出依赖图、并行建议、顺序优化建议（区别于依赖可见性的被动标注——可见性看关系是否显式写出，本维度看是否给出可执行的策略建议） |

**复现对照注意（P5S1）：** 回到 P1S3 整理的作者意图（编写时的理解），按四向对照复现理解——不仅对照「读者能否理解」，还对照「按计划执行能否达成预期效果」。

**错误模式搜索候选（P5S5）：** 以下为计划文档推演中常见错误模式（不是穷举清单，超出清单的根因应正常记录）：

- **操作有，目标无** — 各步骤只写做什么，没写达到什么效果。执行者遇到意外只能僵化执行或原地判停
- **正向有，逆向无** — 解释了为什么选 A，没说为什么不选 B。执行者无法判断选 A 的理由是否适用于自己的情况
- **依赖埋藏在文本中** — 依赖关系写在叙述段落里而非显式标注（如「安装完成后运行配置脚本」——没写「配置脚本」和「安装」的关系）
- **边界遗漏** — 推荐做法给了，禁止做法没给，或没标注哪些是硬约束
- **粒度失衡** — 某一步的复杂度明显超出其他步骤，内部隐含多个原子操作未拆解
- **状态传递假设** — 定义见身份转换的补充（P2 划掉清单第 5 项）；对 agent 执行者是高频错误源
- **编号系统不统一** — 编号有歧义或缺少连贯的编号规则，导致援引出错

## 与设计方法论文档推演的关系

本场景文档与 `design-doc-rehearsal.md` 的边界：design-doc 推演验证**方法论本身**是否自洽、可复现（读者按方法论执行设计）；本场景推演验证**按计划执行的路径**通/不通。当一份文档同时包含方案设计 + 实施步骤时，两者可配合使用：先推演方案设计，再推演执行计划。
