# 设计思想型内容的提取提醒

> 梳理时遇到设计理由/决策依据类内容时按需加载。本文只讲「怎么提取不失真」；怎么写进说明文由你自行发挥（行文见 general/readability.md）。

## 这是什么

**定义**：技能中「为什么这样设计」的内容——设计理由、决策依据、设计动机。

**识别线索**（读到以下任一即属此类内容）：

- 「之所以…是因为…」「设计初衷」「核心理念」「指导思想」
- 决策记录（「我们选择 X 因为…」）
- 「为了…」「目的在于…」
- README.md、CHANGELOG.md 中的演进与取舍理由
- 约束旁边的理由注释（「5000 行上限，防止上下文溢出」）

设计理由是学习者理解技能「为什么长这样」的入口。这类内容的最大风险不在提取而在补充：源里没有理由时，说明文常会「顺手」补一个，把推断当原文呈现。

## 提取注意点

1. **明写的理由原样提取**。
   注意：源中写明的理由不增不减——理由的表述、它支撑的设计点、出现位置三者对应保留。
   为什么：明写的理由是源内容的一部分，丢失 = 省略。

2. **理由与设计点对应**。
   注意：每条理由明确它解释的是什么——哪个约束、哪个流程选择、哪个阈值。
   为什么：理由脱离设计点就成了孤立断言，读者不知道它在解释什么。

3. **决策依据完整**。
   注意：源中记录的决策过程（选 A 不选 B 的原因、权衡）原样保留；被否定的方案如果源里写了也要保留。
   为什么：只保留结论丢掉权衡 = 劣化「为什么」的完整呈现。

4. **理由与版本关联保留**。
   注意：CHANGELOG 等来源中理由附属于哪个版本/变更，提取时保留该关联。
   为什么：理由的时效性是它的一部分——为 v2 引入的理由不等于 v1 也适用，剥离版本会误导学习者。

5. **推断按纪律标注**。
   注意：源中没有理由、但说明文需要补充「为什么」时，按 exposition-guide.md 3.3 的可推断性分类处理：约束反推/行业常识/流程逻辑可推断，标注 `[推断: 依据]`；设计者主观取舍/需项目上下文/超出领域不可推断，标注 `[未推断: 原因]`。
   为什么：推断与原文混在一起 = 学习者把猜测当设计事实。

6. **不可推断时不推断**。
   注意：无法确定是否可推断时，不推断，标注 `[未推断: 无法确定]`；不为了「完整」硬凑理由。
   为什么：硬凑的理由是添油加醋，比缺失更糟——虚构的「为什么」会让学习者误解设计意图。

7. **推断与原文可辨**。
   注意：即使标注了 `[推断: …]`，推断内容与源原文在说明文中也要位置分离、表述可辨，不把推断写进对源内容的转述里。
   为什么：标注是形式，可辨性是实质——标注被忽略时读者仍能看出哪些是原文。

8. **理由来源定位齐全**。
   注意：理由常散落在 README.md、CHANGELOG.md、references/ 而不在 SKILL.md；按 exposition-guide.md 2.2 定位全部位置。
   为什么：只读 SKILL.md 会系统性遗漏设计理由。

9. **提取不评价**。
   注意：提取理由时不评价理由好坏（「这个理由站不住」）。
   为什么：本技能只读源、不评价技能；评价超出阐述职责，也会把学习者引向对设计的批判而非理解。

## 常见失误

- **反例 1**：源里明写「5000 行上限为防止上下文溢出」，说明文只留「5000 行」，理由丢失。
- **反例 2**：源没有理由，说明文写「这个阈值是为了平衡性能」且无标注——把猜测当原文呈现。
- **反例 3**：推断虽标注了 `[推断: 基于约束反推]`，内容却写进了对源规则的转述段落，读者分不清哪句是源、哪句是推断。
- **反例 4**：源里记录了「曾考虑 X 方案，因 Y 否决」，说明文只写「采用 A 方案」——权衡过程丢失。

## 自查提示

- 源里每条明写理由都有对应提取吗？理由解释的设计点标出来了吗？
- 所有补充的「为什么」都带 `[推断: …]` 或 `[未推断: …]` 标注吗？
- 推断内容与源原文在表述上可区分吗？
- 有没有因为「说不清就不完整」而硬凑出来的理由？
- 源里记录过的被否决方案/权衡过程都保留了吗？
