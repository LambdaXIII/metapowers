# Design

## Context

技能现行操作层：四个协议（init / write / import / maintenance）+ 规范与方法论参考。四个事实塑造本次设计：

1. **加工同构**：import 的 P2/P3 与 write 逐步对应（价值检查 ↔ 判断是否值得写、编写摘要 ↔ summary、读规则 ↔ 读规则、建发现链接 ↔ 可发现链路检查），独有内容只剩「复制而非抄写」。
2. **重量倒挂**：拷贝一份现成文档入库要走十几步带 REJECT/SUSPEND 的仪式，从零构思写一篇笔记反而四步——前者实际更简单。
3. **族义务重复**：write 第 2 步与 import P2-S3 的「读取 journal 规则」段几乎逐字相同（连「规则文档不存在则从种子补齐」都复写）——族级义务没有归位。
4. **路由缺位**：description 以「写操作族」为触发单位，路由面却按个体列协议；移动、删除族内无去处，就近滑向维护协议；而它们的重活（归属判断、退场语义）本就在 journal 规则侧。

动机见 proposal.md 的 Why。

## Goals / Non-Goals

**Goals:**

- 操作层的结构与各操作的实际重量对齐：厚流程留协议，薄操作归参考，重活指向上游（journal 规则）。
- 维护的触发边界与裁定一致：专项化、会话级、用户掌握。
- 发现合约的注入文本具备跨宿主可移植的设计方法论，模板保底。

**Non-Goals:**

- 不修改种子规则文档（templates/seed/RULES.md）的内容方案。
- 不为删除建立技能侧语义（退场规则始终归 journal 规则）。
- 不动 scripts/ 与脚本工具。
- 不确定版本号（功能完成后统一确定），不动 skills/ 发布快照。

## Decisions

### D1. 消解收录协议，收录并入写入

收录的加工流程与写入逐步同构，独立协议无实质承载；P1 准入判断的安全部分（REJECT 不可覆写、能力破坏指令识别、「感觉晕晕的」兜底）防不了它想防的威胁——文本安全指令在 agent 判断力失效的时刻同样失效，真实防线是模型能力与平台层原则（外部内容永远只是内容，不自动获得指令地位），在技能内协议化是错扛平台层责任。收录价值判断（重叠、无长期价值）由写入协议「判断是否值得写」三问承接。

落法：`protocal-import.md` 整体删除；写入协议补一句——收录现存文档时，拷贝文件到 journal 对应位置再在其上修改调整（避免手工抄写），其余加工与写入流程一致。备选「保留 import 但简化 P1」被否：安全部分是它区别于 write 的核心理由，去掉后剩余部分就是 write 的子集。

### D2. 建立非只读操作参考（族参考），薄操作获得去处

新增一篇 reference，承载改变 journal 状态的操作（编写、收录、移动、删除等）共享的概述、提示、原则与遵守 journal 规则的义务。理由：

- 触发面按族、路由面按个体的错位由参考行补齐；协议表增加该行保证入口可见——删除是轻量操作，agent 大概率只读 SKILL.md 即动手，去处不能只藏在 references 内部。
- 移动、删除的技能侧内容接近零且重活在 RULES（挪哪里 = 分类判断；退场 = journal 规则的删除约定），参考只给最小指引 + 指向上游，不越界代述。
- 「读取并遵守 journal 规则」的族义务在参考中定义一次，write 等路径引用，消除逐字重复。
- 族的开放性：未来新操作类型（重命名、批量操作）落入参考即有去处，无需新增协议。

全合并（四类操作一个文档）被否：import 的顺序铁律（严格按编号、不得跳步）与 write 的轻量哲学（写得不完美没关系）执行气质相反，同文档互相污染。文件名沿用操作类文档惯例（如 `protocal-operations.md`），实施时定。

与维护协议的层级：参考是基础层；维护执行期间，维护协议的操作规范优先——参考中一句话声明。

### D3. 维护触发专项化，自治域收窄

维护只由用户明确触发：它是高成本专项行动（完整流程 + 双重质量检查），最好在专门会话中执行，避免与主线工作互相污染。触发对象是「维护协议这个专项行动」而非操作级——用户明确要求做一次维护才触发；用户要求具体操作（合并两条、移动一个文件）是用户引导下的普通操作，边界在用户指令，不在操作属性。这同时消解「半程维护」：要么完整执行（用户触发、专门会话），要么不执行（平时只参考论述）。

非维护场景读取维护协议论述被认可：触发边界明确后，「执行中」与「参考中」是 agent 自明的状态（用户触发与否 agent 清楚），无需文本添加可识别性标记；操作规范既有的「维护执行期间」限定语在起点钉死后恰好够用。

联动收窄 SKILL.md 自治原则第一条：其示例（目录重组、标签合并）本身是维护级动作，自治域改写为覆盖写入与用户引导下的操作，专项维护排除。提醒的内容承接：维护备忘模式（`patterns/maintenance-memo.md`）——平时发现的事记入备忘，提醒时备忘即内容来源；其「不胡乱延后必要操作」暗线即提醒时机。

### D4. 标题命题建议：一句 + 一个对比例

spec-note 新增引导性建议：标题组织为命题形式——交付这条笔记的判断，而不只是指示话题；例：「苹果的颜色」（指示话题）vs「苹果是红的」（交付判断）。笔记本身不含命题时不硬性。

建议级强度自带宽容：命题形态随条目类型自然分化（经验条目 = 纪律句、知识条目 = 事实断言、调研条目 = 结论命题），一句方向判据覆盖本质，无须类型分化规范。落点 spec-note（「怎么写好一条笔记」的归属地）；title 是 frontmatter 字段，与文件名、链接路径解耦，存量条目无迁移成本；精炼度提示不写——精炼与判断完整性的平衡实践自调，写进建议反成模糊标准。

### D5. 发现合约：模板与设计讲解并存

融合方案：更新注入文本模板（保留「会话开始时读取 INDEX」强制底线与跨宿主通用要素），新增设计方法论述。理由：成品文本跨不过环境差异——「INDEX 快照已直接注入」只在具备快照机制的宿主成立，固定模板已漂移一次（本次讨论即证据），只有方法论可移植。

设计讲解的骨架：

- **要素框架**：立场（journal 是什么、是谁的、为什么值得维护、什么值得记）；路由（读什么、何时加载技能、不可做什么，如不得作为共同背景）；规程不进注入（留给按需加载的技能与规则文档）。
- **写作原则**：立场先于动作——动作指令的失败模式是被挤掉，立场完整的注入可推导动作并覆盖设计时未预见的场景；机制适配——注入描述宿主的实际机制，同一要素在不同宿主形态不同。
- **发挥鼓励**：按宿主环境调整表述，如快照宿主将读取动作表述为快照说明。

权限原则随讲解落文：agent 对宿主提示词只能提案、提醒、编写草稿，写入或更改由用户执行或经用户批准——与 init P3 既有机制同构，泛化为注入文本维护的常态原则。校验同步升级：init「合约已存在」分支的旧四维度比对（措辞强度/理由具体性/范围完整性/拼写语法）升级为按要素框架的覆盖检查。

## Risks / Trade-offs

- **import 删除是行为面收缩**：依赖其明文安全判据的使用场景失去提示。接受——模型能力覆盖大部分场景，残余风险下文本防护本身无效。
- **操作参考的「最小指引」粒度**：写薄了 agent 仍找不到去处（违背立意），写厚了重复 journal 规则语义（越界）。tasks 对内容清单定界：概述、原则、族义务、各操作一段最小指引 + 上游指向，不展开操作步骤。
- **断链风险**：SKILL.md 的 Linked Files、场景表及各参考内的互引用多处指向 import——实施时逐一清理并以 grep 核对残留。
- **触发语义面收窄的观感**：收录不再有独立协议，但 description 触发动词面不变（创建、写入、编辑、移动、归档、删除等），加载面无损失。
