# 发版计划 · 五问

> 这一批的边界、文档底线与发布节奏需要拍板；已定的部分写在下面，不再占题。
>
> 本卷示范：每题前的实质论述、多级章节、同一章里的多道题、插图、四种题型与推荐标记。版式随内容取用，不是必写项。

## 已定事项

- 这次发版包含命令行工具与配置层，不含图形界面。
- 发版节奏从「随时发」改为「按批次发」，第一批不晚于本月底。
- 文档随代码一起发，不单独排期。

## 范围

核心命令已经跑通，导出与批处理还停在分支上，两边各有未收尾的边界。本月底是第一次对外承诺的日期，按现在的进度，两条路只能走完一条。

收窄的代价不在代码，在预期：用户拿到的是半套功能，文档得替我们把「暂时没有」讲清楚，否则会被当成缺陷报回来。一起做的代价落在时间上——多出来的那个季度里，刚改成按批次发布的节奏会被第一批拖长，后面几批排期都得顺延。这两笔账哪笔更值得，我判断不了。

### 第一批的边界

时间只剩三周，加上回归测试与文档，实际能动的代码时间是两周半。收窄的话，导出与批处理整体推到第二批，接口先按最终形态留好，用户升级后不会因为后续改动再动一次配置。

```single-choice
<scope> 第一批交付到哪儿？
- [x] <narrow> 只做核心命令：本月能上线，用户暂时看不到导出与批处理。
- [ ] <wide> 连周边一起做：功能完整，上线推到下个季度。
```

### 文档底线

文档一直由写代码的同一批人兼着，不在排期里占时间，所以从来没定过下限。上一批上线后，用户问得最多的是两类事：怎么从旧版本升上来，以及某条报错是什么意思——这两部分当时都是空的，全靠值班的人现答。

这次想先定下限，再决定谁补。否则收窄省下的那点时间，会被临场答疑吃掉。

```multi-choice
<docs-gaps> 第一批必须包含哪些文档内容？
- [x] <migration> 从旧版本迁移的步骤
- [x] <errors> 常见报错与处理方式
- [ ] <tutorial> 分步教程
- [ ] <api> 配置项逐条说明
```

前两项缺了，用户会卡在升级当天；后两项可以等第二批补。

## 发布方式

内部用户平时跟着主干走，出问题反馈得快，也愿意试；外部用户不会。两条路径的工程量差不多，差别在暴露面——以及出了问题谁先知道。

### 灰度

内部灰度一周的时长是从上一批估出来的：那次的三个问题里有两个在第三天就暴露了，第三个到第十天才被提起。一周能拦住大多数，但拦不住慢热的那类。

```yes-or-no
<canary> 第一批先对内部用户开放一周，再对所有用户发布。
- [ ] <yes> 先内部一周：能拦下大部分问题，代价是公开发布晚一周。
- [ ] <no> 直接公开：月底如期，代价是问题直接暴露在外部。
```

### 出了问题怎么办

上一批的做法是出问题就回滚，结果同一个缺陷回滚了两次、第三次才修好。这次想把默认动作先定下来，免得当场凭手感决定，也免得每次都在群里讨论半小时。

```single-choice
<rollback> 发布后发现问题时，默认动作是什么？
- [ ] <revert> 立刻回滚到上一版：影响面最小，代价是问题留着没修
- [x] <patch> 当天出补丁：用户不用重装，代价是补丁本身可能再引入问题
- [ ] <defer> 攒到下一批一起修：省事，代价是问题要留一周
```

## 节奏怎么走

灰度与公开发布之间只判断一件事：这一周里有没有阻断问题。有就延后、修完重新灰度；没有就直接全量。整套动作四个节点，不需要额外审批。

```mermaid
flowchart LR
    A["内部灰度一周"] --> B{"有阻断问题?"}
    B -- 有 --> C["延后公开发布"]
    B -- 没有 --> D["全量发布"]
    C --> E["修复后重新灰度"]
```

## 尚未想清的地方

上面四题都是我至少能列出选项的部分。真正没成形的是另一件事：这次改动会不会影响已经写脚本调用老接口的用户——我到现在没想清楚该怎么验证，也没把握给你几个备选。

```single-choice
<open> 这次发版还有哪些我没提到的顾虑？
```

开放题只收自由输入，不产生选项；不写也不影响前面几题的裁决。

五题答完，范围、文档底线、发布与回滚都有了落点。跨题的顾虑写进卷末总评，比如「整体太赶」这类不适合塞进单题的话。
