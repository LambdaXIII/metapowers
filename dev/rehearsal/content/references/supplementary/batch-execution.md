# 批量并行推演执行
> 按需参考 — 被引用时加载。

通用论述「执行策略」中的**委派并行推演**是策略层面的推荐；本文档是采纳该策略时、推演场景较多（≥ 5 个）情况下的执行方法——通过独立的并行子代理高效执行并生成全局聚合报告。

本文档以知识库多场景推演（`knowledge-base-rehearsal.md` 的角色矩阵）为主要适用场景；其他载体的多场景推演可参考本文的调度与聚合骨架。

---

## 适用条件

- 推演场景数 ≥ 5 个（4 个及以下的场景逐个执行或单推演者委派即可，见 `prompt-instruction-rehearsal.md` 的委派推演）
- 每个场景是独立的角色 × 路径，彼此之间不依赖对方的中间结果
- 目标产物是一份**全局聚合报告**（而非每个场景的独立判断）

---

## 执行流程

### 第 1 步：设计角色矩阵

按 `knowledge-base-rehearsal.md` 的角色矩阵设计推演场景。每个场景包含：

- **角色**：身份、知识水平、目标
- **路径**：在入口文档的决策树中走哪条分支、依次加载哪些参考文件
- **验证点**：可逐项判断的具体问题（如"6-7 个可逐项判断的命题"，数量按载体情况调整）
- **边界场景预设**：2 个以上的异常场景（参照通用论述 P4 的主动尝试边界/极端条件）

### 第 2 步：分批调度子代理

受可用并行度限制（按实际环境调整，通常 3-4 个并发/批），将场景分入多个批次：

```
Batch 1 (3 concurrent) → S1, S2, S3
Batch 2 (3 concurrent) → S4, S5, S6
Batch 3 (3 concurrent) → S7, S8, S9
Batch 4 (1) → S10
```

批次间无依赖时无需等待前批完成——由调度器排队即可。

**每个子代理的上下文必须包含：**
1. 推演方法（通用论述的推演步骤）——因为子代理没有读过推演技能
2. 该场景的**载体与范围**（通用论述 P1S1：被推演的文件、覆盖范围、衔接带）及完整角色、路径、验证点、边界场景预设
3. 评估维度定义（知识库批量推演给 `knowledge-base-rehearsal.md` 的 5 个维度；子代理不知道这些维度的定义）
4. 输出格式要求（逐段走查 + 验证点判断 + 边界场景 + 评估整理 + 缺陷清单）
5. 目标文件的绝对路径（或可访问的定位方式）

**关键约束：**
- 不要让子代理执行"先探索项目结构"的任务——它只需要读取指定的文件
- 验证点必须表述为可逐项判断的命题（通过/部分通过/失败 + 证据）
- 单条发现的严重程度按通用论述 P5S3 的格式判定（阻塞/缺陷/建议）

### 第 3 步：聚合报告

所有批次完成后，汇总各子代理的报告：

**产出物：**
1. **评估矩阵表**：每个场景 × 各维度评估（维度分按 ★ 1-5 打分：每个子代理对各评估维度给出 1-5 分及证据——★ 是跨版本量化追踪工具，仅作聚合呈现，不替代严重程度判定）
2. **全局缺陷清单**：按缺陷类别聚合所有场景的发现（类别来源见 [缺陷分类法](../supplementary/defect-taxonomy.md)），归为 3-5 个类别
3. **按维度的横切分析**：计算每个维度的均值，找出最强/最弱维度（维度均值比单个分数更有参考价值——子代理间可能有偏见差异）
4. **场景热力图**：按维度总分排序，标出优秀/良好/警告等级
5. **核心结论**：3-5 条关键发现

**聚合时的注意：**
- 子代理报告是自述性的——同一缺陷可能在不同场景中以不同措辞出现。聚合时需要**归纳为缺陷类别**而非简单罗列（对应 P5S5 错误模式提取的结构性判断）
- **聚合呈现顺序 ≠ 修复顺序**：聚合按出现频率归类（见下文模板），修复优先级仍按通用论述 P5S4 的严重程度排序——阻塞级缺陷即使只出现 1 次也最先修
- 异常容错维度几乎必然是最低分——这是知识库验证推演的系统性规律，而非某个具体知识库的个别问题
- 发现数量 ≤ 10 个时无需分档格式化，直接列出缺陷类别即可

**异常处理：**
- 单个子代理失败/超时 → 重试一次，仍失败则该场景标记"未完成"并如实记录（或降级为单推演者委派）
- 子代理报告相互矛盾 → 作为聚合讨论项列出，标注矛盾点，不强行统一
- 某场景无发现 → 如实标注进评估矩阵（空维度需回答：确实没问题还是没检查——通用论述 P5S4）

### 第 4 步：生成修复计划

基于聚合报告的缺陷类别，制定分组的修复计划：
- 每个缺陷类别映射到 1-2 个具体文件
- 优先修复"系统性缺口"（如多个文件共同缺少某种指引）而非"个别文件措辞"
- 修复计划应标注每个缺陷的可验证关闭条件
- 修复完成后的回归验证：按 `knowledge-base-rehearsal.md` 的「多轮迭代修复验证」（Round 2/3 回归）进行——修复是否生效需要重新推演验证，不是推演技能本身的工作范畴，而是材料所有者的后续动作

## 经验观察

以下为实践中的经验观察（10 场景知识库推演）：

| 指标 | 逐个执行 | 批量并行 |
|------|---------|-----------|
| 耗时 | 逐个串行，数小时 | 分批并行，显著缩短 |
| 报告质量 | 质量随执行者疲劳下降 | 每个子代理独立专注，质量一致 |
| 缺陷发现率 | 高点在前期场景 | 均匀分布，边界场景也充分挖掘 |
| 聚合洞察 | 靠执行者事后回忆 | 结构化报告可直接交叉对比 |

## 缺陷类别聚合模板

发现数量较多（如 > 10 个）时，按出现频率三档格式化（**频率分档，不是严重程度**）：

```markdown
### 🔴 高频（出现 ≥ 3 次）
| 类别 | 出现次数 | 影响场景 | 描述 |

### 🟡 中频（出现 2 次）
| 类别 | 出现次数 | 影响场景 | 描述 |

### 🟢 低频（出现 1 次）
| 类别 | 出现次数 | 影响场景 | 描述 |
```

聚合原则：跨越具体文件/位置的差异，找到**根因类别**。例如"路径末端缺收束"是一个类别，可能出现在 4 个不同文件中。

## 与场景文档及通用论述的关系

- 场景文档知识库推演（`../scenarios/knowledge-base-rehearsal.md`）是**方法论设计**——定义角色、评估维度、检查信号类型；本文档是**执行方法**——当场景数 ≥ 5 时如何通过并行子代理高效完成推演并生成全局报告。两者互补：方法论决定"推什么"和"怎么判断"，执行方法决定"怎么跑"和"怎么汇总"
- 通用论述「执行策略」的委派并行推演是策略入口；单推演者委派子代理代读（而非批量执行）的方法见 `prompt-instruction-rehearsal.md` 的「委派推演」
