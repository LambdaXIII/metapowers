# journaling Specification

## Purpose

本域是 Agent 长期记忆的笔记本系统技能。Agent 跨 session 工作但记忆不跨 session，本技能启发、引导 agent 为自己设计一套结构化的长期记忆笔记系统，解决「写了不读、写了找不到、写了变噪音、写了不维护」四个问题。设计目标是让 agent 自发形成持续演进的笔记系统：记笔记成为自然行为，系统随内容生长，每个新 session 能从先前状态继续。journal 服务于 agent 自身，不服务于用户；系统的具体形态由各 journal 自主决定，技能只提供设计考量与可改的默认方案。

## Requirements

### Requirement: 行为边界
本技能提供「为自己设计一套 journal 长期记忆系统」的指导：启发、引导 agent 为自己设计 journal，而非直接定义 journal 运行的细节。技能内容陈述设计考量与可改的默认方案，对任何具体 journal 的运行细节（分类方案、字段、目录、维护安排）不做规定。

#### Scenario: 分类归属不由技能裁定
- GIVEN 某 journal 的规则文档定义了分类方案
- WHEN 判断一条新内容的目录归属
- THEN 依该 journal 规则裁定，本技能不预设任何强制分类

#### Scenario: 维护不自动启动
- GIVEN journal 存在条目过期或标签蔓延迹象
- WHEN 判断是否启动维护
- THEN 只在用户明确要求时执行；agent 不自行启动维护，可提醒用户触发，并建议在专门会话中进行

#### Scenario: 维护论述的非执行阅读
- GIVEN agent 在用户引导下进行小规模整理或日常写入
- WHEN 需要整理与维护相关的判断依据
- THEN 可读取维护协议的论述作为启发性参考，这不构成维护协议的执行，其流程义务不被触发

### Requirement: 硬性机制
本技能只允许五项机制以硬性约束出现在技能内容中：

1. INDEX 的可发现性保证（发现合约）；
2. 读取与写入的不对称加载：读取 journal 不加载本技能，写入必须加载；
3. INDEX 作为 journal 的入口；
4. RULES 作为规则记录的单一入口，且必须存在；
5. 笔记文件含 YAML 段。

「RULES.md」这一入口名由第 4 项绑定；其内容自定，可自组织为多文件。

#### Scenario: 硬性机制不出此列
- GIVEN 技能内容中以强制措辞陈述的机制
- WHEN 对照本清单
- THEN 只出现这五项，不存在清单之外的硬性机制

### Requirement: 引导性机制
其余一切机制（分类方案、标签集、字段、目录结构、INDEX 板块、维护信息等）在技能内容中只能以引导性建议表述：不使用强制措辞，不要求必填字段，不断言特定目录存在。

#### Scenario: 引导性机制被写成硬性要求即违规
- GIVEN 技能内容要求「每条笔记必须填写某字段」
- WHEN 检查表述
- THEN 判定违规，该机制只能作引导性建议表述

### Requirement: 触发语义
触发边界是操作范围约束而非场景枚举：凡对 journal-root 的写入性操作（创建、写入、编辑、移动、归档、删除、维护、整理、写入设计决策等）都加载本技能；读取访问不要求加载，技能也不为读取增加任何加载要求。description 保持「操作范围约束 + 写入操作示例」结构，不退回场景白名单；保留中英操作动词触发面。

#### Scenario: 新说法的写入操作同样受约束
- GIVEN 用户以新措辞要求把某决策写入 journal 文件
- WHEN 判定是否加载
- THEN 该操作落入 journal-root 写入范围，加载本技能

#### Scenario: 只读访问不加载
- GIVEN 本 session 只需浏览 INDEX.md 与查阅条目
- WHEN 判定是否加载
- THEN 不加载本技能

### Requirement: 收录并入写入
现存文档收录为 journal 条目时，将文件拷贝到 journal 对应位置，再在其上修改调整（避免手工抄写）；frontmatter、summary、链接、分类等加工与写入流程一致。技能不设独立收录协议，不设收录准入判断流程与收录专用安全边界。

#### Scenario: 收录走写入路径
- GIVEN 用户要求将一份现存文档存入 journal
- WHEN 执行收录
- THEN 拷贝文件到目标位置后按写入流程加工，不执行独立的收录协议

#### Scenario: 收录价值判断承接自写入
- GIVEN 待收录内容与 journal 既有条目高度重叠或无长期价值
- WHEN 判断是否收录
- THEN 按操作协议「判断是否值得写」的判据处理，技能内容不另设收录准入步骤

### Requirement: 发现合约的模板与方法
技能内容同时承载发现合约的注入文本模板与设计方法论述。模板保留「会话开始时读取 INDEX」的强制底线与跨宿主通用要素；设计方法论述给出注入文本的要素框架（定位立场、使用路由、操作边界）与写作原则，表述按宿主实际机制适配（如具备 INDEX 快照注入机制的宿主以快照说明替代读取动作）。agent 对宿主提示词只能提案、提醒、编写草稿；写入或更改由用户执行或经用户批准。

#### Scenario: 模板保留读取底线
- GIVEN 使用发现合约的注入文本模板
- WHEN 检查模板内容
- THEN 「会话开始时读取 INDEX」的指令存在且为强制表述，不因宿主差异从模板中移除

#### Scenario: 按宿主机制适配表述
- GIVEN 宿主具备 INDEX 快照注入机制，INDEX 内容随会话自动可见
- WHEN 编写该宿主的注入文本
- THEN 依据设计方法论述将读取动作表述调整为快照说明，要素框架不缺项

#### Scenario: 宿主提示词的更改权限
- GIVEN agent 发现注入文本与设计方法论述存在实质缺口
- WHEN 处理该缺口
- THEN agent 向用户提案或提醒，可编写草稿文本，写入或更改由用户执行或经用户批准

### Requirement: 协议条目与加载指引
「协议」在本技能中是对特定操作的称呼：技能内容提及一个协议，即指名该项操作并指引向这项操作的论述。协议条目不展开操作步骤——方法在论述中。加载指引中的协议条目载明触发时机：何种操作加载该协议，使读者从入口即可判断何时读什么。

#### Scenario: 协议条目即指引
- GIVEN 技能内容中的某个协议
- WHEN 检查其表述
- THEN 它指名一项特定操作并指引到该操作的论述，不在条目内展开操作步骤

#### Scenario: 协议条目载明触发时机
- GIVEN 加载指引中的协议条目
- WHEN 检查其表述
- THEN 条目载明触发时机，读者无需打开协议文件即可判断何种操作需要加载它

### Requirement: 操作协议
技能设一篇操作协议，承载改变 journal 状态的一切操作（新建、补充、编辑、收录、移动、归档、删除等）的共同逻辑：读取并遵守 journal 规则、价值与归属判断、关联一致、INDEX 反映。各操作只留差异指引，不按操作轻重拆分文档；协议名与加载指引明示覆盖全族操作，编辑、移动、删除不因名称被误归入维护协议；具体语义（删除的退场规则、移动的归属判断）由 journal 规则承载；技能不设删除协议，不预设删除语义。

#### Scenario: 全族一条协议
- GIVEN 改变 journal 状态的一项操作
- WHEN 按加载指引寻找操作去处
- THEN 去处是操作协议一处，不存在按操作轻重划分的第二文档

#### Scenario: 编辑与移除不误入维护
- GIVEN 用户要求编辑、移动或删除某条 journal 条目（非维护场景）
- WHEN agent 按加载指引寻找操作去处
- THEN 去处是操作协议；协议名与条目表述不将其引导至维护协议

#### Scenario: 删除请求路由到 journal 规则
- GIVEN 用户要求删除某条 journal 条目
- WHEN agent 按操作协议的删除差异指引执行
- THEN 读取该 journal 规则的删除约定执行，不落入维护协议，也不将维护协议的操作规范当作删除规程

#### Scenario: 族义务单处定义
- GIVEN 新建、补充、编辑、收录、移动、删除各操作路径
- WHEN 陈述「读取并遵守 journal 规则」的义务
- THEN 该义务在操作协议中定义一次，各操作路径引用它，不逐字重复

### Requirement: 发现合约论述与步骤的分工
发现合约的方法以论述承载：这项工作的介绍、判断依据与事实（注入文本模板、要素清单、检测清单）在论述中定义一次；初始化协议的发现合约阶段只承载步骤——目标、禁令、动作序列、完成条件——引用论述而不重复其事实。

#### Scenario: 事实单处承载
- GIVEN 注入文本模板、要素清单与检测清单
- WHEN 在技能内容中查找其定义位置
- THEN 只在发现合约论述中定义一次，协议步骤只引用不复制

#### Scenario: 步骤只承载定序与边界
- GIVEN 初始化协议的发现合约阶段
- WHEN 检查其内容
- THEN 只含目标、禁令、动作序列与完成条件，方法细节指向论述

### Requirement: 内容边界
技能内容只承载运行时读者需要的操作事实与判断依据。技能内容不承载文档自述、设计理由与权衡、历史叙事、写给未来编辑者的注记、免责式表述；有承载功能的信息（术语首现定义、文档间路由）归入正文与加载指引，不以自述形式存在。

#### Scenario: 文档自述即违规
- GIVEN 技能内容中的任一文档
- WHEN 检查其开头与正文
- THEN 不存在「本文件提供/定义/分为……」式自我定位与结构介绍，正文直接进入读者的操作或判断内容

#### Scenario: 设计理由与编辑者注记不入内容
- GIVEN 文档中的重复、命名、格式等编排选择
- WHEN 检查技能内容
- THEN 不出现其设计理由、权衡说明，或写给未来编辑者的保留/注意注记

#### Scenario: 历史叙事不入内容
- GIVEN 技能内容中的示例与启发
- WHEN 检查其表述依据
- THEN 不以带日期的个案事件或重构沿革作为论述依据

### Requirement: 读者路由
加载指引的参考文档清单承载参考层的读者路由：逐条载明加载时机，回答「何时读」，不只列文件名。技能内每篇参考文档都从该清单可发现。

#### Scenario: 清单载明加载时机
- GIVEN 加载指引中的参考文档清单
- WHEN 任取一条检查
- THEN 能从中读出该文档的加载时机

#### Scenario: 参考文档全量可发现
- GIVEN 技能内的任一参考文档
- WHEN 从加载指引查找它
- THEN 清单中可见，无需打开其他参考文件才知道它存在

### Requirement: 维护的价值主轴
维护协议以知识的真正整理、进一步沉淀与充分优化为核心目的；形式合规是底线检查，不是维护的目标。维护的流程、检查与评价均以此主轴组织。

#### Scenario: 交付检查以知识质量为主
- GIVEN 维护协议的交付检查
- WHEN 检查其项目与措辞
- THEN 知识的整理与沉淀质量是主检项，合规是底线项

#### Scenario: 维护目的锚定文首
- GIVEN 维护协议全文
- WHEN 读其开篇
- THEN 核心目的在文首陈述并贯穿全文，不存在把「文件改合规」表述为维护目标的内容
