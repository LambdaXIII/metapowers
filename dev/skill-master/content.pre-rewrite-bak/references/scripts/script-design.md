# 决定要不要写脚本

「给这个技能配个脚本」不是需求，是症状。先诊断它属于哪一种，三种情形的修法完全不同，误判会把信息缺口当成工具缺口，把手段固化当成能力补齐。

## 三种诊断

**一、信息缺口（最常见，也最便宜）**

- 先查最简单的可能：缺的是不是知识。工具已经存在、入口已经引用了，而使用者没读到——病根在引用处，修法是在引用处写一句带触发条件的提醒，不是再造一个工具。
- 实证：某技能收到「把检查三步工具化」的诉求，实际该技能的入口早已引用了这两个脚本并给了用法示例，提交诉求的 agent 根本没读到。这类诉求按一句话提醒处理，不动正文、不加脚本。

**二、手段固化（设计错误，不要照做）**

- 再看诉求固化的是「要做什么」还是「用什么做」。前者是知识，写进正文；后者是手段，属于启发层。手段固化之后，读者照脚本机械执行，不再现场判断——而每轮要验证的面并不相同，灵活性正是在这里丢掉的。
- 红线管「要做什么」，不管「用什么做」。某技能的红线是「交付前做双重质量检查」，跑哪个脚本是手段；把「跑三步脚本」写成硬性步骤，读者就会跳过「这次该检查什么」这一步思考。
- 技能的职责是启发读者自给自足（遇到重复性工作自己造工具并沉淀），不是把所有工具写进协议。写进协议 = 文档膨胀 + 手段固化，两头受损。

**三、真工具（只有这种才写）**

- 三个信号同时成立才值得写：**跨文件的组合关系**（一次遍历多个文件做关联分析）、**内容不变的机械重复**（每次做都要重复同样的动作序列）、**输出要结构化供下游处理**（JSON 可管道给别的命令）。
- 单项成立通常用现有工具链就够（`grep` + `test -f`），不值得为它维护一个脚本。三项齐全时，脚本替换掉的是力气，不是判断——这是唯一的绿灯。

## 脚本是便利设施

- 脚本优化的是力气，不是能力：把文档里已经写明的动作跑得更快更稳，**不承载读者在文档里读不到的知识**。技能对脚本没有硬性依赖——脚本不可用，技能仍须可用。
- 校验方法：把脚本删掉，零上下文读者还能不能只靠文档完成同一件事（慢一点但能完成）？不能，说明脚本在偷偷承载知识，把那段知识搬回文档。
- 引用写法：凡提到脚本的地方，**手动做法必须写全**，脚本只是附加提示（「……这一步的做法是 X。脚本 Y 可一次完成这一步」）。写成「运行脚本 Y」，脚本不可用时读者就断在半路，且无从知道手动替代是什么。
- 完整命令参考交给 `--help` 或脚本旁的参考文档，入口保持薄：只给最常用场景的一两个用法示例。

## 三层披露

引用脚本的文档在同一处交代三层，少交代一层读者就卡在哪一层：

- **做什么** —— 一句话说清任务与适用场景，读者据此判断值不值得跑。
- **怎么用** —— 最常用场景的用法示例，一两个就够；完整参考交给 `--help`。
- **失败时的表现与处置** —— 报错长什么样、通常意味着什么、下一步做什么。这层最容易被省，也最伤人：读者分不清是自己用错还是脚本出错，两种情形的下一步完全不同。

失败那一层要求脚本在设计阶段就把错误处理做到「失败表现可以被描述」——写不出失败表现的错误处理，文档也就写不出这一层（见[脚本编写手艺](scripting-craft.md)）。

## 与知识的边界

- 内容进脚本还是进文档，看执行时还要不要现场判断：判断依据（标准是什么、这次查哪些、结果怎么解读）是知识，写文档；判定已定、剩下的是机械重复动作（遍历、比对、按固定规则转换），才进脚本。
- 脚本替不了读者回答「这结果意味着什么、下一步怎么决定」。硬塞进去，等于把判断冻结在写脚本那一刻的场景里。
- **划界与改动以功能角色为单位，不以主题词为单位**：同一主题下的内容可能服务完全不同的场景。收到「合并这几个脚本」「简化这段逻辑」的诉求，先做角色分离——枚举与目标同主题但角色不同的东西，逐个独立判断它服务哪个失败场景，只动真正冗余的那个。判据是：只删最精确的那个目标、其他不动，我是否仍认为指令完成？是，那其他就不该动。
- 合并前先问：这个部分被哪个场景验证过？说不清的，不该顺手圈进改动。按主题词圈范围会把几处各自独立的保护机制一起扫掉，故障在之后很久才暴露，且不再能隔离根因。
