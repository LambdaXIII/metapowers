# 技能设计讨论 · 九问

> 这是一份示例问卷：正文按主题分章，问题块嵌在论述之间，章节、子章节与问题交错排布。同一章节可以连续提出多个问题，也可以把问题收进子章节；单选、多选、判断与开放四种形态均有出现，部分选项带 `[x]` 推荐标记。
>
> 全卷九问。问题块上方是粗体题面与必要的论述；答卷只回传选项 id 与自由输入，题干始终以本问卷为准。

## 背景

讨论收束时留下九个待决点，散落在行文里。本问卷把它们逐题立起，每题附上当时的选择依据。这些问题多数是格式与机制层面的裁定，答完即可推进下一步。

**已定事项**（讨论中已形成共识，不占用题目）：

- 答卷为 JSON 纯数据层：只含问题块 ID、选项结果、每题自由输入与 global comment，不回显题干——题目文本的唯一权威是问卷本身。
- 脚本提供**拼装答卷**能力：解析问卷与答卷，输出完整文档，将问题块替换为作答结果。拼装视图按需现算、不落存储，服务人工审读与 agent 的跨会话回读。

> 这九道题决定的不是问卷长什么样，而是问卷怎样被写出来、又怎样被读回去。机制一旦定稳，后面的题库、渲染与拼装才有地基。

## 这份问卷怎么用

问卷本身是一份普通 markdown：论述照常写，需要裁决的地方嵌一个 `qa` 块，一块只对应一个决策点。交互页读的是块，人读的是块外的正文，两者互不替代。

```mermaid
flowchart LR
    A["agent 攒起待决点"] --> B["写成问卷 md"]
    B --> C["show 打开交互页"]
    C --> D["提交生成 answers.NNN.json"]
    D --> E["assemble 拼装回读"]
```

块内是 `key: value` 的扁平结构，选项一行一个；破折号后的文字只给人看，不进答卷。一个最小的问题块可以写成这样：

```text
id: sample-question
type: radio
options:
  - first — 选项正文，破折号后补一句取舍理由。
  - second — 理由写给答题的人，答卷只记录选中项。
```

块外的正文在拼装时原样保留，只有 `qa` 块被替换成作答结果。因此论述可以写得比题目长，也不必担心它被答卷吞掉。

## 全卷导航

九道题按主题分成四段，读法上仍有层次：

- **格式与机制**（Q1–Q3）：问题块怎样获得标识、第一版契约铺多宽、格式设计前要不要先看先例。
- **运行与收卷**（Q4–Q6）：脚本提交后停在哪里、答卷文件怎么命名、问卷被编辑后怎样确认配对。
- **出题纪律**（Q7）：哪些提问技巧值得写进技能正文。
- **契约的边界与回读**（Q8–Q9）：契约还漏了哪些情形，以及拼装结果是否保留块 id。

机制层的答案会约束契约层：ID 由脚本生成，配对校验就必须覆盖重排；提交后常驻，答卷命名就得考虑并发。反过来则不成立，所以答题时不妨从上往下读。

## 格式与机制

这一章处理问卷文件本身：问题块怎样被指认，契约第一版铺到哪里为止，以及在自定格式前是否先看已有的先例。

### 问题块的标识

答卷只记选项 id，不记题干；要把一条回答对回原题，靠的是问题块 id。第一个分歧就在 id 由谁产生。

**Q1 · 答卷条目与问题块的对应：ID 由谁生成？**

```qa
id: id-generation
type: radio
options:
  - auto — 脚本按块序自动生成。问卷作者零负担、无拼写错误；问卷编辑重排后由配对校验（见 Q6）兜底。
  - explicit — agent 在问卷块中显式声明 id。问卷被编辑重排后引用仍稳定；代价是作者多写一个易错字段。
```

### 契约的宽窄

**Q2 · 交互块 schema 第一版的宽窄**

```qa
id: schema-width
type: radio
options:
  - narrow — 第一版只有 radio/checkbox + 每题自由输入。核心痛点（批量裁决与推翻权）已全覆盖；控件按真实需求再加。
  - wide — 第一版即规划日期、评分、文本框等控件。覆盖面广，但渲染面与 JSON 契约立刻变大，未有需求驱动。
```

宽窄之争真正要定的是契约的冻结点，而不是控件的多寡。JSON 答卷只要保留每题自由输入这个逃生口，后续加控件就只是加法；反过来，第一版铺开控件面，每一类都要在渲染、答卷、拼装三处同时落地，成本按三倍计。

这也是为什么下一题先问调研：Formdown 若已有成熟的字段约定，宽窄的边界可以照着它划；若没有，narrow 就是唯一能守住的范围。

### 先例调研

「md 内嵌 fenced 块 → 交互表单」有先例 Formdown（面向 AI 生成表单的格式），schema 细节未核实。

**Q3 · Formdown 先例调研**

```qa
id: formdown-survey
type: radio
options:
  - survey — 花十分钟查其 schema 与渲染约定，回来给借鉴/不借鉴的结论，格式设计前心里有底。
  - self-decide — 不查，直接自定格式。快，但可能重复发明或错失互操作机会。
```

调研结论不必然推翻 Q2 的选择，但它决定 wide 的边界是从真实需求长出来，还是照着别人的字段表抄一遍。

## 运行与收卷

题目与契约定下后，剩下的是脚本在什么时候停、答卷落在哪里，以及事后怎样确认一份答卷仍然对得上这份问卷。

**Q4 · 提交后脚本的退出行为**

参照 plannotator 的形状。

```qa
id: submit-exit
type: radio
options:
  - block — 前台阻塞至提交完成，打印答卷路径后退出。agent 按路径取数，一次往返。
  - serve — 服务常驻，agent 轮询查询新答卷。支持长时间开放的问卷，但多一套查询机制。
```

阻塞与常驻的差别不只在实现量：前者把「一次往返」写进流程，后者把问卷当成一段可以长期开放的服务。

**Q5 · 答卷文件命名**

一份问卷可产出多份答卷。

```qa
id: answer-naming
type: radio
options:
  - seq — `<问卷名>.answers.<NNN>.json` 按序号。目录列表即查询；并发提交时序号分配由脚本处理。
  - time — `<问卷名>.answers.<时间戳>.json`。天然防并发；顺序需按文件名排序得到。
```

序号与时间戳都能防重名，差别在查询方式与并发语义：序号让目录列表本身就是索引，时间戳把顺序交给文件名排序。

**Q6 · 答卷与问卷的配对校验**

JSON 答卷不含题干，靠 ID 与问卷对应。若问卷在展示后、提交前被编辑，按块序生成的 ID 会静默错位，需要绑定机制。

```qa
id: pairing-check
type: radio
options:
  - snapshot — 展示时脚本对问卷做快照，答卷与快照绑定；事后编辑原问卷不影响对应关系。
  - hash — 答卷记录问卷内容哈希，拼装时校验，不一致即报错；答卷文件更轻，但校验失败时旧版本可能已不存在。
  - nameonly — 仅靠同名文件约定，不做校验；最简单，事后编辑会静默错位。
```

Q6 与 Q1 不是同一问题的两个版本：Q1 决定 ID 怎么来，Q6 决定 ID 失效时谁来发现。前者是省事与稳妥的取舍，后者是失败模式的兜底，两者可以独立选择，组合起来才是完整的配对方案。

也可以把它读成对 Q1 的压力测试：若 ID 由脚本生成，Q6 的答案就必须能覆盖重排；若 ID 由 agent 显式声明，Q6 更像一道保险。前者让机制自己兜底，后者把责任留在写问卷的人手里。

## 出题纪律

机制与契约之后，剩下的是写问卷的人该守什么。这一题是多选：下列候选哪些值得写进技能正文？未选的视为一般常识，不占技能篇幅。

**Q7 · 提问技巧候选条目（多选）**

```qa
id: discipline-entries
type: checkbox
options:
  - chain — 依赖链问题不进同一批：答案会改变后续问题的题目本身。
  - [x] compress — 上下文压缩到决策相关：需要 200 行才看得懂的题，说明 agent 还没消化好。
  - [x] assumption — 承重假设显式标注：让用户检验问题成立的前提，而不是只在选项里挑。
  - prose2qa — 讨论文本问卷化：把行文中散落的待决点逐题立起（本问卷即示例）。
```

推荐标记落在 compress 与 assumption 上：这两条都能从真实案例里找到反例，而 chain 与 prose2qa 更接近通用写作常识。

## 契约的边界与回读

最后一段留给契约自身的盲区，以及答卷读回来时的形状。

**Q8 · 契约还漏了哪些边界情形？（开放题）**

开放题没有候选答案，只收自由输入。前七题定下了字段、校验与文件命名，但边界情形往往在真实答卷出现时才暴露：问卷在中途被改名、同一 ID 在两个块里重复出现又被手改回去、答卷里出现了问卷中不存在的选项 id——这些都值得在契约里写清处理方式。

```qa
id: contract-edges
type: radio
```

开放题的回答进入答卷的 `text` 字段，`selected` 为空数组；没有选项可挑，也就不存在推荐标记。

**Q9 · 拼装视图应当保留问题块 ID 作为对照锚点。**

回读形态同样属于契约：拼装结果目前是「选：…… / 补充：……」的引用块，读起来像终稿，但不含块 id。保留 id 会让跨会话回读更容易把每条结果对回原题；不保留则更接近纯人读文档，对照只能靠题干文字。

```qa
id: assemble-anchor
type: yes-no
options:
  - [x] yes — 需要：回读时逐条对回原题，代价是拼装结果多出一层机器标记。
  - no — 不需要：拼装结果保持纯人读形态，对照靠题干文字。
```

九题答完，问卷的机制、契约与写法就都有了落点。若仍有未列入的顾虑，写在每题的自由输入或卷末总评里即可。
