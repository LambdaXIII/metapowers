# 提示词/指令集推演
> 场景文档 — 配合推演通用论述（`../rehearsal-guide.md`）参考使用，补充提示词/指令载体的特化内容。

将推演方法应用于提示词、系统指令、任务指令、提示词模板等"按文字指令执行"的载体。适用于：
- 给 AI 模型的系统提示词或任务指令
- 给人类执行者的操作指令或规范文档

## 本载体的核心差异：双维度推演

提示词推演横跨两个维度，且**必须同时推演**：

- **内容表达层**：措辞是否准确、表述是否清晰、是否会引起过拟合/欠理解/误解
- **逻辑执行层**：按指令链路走下去，模型/执行者会得到什么结果

大多数载体只关注其中一个维度，提示词是少有两个维度同等重要的载体。通用论述「推演者定位」中的两层观察（内容表达层 + 逻辑执行层）在提示词载体是最严格的检验场——推演时每走一步都要同时问："这句话写得好吗？"和"按这句话走会怎样？"

### 推演者的双重定位

「双重」指推演者需要同时规避两重身份：作者（你知道意图）与模型（你在模拟它）。推演提示词时需要保持一个清醒的"第三者"位置——**站在中间评估这次通信的观察者**（与上节「双维度」的区别：双维度是检查的对象，双重定位是推演者自己的站位）。

- 不要变成作者：你已划掉设计意图（P2 身份转换）——你看到的只是文本本身
- 不要变成模型：你在观察模型的"理解过程"，不是在真的理解并执行
- 保持评估者位置：每走一步自问"我现在是评估这条指令的人，还是在执行这条指令的人"
- 尽量客观：推演者的理解和判断能力直接影响推演质量——理解能力不足会导致误判

## 推演前的准备（P1 的要点）

（先完成本节准备，再进行 P2 身份转换——按通用论述的 P1 → P2 顺序执行）

进入推演流程前，以作者身份写下以下信息（P1S2 读者画像 + 期望效果、P1S3 作者意图在本载体的具体化）。**不写下来，推演结束后就没有对比基线**：

1. **这条提示词/指令是给谁的？** 模型类型（大模型/小模型/代码模型）？执行语境（独立会话/工具链一环）？已知约束（上下文长度、工具集、输出格式要求）？
2. **期望的执行效果是什么？** 正常路径下，模型读完这条指令后应该做什么？输出什么？**不**做什么？
3. **你做的隐含假设是什么？** 你假设模型已经理解了哪些概念？你假设哪些信息会从其他渠道（系统提示词、工具定义、上下文）进入？

P2 身份转换时，除通用论述要求划掉的作者侧要素外，本载体特别需要显式划掉：

- 我不理解作者的「本意」——我只看到文字
- 我不会「应该能猜到」——没写的约束 = 不存在
- 我没有这段提示词之外的任何背景
- 我不会自动纠正措辞矛盾——我按字面执行

推演结束的复现对照（P5S1）以这份推演前写下的记录为对照基准——不是和「你觉得应该怎么样」对比，是和**你当时写下的期望**对比。偏离期望时两个方向都可能是问题：

- 推演路径暴露了指令的模糊或遗漏 → 指令需要改
- 推演结果更优，但偏离了你原来的期望 → 你的设计意图本身可能有问题

不要偷偷修改写下的期望来让推演结果「合格」——推演的价值恰恰在于发现你没想到的路径。

## 读者定位（P2 身份设定的要点）

本文以 AI 模型为典型画像：AI 模型（LLM 或其它指令执行系统）或按字面执行的指令执行者。已知系统提示词和工具定义（如有），无人类常识——只按指令文字执行，没有设计者的隐含假设。

若读者是人类执行者（操作指令/规范文档场景），画像相应调整——人类有常识与推断能力，歧义容忍度更高；此时按「模拟一个按字面执行的人」设定身份，并留意人类会用常识填补缺口的倾向。

初始状态：
- 只有被注入的提示词和工具定义
- 没有设计意图、没有上下文暗示
- 按字面理解约束——"不要做 X"只看是否说了，不猜作者"应该指的是什么"

P2 身份设定的示例（精确到可操作）：

> 我是一个被注入以下系统提示词的 LLM。我只有被注入的提示词和工具定义，没有其他上下文。我不猜测作者的意图，不填补文档中的空白。我按字面理解每一条指令。

## 模拟阅读时的特有信号（P3 补充）

P3 模拟阅读中，提示词载体的信号分两列记录：

**内容表达信号（措辞层）：**

| 信号 | 含义 |
|------|------|
| "这句有歧义" | 可能被理解为多种不同的约束 |
| "这个词太绝对" | 过拟合风险——"永远""必须所有" |
| "这个概念没定义" | 模型不知道具体指什么 |
| "这里跳得太快" | 缺少中间推理步骤，模型跳跃式执行 |
| "这句像作者的自言自语" | 元语境渗漏（身份边界错位）——混入了调试注释、内部编号、"本文不出现 X"式写作约束、作者的声音 |

**逻辑执行信号（执行层）：**

| 信号 | 含义 |
|------|------|
| "这条约束和上一条冲突" | 模型选哪条？会不会都违反？ |
| "这个步骤缺失" | 按指令走到了这一步，然后该做什么？ |
| "这个判断条件不完整" | 有些情况没有被条件覆盖 |
| "这个后果描述不够强" | 模型可能忽略约束，因为没有感受到后果 |

## 边界与异常场景（P4 补充）

P4 推演过程回顾中，提示词载体值得主动尝试的异常场景：

| 场景 | 检查目标 |
|------|---------|
| 缺失前提 | 缺少一条关键上下文，模型是否就偏离了？ |
| 误导性措辞 | 某句话被模型理解为相反的意思——措辞是否足够精确？ |
| 冲突指令 | 两条约束在某个输入下同时触发且互斥——优先级的说明是否清晰？ |
| 过拟合陷阱 | 例子/约束描述了一个具体模式，模型是否误以为只能用这个模式？ |
| 欠覆盖 | 一种常见违规模式没有被任何约束覆盖 |
| 注入攻击 | 用户输入中包含了类似系统指令的措辞——是否防注入？ |
| 约束组合爆炸 | 大量约束同时触发、上下文超长——优先级和主次是否仍然清晰？ |

## 委派推演（如何做）

自我模拟有一个上限：你作为推演者同时也是作者——你们的推理结构相似。你「划掉」掉的假设，你的推理结构会自动补回来。这就是提示词推演中最常见的失败「滑入模型角色」——你读着读着就真的按你（作者）的意图去理解了。

**将阅读委派给子代理**可以突破这个上限。子代理和你是不同的推理实例——它没有你的上下文和隐含假设。你给它什么，它就只能从什么出发。

委派模式下推演者的站位会变化：P3 的阅读由子代理承担（「不要变成模型」由子代理的身份设定保证），你的角色变为**分析记录者**——把子代理的逐段记录当作 P3 信号来源，信号表（见上节）同样用于分析记录。

通用论述「执行策略」中的**委派并行推演**是策略层面的推荐；本节是采纳该策略时的具体操作方法——单推演者把阅读外包给子代理（多场景批量执行见 `../supplementary/batch-execution.md`）。

### 子代理提示词原则

给子代理的提示词必须遵循以下约束：

1. **不透露推演目的**：不要说「帮我检查这条指令有没有问题」「帮我找盲区」——这会让子代理进入评审模式，而不是接收模式
2. **不透露侧重和倾向**：不要说「重点看约束部分」「注意检查措辞精确性」——这等于提前告诉它哪里有坑
3. **设定阅读身份而非评估身份**：告诉它「你是 X，你要读 Y」，不是「你是评估者，你要评估 Y」
4. **只读不执行**：明确指示「只逐段阅读并记录你的理解，不要实际执行任何操作」
5. **逐段记录而非总结性评价**：要求子代理「每读完一段就写下：你理解这段在说什么？你认为接下来应该做什么？」——不要让它给整体评价

### 委派提示词模板

以下是给子代理的提示词模板。使用时只替换 `[ ]` 中的内容：

```
你现在的身份是：[ 读者描述，如"一个被注入了系统提示词的 LLM" ]

你的任务：逐段阅读以下提示词/指令，每读完一段（一个自然段或一个逻辑单元）就写下：

1. 这段在说什么？（你的理解）
2. 读完这段后，你认为你应该做什么？（你的行为倾向）
3. 这段和前文有什么关联或矛盾？

不要给整体评价。不要跳到结论。不要实际执行任何操作。
只阅读、理解、记录。

以下是你要阅读的内容：

---
[ 待推演的提示词/指令全文 ]
---
```

子代理的输出就是一份逐段阅读记录。你（推演者）的工作是分析这份记录——对比「推演前写下的期望」，找出偏离和盲区。

### 为什么不总是委派

通用论述给出的委派适用条件仍然有效：材料比较简单且推演目的特别明确时才考虑委派——委派有设置子代理与分析的额外成本。此外，子代理的推理结构和你仍然相似（同模型族）。对于非同构读者（7B 小模型、特定领域专家），委派推演的准确性同样受限。但对同构读者场景（你推演自己的系统提示词、你的 prompt 将被同级别模型消费），委派推演优于自我模拟——它至少隔离了你的隐含假设。

## 评估整理（P5 的要点）

**严重程度格式：** 阻塞/缺陷/建议。三级定义：

- **阻塞**：模型产生错误/不可控输出（如约束冲突、措辞歧义）
- **缺陷**：模型输出质量受影响（如边界未覆盖）
- **建议**：措辞可进一步精确

发现归类（P5S2）时，为每条发现标注缺陷类型（参见 [缺陷分类法](../supplementary/defect-taxonomy.md)）。

**评估维度提示（在通用论述评估维度表提示词/指令行 5 项基础上扩展为 7 项；额外提示，非硬性指标）：**

| 评估维度 | 含义 |
|------|------|
| 因果方向清晰度 | 约束的"因此""否则"链路是否明确——模型知道为什么不能这样做 |
| 违规模式覆盖 | 常见的违规行为是否都被约束覆盖了 |
| 自检可执行性 | 检查和判决是否可执行——模型能否自行判断是否违规 |
| 后果说服力 | 违规的后果描述是否有力量——"会出大问题"比"不建议"有效 |
| 边界覆盖 | 边界输入下是否有未定义的约束行为 |
| 过拟合抵抗力 | 例子和约束是否足够通用——不会让模型误解为"只有一个模式" |
| 措辞精确性 | 指令措辞是否精确——不会产生误解或多解释 |

**复现对照注意（P5S1）：** 提示词场景的特殊性——推演结果偏离期望时，两个方向都可能是问题：指令需要改，或设计意图本身有问题。内容表达层和逻辑执行层都要对照到。

**错误模式搜索候选（P5S5）：** 过拟合陷阱、约束冲突的定义见上节边界表——当它们在推演中反复出现时即为错误模式（同一根因多次触发）。另需留意的候选：

- **后果说服力不足** — 「不建议」比「会导致 X 问题」弱得多，模型可能忽略

## 与逻辑链路推演的关系

提示词推演和逻辑链路推演（[logic-chain-rehearsal.md](logic-chain-rehearsal.md)）都涉及"按链路跟踪执行结果"。提示词推演中的逻辑执行层面本质上就是一次逻辑链路推演，但叠加在模糊语义之上。关键区别：

- 逻辑链路推演模拟的是确定性的**执行引擎**（计算机/解释器），行为可精确预测
- 提示词推演模拟的是**AI 模型**，行为不确定、受措辞影响、存在过拟合/欠理解

推演提示词时如果发现执行链路上的问题，可以引用 [logic-chain-rehearsal.md](logic-chain-rehearsal.md) 的方法分别推演"被理解的逻辑本身"是否有漏洞。两个独立的推演，各自有各自的载体。

## 常见陷阱

- **滑入模型角色**：读着读着真的去执行了。每步必问自己"我现在是评估者"
- **忽略内容层**：只跟踪了逻辑没有评估措辞。一个措辞不当的完美逻辑在模型手中就是随机逻辑
- **忽略逻辑层**：只看了措辞没跟踪执行。一个表达精美但逻辑模糊的指令在模型手中也会执行，但不受控
- **用作者知识补洞**：某步骤缺失但作者心想"模型应该理解这里"。这就是推演失效——模型没有你的暗示
- **混淆读者**：把给开发者看的文档当成给模型看的指令来推演，或反之。推演前确认——这份材料的读者是 AI 模型还是人类开发者？开发者内部的组织代号和速记（如层级编号、项目缩写）对 AI 模型而言不传达任何语义，模型只理解自然语言描述；对开发者在讨论中使用这些代号效率更高。用错了读者身份，等于用错误的语言测试理解
- **跳过推演前准备直接推演**：没写下设计意图就开始推演，等于没有对比基线。推演结束后你说「这里有问题」，但和什么比？和你脑子里模糊的「应该」比？写出具体的期望，每一条期望对照推演结果——没对照到的地方就是盲区
