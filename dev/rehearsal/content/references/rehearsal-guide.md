# Rehearsal（推演）— 通用论述

## 推演是什么

**Rehearsal（推演）= 暂停作者身份，完整走一遍另一个视角的「首次接触 → 理解 → 决策」链路。**

它和载体无关——可以推演文档、代码、UI 流程、API 设计、教学大纲、定价页、演讲脚本、审查清单。
它和客体也无关——客体可以是 AI 模型、真实用户、读者、学生、顾客、新人同事。

## 为什么推演管用

作者有一个致命盲区：**你知道"应该得到什么结论"，所以你看不到"得不到的人会在哪里卡住"。**

Rehearsal 就是强制切除"设计者知识"。你假装不知道——然后走一遍。哪里卡住了，哪里就是设计有问题。

## 局限性

Rehearsal 是**同体模拟**——你在模拟一个和你推理结构相似的客体。如果你的推理结构和客体差异大（比如你在模拟一个 7B 小模型，或一个完全不了解你领域的用户），准确性会下降。

对低同构性的客体，rehearsal 仍然有价值（暴露明显的结构问题），但不应被视为精确的可用性测试。

## 与其它方法的区别

- **Rehearsal ≠ 测试**：测试需要真实客体（真实用户、真实模型）。Rehearsal 是模拟，零成本。
- **Rehearsal ≠ 自查**：自查是"我再看一遍有没有错别字"。Rehearsal 是"我假装不是作者再走一遍"。
- **Rehearsal ≠ 同行评审**：同行评审有另一个真人参与。Rehearsal 是你在自己的脑子里跑另一个人的模拟。

## 核心方法

### 三个不变元素

| 元素 | 含义 | 自问 |
|------|------|------|
| **客体** | 你要模拟谁的视角 | 他知道什么？不知道什么？期望什么？怕什么？ |
| **载体** | 被推演的产物 | 它是什么形式？客体按什么顺序消费它？ |
| **链路** | 从接触到完成目标的完整路径 | 第一步是什么？哪里可能停？哪里可能跳？哪里可能误解？ |

### 四步流程

核心流程包含四步（1-4），第 0 步是推演前的准备工作——在进入核心流程前先明确设计意图。
**0. 作者视角**

先以作者身份回答三个问题。写下答案——不是想一想，是写下来：

1. **这份材料的目标读者是谁？** 他有什么背景知识？他期望从这份材料中得到什么？
2. **阅读完成后，他应该知道什么、能做什么、感觉到什么？** 这是你的设计意图——推演打分时将用它对照实际接收效果。
3. **你的前置假设是什么？** 你假定了读者已经知道哪些事、手边有哪些工具、处于什么状态？

跳过这一步的典型后果是 Context Leak——你写下的参照点只有你自己知道，读者看到的是悬空指针。这种缺陷的识别和修复见[缺陷分类法](supplementary/defect-taxonomy.md)中的 Context Leak 条目。

这三个答案构成推演的**设计意图基线**。推演结束后，回到这些答案，逐条确认客体的实际接收是否与意图一致。中间偏离意图的不一定是问题（也许是更好的路径），但偏离意图而你没想到的——那就是盲区。

**1. 清空**

扔掉所有作者记忆。不是「假装不知道」——是显式地写下你**不再拥有**的东西：

- 作者意图：「这份材料想达到的目的是……」——划掉。客体不知道目的。
- 隐含上下文：「读者应该知道 X 是 Y 的别名」——划掉。没写 = 不存在。
- 设计过程中的取舍：「这个方案是因为 Z 约束才选的」——划掉。客体只看到最终结果。

然后显式设定你的阅读身份：

- 我是 [ 客体描述 ]，我此刻的状态是 [ 初始状态 ]
- 我手里有 [ 材料名称 ]，除此之外没有任何其他参考
- 我的目标是 [ 读完后要做什么 / 决定什么 ]

身份设定越精确，推演越有效。模糊的身份（「我是一个用户」）产生的信号也模糊（「这里有点 confusing」）。精确的身份（「我是一个刚入职两周的开发者，第一次读部署文档」）产生可操作的信号（「读到第三步时我不知道 `deploy-key` 在哪里找——文档没有说明生成位置」）。

**2. 逐帧跟**

按客体消费的顺序逐段走，记录每步的心理反应。不要跳到结论——瓶颈往往在中间某一步，不是最后。

记录格式（内心独白）：

- "这里停顿了" → 信息密度过高或措辞模糊
- "这里被吓到了" → 警告/限制过多，客体可能放弃
- "这里跳过了" → 结构上没有抓住注意力
- "这里误解了" → 措辞有歧义
- "这里不知道该做什么" → 缺少明确的下一步

**3. 边界刨**

故意走非正常路径。至少覆盖三类常见模式：

- **信息缺失**：客体缺少某条前置知识，或跳过了某个章节
- **错误输入**：客体做了错误操作，或误解了某条指令
- **跨模块跳转**：客体从中间进入，或从另一条路绕过来
- **责任边界错位**：边界条件超出被推演载体的责任范围。上游阶段已验证的条件不属于本载体的推演漏洞——那是上游的问题。推演前先明确"这个载体负责什么、不负责什么"

**边界范围约束**：每个边界条件必须在载体的**自身责任范围**内。不测试上游阶段或依赖已经保证的条件。有效的边界是载体自身可以预料并处理的合理变化（如极简/极繁输入、大量分支、不确定步骤、并行链路）。超出责任范围的边界暴露的是上游问题，不是载体的问题。

**4. 打分**

分维度给判断，不笼统说"还行"。每个维度用 ★ 打分（1-5），并指出具体缺口。

维度根据载体类型选择：

| 载体 | 推荐维度 |
|------|---------|
| 提示词/指令 | 因果方向清晰度、违规模式覆盖、自检可执行性、后果说服力、边界覆盖 |
| 文档/教程 | 入口明确性、术语一致性、步骤可跟踪性、缺失场景覆盖 |
| 交互流程（UI/CLI） | 首次可执行性、困惑点密度、放弃率预估、错误恢复路径 |
| API 设计 | 命名一致性、默认值合理性、错误信息可操作性、缺失 endpoint 覆盖 |
| 逻辑链路 | 控制流正确性、边界条件覆盖、状态一致性、资源生命周期、异常安全 |


## 推演者定位

推演的核心是站在评估者位置，模拟客体视角——不是变成客体。推演者需要同时维持两层观察：**内容表达层**（措辞是否准确、语义是否清晰）和**逻辑执行层**（按规则走下去得到什么结果）。每步自问"我现在是评估者还是客体"，不要滑入客体角色放弃对载体的判断。

这条原则在所有场景文档中成立，在提示词/指令集推演（`scenarios/prompt-instruction-rehearsal.md`）中尤为关键——读着读着就真的去执行了，是推演中最常见的滑落。保持评估者定位的同时尽量客观，是推演质量的前提。

## 执行策略

### 嵌入优于收网

推演不必积攒到最终一次性做。每完成一段时做一次短推演（只测刚完成的部分），比最后做一次全量推演更有效——缺陷发现得越早，修复成本越低。但阶段性推演只解决"有没有明显问题"，取代不了最终的全景推演（跨模块交互问题往往只在全景推演中暴露）。

## 示例：推演一个指令集章节

以下是一次真实的推演记录（内容已脱敏）。

```
客体：第一次接触工作流程的执行者
载体：操作规范文档中的「文档先行原则」章节
```

### 逐帧跟（节选）

读到 `[文档] → [代码]` 箭头图 → 执行者停顿了一拍。三个短句都指向同一件事。规则存入高优先级槽位。

读到"唯一合法动因" → 执行者建立了清晰的门控规则。如果修改代码的理由不是"文档说了不同的话"，就是违规。

读到三个典型案例 → 执行者的内心独白匹配到了自己以前的模式。常见的"顺便更新""统一补文档"被标记为违规。

读到"沉默的技术债务" + "主动误导下一次决策" → 威胁感知激活。不只是"过期"，是**主动伤害**。

读到自检问题 → 执行者获得一个可执行的门控：单一问题、二元答案。

### 边界刨

**场景：纯重构（行为不变）**
执行者决定拆模块 → 自检：「文档描述了我的目标状态吗？」→ 目标状态和现有文档一致 → "是" → 自检通过。合理。

**场景：文档不存在**
执行者要加功能但没有对应文档 → 自检失败 → 但不知道该创建在哪个目录、叫什么名字 → **问题发现**：缺少"找不到对应文档时怎么办"的指引。

**场景：文档与主 README 矛盾**
新原则说"文档是契约"，README 第 74 行说"以代码为准" → 执行者困惑 → **问题发现**：README 需要同步修复。

### 打分

| 维度 | 评分 | 说明 |
|------|------|------|
| 因果方向清晰度 | ★★★★★ | 箭头图 + 永不反转 + 唯一合法动因，三重锁定 |
| 违规模式覆盖 | ★★★★☆ | 三个典型案例，但缺少"不知道该改哪个文档" |
| 自检可执行性 | ★★★★★ | 单一问题二元答案，不留模糊空间 |
| 后果说服力 | ★★★★★ | 沉默技术债务 + 主动误导，击中要害 |
| 边界覆盖 | ★★★☆☆ | 主要缺口已修补（README 同步 + 缺失文档指引） |

## 维护者须知

### 目录组织

`references/` 下的两个子目录按触发机制分离，**不是按主题或序号**：

- `scenarios/` — 场景文档。按**载体类型**匹配加载——路由表根据推演对象的性质（文档？API？提示词？）选择对应的场景文档。
- `supplementary/` — 补充参考。按**情境**加载——推演场景 ≥ 5 个时加载 batch-execution，发现缺陷需要归类时加载 defect-taxonomy。不受载体类型驱动。

新增文件时据此判断归属：如果新文件是按载体匹配的 → `scenarios/`；如果是跨载体的情境工具 → `supplementary/`。不要合并这两个目录——触发机制不同，合并会造成路由混乱。

### 开发速记 vs 技能呈现

在开发讨论中使用「L0 / L1 / L2」作为内部速记是方便的——指代明确、沟通高效。但**这些代号不得出现在技能内容（`content/`）中**。

理由：技能的运行时读者是 agent。agent 读到 `L0`、`L1`、`L2` 时不理解这些代号指什么——它们不传达语义，只会造成困惑。技能内容中始终使用自然语言：「必读入口」「场景文档」「补充参考」。

本文档中出现的任何 L0/L1/L2 代号均位于开发侧文件（SKILL-DESIGN、CHANGELOG），不出现在 `content/` 目录下的任何文件中。如果你在 `content/` 中看到了这些代号——那是 bug，修复它。
