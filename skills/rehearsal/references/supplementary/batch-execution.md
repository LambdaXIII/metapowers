# 批量并行推演执行

> 按需参考 — 被引用时加载。假设已读通用论述（`../rehearsal-guide.md`）与对应场景文档，本文只补充批量委派的操作方法，不重复已有内容。

通用论述「执行策略推荐」的**委派并行推演**在推演场景较多（≥ 5 个）时采取批量形式：每个场景的 **P3 模拟阅读委派给一个独立子代理**，推演者自己保留 P1/P2/P4/P5。

## 为什么是委派而不是串行自推演

多场景推演的对象通常是同一份材料被读 N 次。串行自推演做不到 N 次真正的首次接触——读到第几个场景时，入口文档你已经烂熟，P2 划掉的假设会被熟悉感自动补回来，后面的场景全是污染样本。每个场景交给一个没读过任何前文的子代理，才拿得到 N 份互相独立、也不受作者上下文污染的第一次阅读；这些记录是 P3 信号来源，其客观性等同于提示词场景文档「委派推演」所述的推理实例隔离。多个独立场景之间无依赖，并行调度只是顺带的效率收益。

场景 ≤ 4 个时无需批量机制，单推演者委派按 [提示词/指令集推演](../scenarios/prompt-instruction-rehearsal.md) 的「委派推演」执行。

## 委托边界

**子代理只做一件事：以指定身份阅读指定材料，逐段记录理解。** 它不知道、也不需要知道这是推演。

下发给子代理的内容，仅限四项：

1. **身份设定**——场景的角色（P2 在本场景的具体化），写成第一人称身份句
2. **阅读起点与任务目标**——入口文件 + 这个角色想完成什么（如"我刚接手这套方法论的维护，产出上线后行为异常，我想知道问题出在哪一步"）
3. **材料**——入口文件路径；路径上的其余文件由它按入口文档的指引自行加载
4. **输出格式**——逐段记录：这段在说什么 / 我接下来该做什么 / 与读到的前文有何关联或矛盾；读到终点后补一段整体复述（这份材料讲了什么、我能做什么、还缺什么）。记录选择点：在哪一步依据什么选择了哪条路

**红线：除此之外的任何信息都不下发。** 推演方法本身、评估维度、验证点、严重程度定义、预期路径、边界场景的测试意图——透露其中任何一条，子代理就从接收模式滑进评审模式，隔离失效，这份记录就不值钱了。委托提示词的五条约束见提示词场景文档「子代理提示词原则」，批量场景同样适用。

**只给入口、不给路线，是有意设计**：子代理在入口决策树上选错分支、该跳转却没跳转，本身就是高价值发现（导航缺陷）；提前告知路径就永远测不到这些。

## 调度

- 场景相互独立（场景文档的角色矩阵设计保证了这一点，知识库载体见 [多场景知识库验证推演](../scenarios/knowledge-base-rehearsal.md)），并发上限按运行环境实际并行度分批，批次间无需等待。
- 单个子代理失败或超时 → 重试一次；仍失败 → 该场景降级为推演者自推演（接受其污染度，在报告中注明），或标记未完成如实记录。
- 边界尝试（P4）可以物化为附加的阅读委托：同一个角色，换起点（"直接从参考文件 B 开始读"）或换输入（给了错误信息）。委托语句里只出现新设定，不出现"这是边界测试"。
- 修复后的回归轮次（知识库场景文档「多轮迭代修复验证」，属材料所有者的动作）场景数同样达到门槛时，按本方法批量执行。

## 汇总

汇总 = 先逐场景完成 P5，再做跨场景归纳。

**逐场景**：每个子代理的阅读记录是该场景 P3 的信号来源，照常走 P5——复现对照用 P1S3 的意图清单和本场景验证点作基准（验证点在这里上场：主侧逐项判断，而不是下发给子代理判断）。子代理不会给出评估结论，评估是拿记录对照意图之后推演者的工作。

**跨场景归纳**：

- 同一缺陷在不同场景的报告中以不同措辞出现——按根因归为缺陷类别（[缺陷分类法](defect-taxonomy.md)），归纳而非罗列
- 出现频率只决定呈现顺序，修复优先级仍按 P5S4 的严重程度排——阻塞级缺陷哪怕只出现一次也排最前
- 各场景的实际路径与设计路径的偏离、子代理记录之间的矛盾，单列为观察项如实呈现，不强行统一——矛盾本身往往是结构性缺陷的信号
- 覆盖检查按 P5S4：空维度必须回答"确实没问题还是没检查"，必要时补委托
- 呈现规模随发现数量走：量少（如 ≤ 10）直接列缺陷类别，不必做分档表格——格式服务于阅读者，不是仪式

需要跨版本量化追踪时，★ 打分在主侧汇总时产出（用途见通用论述 P5S3），不由子代理打分。
