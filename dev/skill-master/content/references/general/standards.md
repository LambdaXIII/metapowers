# 组织一个技能的结构

内容写完之后要落到文件里：进哪个目录、叫什么名字、读者从入口怎么走到它。这一册管这件事——按什么取舍（加载成本与到达率），以及交付前怎么核对。

两个时机，用法不同：正在摆放文件、决定内容放哪时，从「目录结构」读起逐条比照；交付前核对合规、或核对一个已有技能的结构时，跳到「校验」交给机器跑一遍，再回来看失败项。

## 两套约束

- 结构上的约束来自两个出处，混在一起会让人把环境规定当成通用标准，或反过来。分法：
  - **开放标准**（地板）——不满足就不是合法技能包。字段约束、渐进式披露、引用规范都出自这里。
  - **运行环境追加**——目标环境在标准之上加的要求。例如本仓库要求 `content/` 只含白名单条目、frontmatter 必带 `metadata` 的四个子字段、自定义许可证要附 `LICENSE` 原文。这类要求不出现在标准里，以环境的规则文件为权威。
- 判断一条约束值不值得为它改结构，先看它属于哪侧：地板侧没有讨论空间；环境侧按环境规则执行，且**换环境要重新确认**——方法是读目标环境的规则文件，找技能规范那一节。
- 本册转述标准约束（表内标「标准」），只转述与结构直接相关的环境约束（标「环境」）。分支策略、发布流程这类环境纪律由环境规则提供，不进本册。
- 目录树从技能根开始画（如 `my-skill/`），不含仓库或磁盘上的上层路径——上层路径是放置细节，不属于技能身份，技能每搬一次家就得改一次树。

## 目录结构

- 一个技能是一个目录，最小合法形态只有一个 `SKILL.md`：加载器按目录发现技能，没有目录就没有技能。

| 目录 / 文件 | 装什么 | 装载约定 | 来源 |
|---|---|---|---|
| `SKILL.md` | 元数据 + 指令 | 必须；命中后全量加载 | 标准 |
| `references/` | 按需阅读的文档 | 每份聚焦单一主题、尽量小——文件越小，按需读一次的代价越低 | 标准推荐 |
| `scripts/` | 可执行代码 | 自包含或显式写出依赖；报错信息要有用；边界情形优雅处理 | 标准推荐 |
| `assets/` | 静态资源：模板、图片、查表数据 | 供查阅，不是主阅读路径 | 标准推荐（本环境白名单不含） |
| `templates/` | 提示词或文档模板 | 按需读取 | 环境 |
| `examples/` | 参考示例 | 每个文件以摘要头开始 | 环境 |
| `LICENSE` | 许可证原文 | 仅当采用自定义或非公开引用的许可证时 | 环境（条件性） |

- 标准允许技能目录里出现任意其他文件与目录，上面三个推荐目录只是约定。真正的约束不是目录名单，是**可达性**：一个文件只有在某处有指针指向它时才会被读到。用了非约定目录名，等于放弃「读者会习惯性地往这里找」这份预期，指针一旦漏写，那里的内容对读者就不存在。
- **放静态资源之前先查目标环境允许哪些目录**。标准推荐 `assets/`，但本环境（metapowers）的 `content/` 白名单是闭集——只含 `SKILL.md`、`references/`、`templates/`、`examples/`、`scripts/`（加条件性的 `LICENSE`），模板进 `templates/`、示例进 `examples/`，建 `assets/` 会超出白名单。换环境按同一问法重判：这个环境允许哪些目录，静态资源在其中对应哪一个。
- 放哪个目录与按什么方法写是两回事。模板、工作流、脚本各有各的写法（见 `documents/` 与 `scripts/` 各册），不因为落在哪个目录而改变——同一份模板进 `templates/` 还是 `examples/`，写法都一样。按打包位置去翻编写方法是常见的错路。

## frontmatter

`SKILL.md` = YAML frontmatter + Markdown 正文。标准只约束 frontmatter；正文写什么、怎么排版不设限（只给建议：分步指令、输入输出示例、常见边界情形）。

| 字段 | 必须 | 约束 | 来源 |
|---|---|---|---|
| `name` | 是 | 1–64 字符；仅小写字母、数字、连字符；不得以连字符开头或结尾；不得含连续连字符；须等于父目录名 | 标准 |
| `description` | 是 | 1–1024 字符，非空；说明技能做什么与何时用；含帮助识别任务的具体关键词 | 标准 |
| `license` | 否 | 许可证名，或对包内许可证文件的引用 | 标准 |
| `compatibility` | 否 | 1–500 字符；环境需求（目标产品、系统包、网络访问等）；多数技能不需要 | 标准 |
| `metadata` | 标准可选，本环境必须 | 字符串到字符串的键值映射，容纳标准未定义的附加属性 | 标准 + 环境 |
| `allowed-tools` | 否 | 空格分隔的预批准工具列表；标注为实验性，各实现支持度不一 | 标准 |

- `name` 是双重身份：加载器标识 + 用户称呼。改名要同时动目录、`name` 字段、正文称呼与其他技能对它的提及，涟漪比任何一次正文编辑都大——命名要在写 `description` 之前定稳，方法见[让技能被正确命中](disclosure.md)。
- `description` 的字段级约束（长度、必须同时说明做什么与何时用）到此为止；措辞怎么命中匹配面是另一套方法论，见[写入口文件](../documents/skill-md-writing.md)。
- `metadata` 在标准里是附加属性位：识别只看 `name` 与 `description`，加载器不读 `metadata` 做匹配，把版本、作者、更新日期放这里是为了人与工具查阅。本环境把它定为必填，四个子字段（`version`、`last_updated`、`author`、`license`）的值在 YAML 里一律加双引号——`version: 1.0.0` 会被解析成浮点数、`last_updated: 2026-06-27` 会被解析成日期对象，加引号强制为字符串，保证读取时类型一致。

## 按加载成本分层

| 层 | 内容 | 成本形态 |
|---|---|---|
| 元数据 | 全部已发现技能的 `name` + `description` | 约 100 词元；常驻，每次会话全程付费 |
| 指令 | 被命中的技能的 `SKILL.md` 正文 | 建议 5000 词元以内；命中后一次性全量加载 |
| 资源 | `references/`、`scripts/`、`templates/`、`examples/` 中被链接的文件 | 按需付费，不读不花 |

- 三层成本形态不同，组织方向因此确定：匹配信号留在元数据层，决策依据放指令层，长论述后置到资源层。把长论述写进 `SKILL.md`，等于让它在每次命中时都被全额支付，无论这次任务用不用得上。
- **预算按词元算，不按行数算。** 标准给的「正文不超过 500 行」是按英文散文的字符密度估的代理指标；中文每单位信息的词元开销高于英文，同样 500 行中文正文的词元数通常是英文的两倍以上。写中文技能把 5000 词元换算成字数（约两三千汉字）当预算，别拿行数当安全线。拿不准就在你的环境里实测一次正文的词元数，这个数字比任何经验值都可靠。

### SKILL.md 极简

- 三层里只有指令层是每次命中全额支付的，所以 `SKILL.md` 只承担三件事：**被加载器命中**（`description` 提供语义匹配面）、**触发决策**（加载后判断这次该不该启动、走哪条路）、**路由引导**（指向真正的主内容）。
- 完整的方法论述、执行流程细节、检查清单展开都不进 `SKILL.md`，进 `references/` 下的主文档按需加载。判据就是那句：**这一句每次命中都要用到吗**——不是，就后置。
- 极简不是越短越好。太薄会退化成一张纯目录：读者在路由处看不出该选哪条，只能全扫一遍。留多长的判据是——读者读完路由，能否不看支撑文件就判断「我这次该进哪一册」。
- 主文档自己要独立站住，不假设读者先读过 `SKILL.md` 的其他段落或别的支撑文件。特化文档是补充不是替代：它只承担某一类情形的展开，主干里该有的判断依据不能只存在于特化文档里——那样按主干走的读者会缺一块。
- 入口文件的具体写法（前提节怎么产生、路由按什么轴组织、索引与路由怎么合一、不触发条件放哪里）见[写入口文件](../documents/skill-md-writing.md)。

### references 内部是分层的

- 资源层不是一堆平铺的文件，它有自己的层级：顶层一册**主文档**（`SKILL.md` 直接路由到它，承载这个方法的主干），其余按一个切分轴分成组。
- 分组有两种实现，二者等价，按组的体量选：
  - **子目录** —— 组内文件多且分组稳定时用，如 `references/scenarios/`、`references/structure/`。
  - **文件名前缀** —— 每组只有两三份、平铺就能看清全貌时用，如 `design-*.md`、`spec-*.md`。
- **目录名与文件名共同承担路由信息**，这是分层最大的收益：读者看到 `references/structure/pattern-iceberg.md`，路径本身已经说了「结构类 / 模式 / 冰山模型」；看到 `scenarios/api-design-rehearsal.md`，就知道「场景类 / API 设计」。路由表因此不必为每个文件重述它属于哪一类，而平铺的文件名做不到这一点，只能靠文件名里的主题词去猜。
- 切分轴按**触发机制**选，不按主题词选：按载体类型匹配的文档与按情境加载的文档物理分开（如一个技能的 `scenarios/` 与 `supplementary/`）。同一主题词下的内容常常在不同时机被需要，混进一个目录会让读者在错误的时机读到它、在需要的时机找不到它。
- 深度就一层：`SKILL.md` 一次跳转到达支撑文件。子目录不消耗跳数（路径深不等于链长），但链上再加一层就多一次「要不要追读」的决策，也多一个断链点。新增的特化文档要注册进主文档的路由表，否则它不在任何动线上。
- 引用一律写从技能根出发的相对路径（`references/structure/pattern-iceberg.md`），不写绝对路径、不带上层目录。绝对路径只在作者机器上成立，上层目录一换就断。

## 内容该放哪一层

- **留在 `SKILL.md`**：每次命中都要用到的判断依据——这次该走哪条路、什么情况下不该用这个技能、各册的分工。
- **下沉到资源层**：只在某个分支上用到的展开——某形态的完整写法、某类场景的处理、供查阅的资料。
- 下沉不是免费的。后置内容的到达率完全押在指向它的那句指针上（指针三要素见[编写手艺](../documents/writing-craft.md)），而且断链是静默的——技能照常加载，取不到内容时没有任何报错。下沉前先算这笔账：省下的常驻成本，值不值押上到达率。
- 过度下沉的症状有两种：入口只剩一堆链接，读者在路由处无从选择；或某个判断依据只存在于深处，读者在入口层做决定时手里没有它。修法都是把那一句上移，不是把深处的内容复制上来——复制会让两处从此不一致。
- 一节能不能独立成册，看两条：它会被读者单独进入吗（有没有读者只找它、不需要先读别的），以及内容重量撑不撑得起一份文件（只有两三句的小节切出去，多一次跳转却省不下阅读量）。

## 校验

- 结构合规是机械问题，可检查三类：frontmatter 完整性（必填字段齐全、`name` 合规且与目录名一致、环境要求的子字段齐全）；引用无断链（正文指向技能内文件的相对路径目标确实存在）；目录与文件都在环境允许的条目内（不在白名单里的目录，换环境时第一处就报错）。
- 标准生态提供参考实现 `skills-ref` 做机器校验（`skills-ref validate ./my-skill`），机械检查 frontmatter 合法性与命名约定。交付前跑一遍，不靠自觉——设计过程靠判断，越接近交付越该让机器兜底。
- 断链的失效形态是静默的：技能照常加载，指向不存在文件的那部分知识在需要时取不到，作者收不到任何报错信号。机器校验是交付前发现它的可靠手段，也是找出问题时唯一不需要判断力就能拿满分的一项。
