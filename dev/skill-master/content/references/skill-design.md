# 技能设计（skill-design）

> 本文档是 skill-master 技能的设计工作论述：从零把一套已被走通的做法
> 设计成一个可交付的技能——怎么锚定、材料从哪来、怎么组织与打包、依什么
> 顺序编写、怎么披露与验证。读者默认已读 SKILL.md 的前提节《什么是一个
> 好的技能》；落笔写内容时的句子级手艺见 documents/writing-craft.md。
> 本文档只写设计这一种工作；各内容形态的编写细则在 documents/ 三册。

## 锚定

锚定是设计起点：先确定技能提供什么、指导什么、不管什么，并据此判定
值不值得做、材料够不够。它也是后续一切设计决定的依据——description 按
锚定结果收敛，审查按它区分「缺陷」与「设计如此」；锚不定，后面每一步都
在流沙上盖楼。

**定位三问。** 一句话概括通常不是一次到位，随材料与讨论逐步精确化；定稿
时必须精确回答三问：

- 提供什么——以文档交付的知识、方法与判据。技能的本体是一组文档，自身
  不执行任何操作，运行它的是加载后的 agent，「提供」因此总是文档形态
  的承载；
- 指导什么——在何种情况下引导 agent 如何行事；
- 不管什么——明确排除的相邻职责。排除边界与提供内容同等必须：没有排除
  项的定位必然过宽；排除项日后固化为 SKILL.md 的不触发条件。

**能力句。**「提供什么」的定稿形态是一句能力句：「提供通过 X 实现 Y 的
能力」。判据在时态上：X 必须是已被走通的做法——句子写成「打算、将、希望」
时，说明锚定的还是愿望而不是能力。

**值不值得做成技能**，三项判据缺一不做：

- 非一次性：任务会重复出现。只出现一次的活配一个技能是净负债——封装、
  维护、校验的成本都由这一次使用摊还；
- 真知识缺口：agent 缺的正是这块知识。agent 本来就会的、搜索即得的
  不是缺口，技能不增加价值；
- 需结构化封装：散落的经验不够用，需要组织成入口加支撑文件才能稳定
  复现。

**可行性**：材料能否撑起完整的技能结构——一个入口（SKILL.md）加至少
一本支撑内容。撑不起结构的技能是空壳，说明实践还没走到值得封装的那一步。

**身份前提**：设计输入是已被走通、被检验的做法；技能是实践的沉淀，没有
真实做法就没有设计对象——不为推测中的需求设计。

范围过宽的信号一句带过：一个技能锚不住三项以上独立职责时拆开，拆的判据
是每一半都能独立回答定位三问。

## 材料从哪来

设计材料来自真实实践，不是来自想象。判据是「反复走通、可复现」：同一件
事被走通过不止一次，换个人照做也能得到同样结果。三类东西不算材料——
推测（没做过、只是觉得该这样）、个案（一次巧合，未经复现检验）、搜索
可得（公开资料随处能查，封装它不增加价值）。

实践中的材料按形态分四类，各归其所：

- **客观资料**——事实、参数、边界条件，是查的不是读的，打包归 assets
  供查阅；
- **步骤序列**——按什么顺序做什么，是工作流形态，按
  [workflow-writing.md](documents/workflow-writing.md) 的方法编写；
- **判断依据**——什么条件下选什么、凭什么，是论述形态，按
  [essay-writing.md](documents/essay-writing.md) 的方法组织；
- **稳定输出框架**——产出长什么样，是模板，按
  [template-writing.md](documents/template-writing.md) 编写。

弯路与失败尝试不扔：它们构成 Gotchas——已知失败模式清单的素材。正文写
「这么做会踩什么坑、为什么、该做什么」，比只写「这样走就对了」有用——
失败模式是别人付过学费的浓缩，读者靠它避开整类错误。

各形态的编写细则在 documents/ 三册，本节只定去向。

## 组织与打包

技能的文件组织受开放标准约束，规范条目见
[standards.md](general/standards.md)——何时读：开始摆放文件结构、或核对
结构合规时。本册不转述规范条目，只立两条判断：

- **打包目录是放置问题**：SKILL.md 放技能根，内容按性质进 references /
  templates / scripts / assets；
- **打包与编写分离**：把一个工作流文档打包成 asset，不改变它按工作流
  形态编写的事实——「放哪个目录」与「按什么方法写」是正交的两轴。混淆
  两轴会按打包位置去找编写方法，是错误路由的根源。

展示目录树时从技能根开始，不含仓库上层路径。

## 编写

成文顺序有讲究：先写支持文件，再写 SKILL.md，最后写 description。

- 支持文件先写：SKILL.md 的路由要指向真实存在的文件、预告真实装着的
  内容——先有支持文件，入口才知道指向哪里；
- description 压轴：触发面是覆盖面在加载器那侧的投影，技能实际覆盖什么
  到正文齐了才确定，提前写必然返工；
- 内容形态决定写法：一份内容是工作流、论述还是模板，路由到 documents/
  对应册取方法；不按打包位置取编写方法；
- 句子级手艺——no-op 检验、正向陈述、量化模糊词、指针三要素——见
  documents/writing-craft.md，任何一段落笔前都值得先过一遍。

## 披露

披露是技能向加载器与用户呈现自身的方式，由 description、触发面、命名
构成。技能名是双重身份：加载器靠它识别、用户靠它称呼——简短、自解释、
不与相邻技能撞名，称呼才叫得准、匹配才分得清。

description 与触发面的设计方法论见 [disclosure.md](general/disclosure.md)
——何时读：写 description、定技能名、打磨触发词时。锚定在这里只提醒一句：
description 的每个词都是每次会话常驻的成本，覆盖面收敛之前不要写它。

## 验证

设计完成的技能在交付前验证自足性：委派一个无上下文的子代理，让它仅凭
技能文档完成目标任务，收集它卡在哪、误解了什么。验证查的是「写全了
没有」——零上下文的读者用不起来，多半是缺了判据或断了链路，不是句子
写错；卡点清单就是下一轮修改的工单。

**隔离纪律**：任务预期与对比信息不进子代理的 context。子代理一旦知道
「应该得到什么」，预期引导会把技能缺的环节悄悄补上——这时验证的是提示词
而不是技能。同理，场景别只挑自己能通过的：手动模拟有验证者偏见，委派
子代理正是为了绕开它。

验证与审查的分工：验证判「零上下文能不能用起来」，审查判「写得对不对」，
两者不互相替代。卡点修不动、或修着发现是设计意图问题，就回锚定重答三问。

## 推荐路径

大致的走向是 锚定 → 组织 → 编写 → 验证，但这不是阶段流水线：设计是
发现过程，卡在任一处都可以随时回头——材料不足回实践补积累，写出来发现
范围没钉住就回锚定重答三问。回头时关键要明确回到哪一步、修什么，而不是
模糊地「重新想想」。只有内容本身是程序时才用流程形态；判断依据按需查阅，
不设门禁。

## Gotchas

- **禁止语悖反**：禁止语让被禁行为更可及——「不要跳步」反而把跳步送到
  读者眼前。该做什么：规则正向陈述目标行为；只有无法正面表达的硬护栏
  才保留禁止，且必须配对「该做什么」。
- **为推测的需求设计**：没有真实做法支撑的「需求」不构成设计输入，按它
  设计的技能无人会用。该做什么：锚定时先问「这套做法是否已被走通」，
  答不上来就回去积累实践。
- **成品格式化石**：把一个个案的成品格式当作方法论写进技能——技能教的
  是可复用的判断，不是某次的产出形状。该做什么：先问产出形状背后有没有
  可迁移的结构；有则按 template-writing 拆骨架、试填验证，没有就让它
  留在个案里。
- **委托边界泄漏**：把该隔离的信息（预期、对比基线）写进执行方读的文档，
  验证就失去效力——子代理会顺着预期把技能缺的环节补上。该做什么：验证
  用的预期与对比信息只留在验证者手里，不进技能文档、不进子代理 context
  （见「验证」节的隔离纪律）。
