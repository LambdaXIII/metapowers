# Init Protocol

## 初始化目标

Journal 初始化完成后应处于两个状态：

- **就绪态**：RULES.md、INDEX.md 已就位。内容是种子级别的——最小可用骨架。以后的内容由日常操作驱动，自然生长。不预填、不预设。
- **可发现态**：后续每次 session 启动时，agent 的上下文中**直接可见**一条指令：必须读取 INDEX.md。不需要搜索、不需要回忆、不需要猜测。

  这是各阶段共同保证的效果：

  ```
  发现合约（P3 设计）
    → 每次 session 启动时自动注入上下文
      → 指令：读取 <journal-root>/INDEX.md  （P1 确定的位置）
        → INDEX.md 协议声明节告知              （P2 创建/修复的）
          - Read without skill
  ```

初始化后的生长由真实使用驱动：
- 第一个标签、第一条经验、第一条知识——从工作中自然产出
- 目录在写入时按需创建（由规则文档分类板块或后续分类审计催生）
- INDEX.md 的内容随实际经验积累自然填充

---

## P1: 确定位置 + 检查

> journal-root 是所有操作的锚点。位置不确定则后续步骤无依托，文件可能错位。

**判断上下文**：
- 上下文中已明确 journal-root → 采信，直接进入下一步
- 上下文中未明确 journal-root → 询问用户，推荐 `~/.journal`，确认后采信
- 用户执行前已直接指定路径 → 视同已确认，直接使用

**检查目录中是否已有笔记文件**：
- 判定标准：目录中已存在笔记条目——除 INDEX.md、RULES.md 等骨架文件外的 .md 文件——与否
- 已有笔记文件 → 继续 P2 创建骨架，并在 P4 执行一次维护协议
- 无笔记文件 → 继续 P2 创建骨架，P4 跳过

P1 完成条件：journal-root 已确定且唯一、已有内容情况已明确。无需验证步——确认即完成。

---

## P2: 创建骨架

两个骨架文件：**INDEX.md**（协议声明）+ **RULES.md**（规则文档种子）。

四个种子目录（inbox/ experience/ knowledge/ active_works/）**不主动创建**。它们由写入操作按需催生——写入时检查目标目录是否存在，不存在则创建。

### 通用检查流程

对每个骨架文件：

1. 检查 journal-root 下同名文件是否存在
2. 存在 → 先改名为 `<原名>.bak`（保留原内容供维护期参考），再继续
3. 从 `../templates/seed/` **复制**对应种子文件（复制，不建议抄写）

| 骨架文件 | 内容 | 种子 |
|---------|------|------|
| INDEX.md | 协议声明（技能管理声明/加载标注） | `../templates/seed/INDEX.md` |
| RULES.md | 规则文档（分类/标签/元数据字段/INDEX 结构/写作需求板块） | `../templates/seed/RULES.md` |

**旧种子文件处置**：若存在 CLASSIFICATION.md / TAGS.md / CONVENTIONS.md（旧版种子文件）→ **保留原样**——不参与 .bak 改名、不删除、不迁移。其内容如何并入新规则文档由 P4 触发的维护协议处理。

> 注意：新种子 INDEX.md 仅含协议声明、无初始化占位行——无占位符替换步骤。

> 核心原则：先备份后覆盖，不丢失用户已有内容。

### 验证

逐项确认：
- [ ] `<journal-root>/INDEX.md` 存在且包含协议声明节
- [ ] `<journal-root>/RULES.md` 存在（内容可为种子形态）

## P3: 设计发现合约

> ⚠️ **禁止自行执行**——此阶段只提案、提醒、编写草稿。不做任何写入操作，不改任何配置。
>
> 禁令作用域：仅限「发现合约的建立与配置变更」。P2 的骨架创建与 P4 触发的维护不在此禁令内。

**目标**：为 journal-root 建立发现合约，达成【初始化目标】中的可发现态——下次 session 启动时，agent 无需搜索即可读到「读取 INDEX.md」的指令。

**动作序列**：

1. **检查现有合约**——按 [已有合约的检测](design-discovery-contract.md#已有合约的检测) 的特征文本搜索当前环境；找到即逐项比对 [要素覆盖检查](design-discovery-contract.md#要素覆盖检查)，报告差异与更新建议，不重复设计
2. **载体清查**——按 [载体清查](design-discovery-contract.md#载体清查) 逐类检查当前运行时可能的注入机制，确认读写权限
3. **评估**——用 [评估候选载体](design-discovery-contract.md#评估候选载体) 的三个过滤问题裁定候选，选出推荐载体
4. **推荐呈报**——向用户说明推荐载体与理由、合约文本、风险、备选方案（[推荐与呈报](design-discovery-contract.md#推荐与呈报)），由用户决定
5. **回退触发**——无候选通过过滤时回退：journal-root 沿用已确定的路径（回退只影响发现合约的载体选择，不改变 root；用户另行指定除外，如改用 `~/.journal/` 等更通用的路径），把 [注入文本模板](design-discovery-contract.md#注入文本模板) 交给用户手动粘贴并自行确认位置，并告知此方案需手动维护、可靠性低于自动合约

**禁令**：不得自行写入宿主提示词——对注入文本只能提案、提醒、编写草稿，写入或更改由用户执行，或经用户批准后执行（[更改宿主提示词的权限](design-discovery-contract.md#更改宿主提示词的权限)）。

**完成条件**：可发现态检查——已有合约或用户已执行写入时，核验下次 session 启动无需搜索即可读到「读取 INDEX.md」的指令；尚无合约且写入未发生时，完成态是呈报已交付并获用户确认，合约生效由用户写入后达成，不作为本阶段的前提。

这项工作是什么与为什么、有效合约的条件、检测与评估方法，见 [发现合约论述](design-discovery-contract.md)。

---

## P4: 维护接管（条件触发）

若 P1 检查发现目录中已有笔记文件 → 执行一次【维护协议】（见 `protocol-maintenance.md`）——已有内容由维护协议接管整理（含旧种子文件内容并入规则文档），初始化协议不处理内容迁移。

若 P1 检查无已有笔记文件 → 跳过本阶段。
