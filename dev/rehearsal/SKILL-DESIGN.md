# Rehearsal — 设计锚定文档

## 本文档的定位

这是 rehearsal 技能的**设计锚定文档**——记录这个技能为什么这样设计、修改时哪些约束不可破坏、新增功能时如何保持一致性。读者是接手维护这个技能的开发者，不是在寻找技能使用说明（那在 SKILL.md 和 references/ 中）。

**本文档只锚定本技能特有的设计方向、原则、目标，及其理由。** 三条排除规则：

- **不记录通用技能设计方法论**：description 写法、references 组织、开发速记纪律等适用于所有技能的规范已固化在 AGENTS.md（§2.7、§4.6、§4.7），本文档不重复，只记录 rehearsal 对这些规范的**具体落实与理由**
- **不记录技能内容**：触发规则、执行流程、步骤结构、文件目录树、评估维度、术语定义——那些是 SKILL.md 和 references/ 的职责。技能内容变了但方向没变，不更新本文档
- **不记录历史**：版本沿革、当时的变更过程、反例教训的版本归属——那些是 CHANGELOG.md 的职责；本文档只保留仍然成立的方向，不保留它是在哪个版本确立的

与相关文档的边界：

- **SKILL.md**：技能入口——触发条件 + 核心指令。不展开设计理由。
- **CHANGELOG.md**：逻辑变更记录——按版本号组织。不记录设计理由。
- **AGENTS.md**：项目规范——通用技能设计方法论 + SKILL-DESIGN 格式要求。不包含具体技能的设计。

更新时机：**仅当本技能的设计意图或方向变化时更新**。局部实现、措辞、bugfix 不触发更新。

## 命名理由

**rehearsal**（彩排/预演）：

- 跨语言可读：英语中 rehearsal 不带有任何特定行业或框架的联想
- 跨载体通用：可以用于文档、代码、UI、API、会议脚本、教学大纲等任何交付物
- 本质贴合：rehearsal 的核心是"在正式演出前走一遍流程，找出问题"
- 动作感强：作为技能名易于触发，读者能直观理解其功能

候选排除（防止未来改名冲动——名字一旦确立就是方向的一部分）：

- `first-contact-simulation` — 过长，且过于强调"首次"忽略了推演也适用于非首次场景
- `perspective-audit` — 过于抽象，不易理解
- `dry-run` — 在工程语境中已有特定含义（测试不含实际效果的代码运行），易混淆

## 设计意图

这个技能解决什么问题？**任何人在生产"给别人看/用的东西"时都无法感知接收方的第一视角体验。** 作者知道自己想表达什么、目的是什么，因此看不到"不知道目的的人会在哪里卡住"。

rehearsal 就是强制切除"作者知识"的方法——让作者或评估者在脑子里模拟一次接收方的首次接触 → 理解 → 决策过程。哪里卡住了，哪里就是材料的问题。

## 设计定位

技能在方法谱系中的位置。这三个定位决定技能应该长成什么样，是判断一切修改是否偏离方向的依据。

### 提示性框架，不是工作流设计

推演方法是**提示**（guide），不是**规范**（工作流）。运行时 agent 结合具体场景判断，优于预先规定的机械规则。因此：

- 硬性约束只保留在流程骨架层面（准备 → 模拟 → 评估）
- 具体操作给判断空间：不写场景特化规则，"有则有，无则无"
- 过度机制化（如强制要求"必须有记录"）反而违反准确复现——它让推演者为满足形式而编造内容

### 轻量模拟，不是严谨校对

推演相对"理想严谨校对"（新 agent 读材料 + 全部对话历史 + 逐项校对 + 分层处理上下文溢出）是轻量手段：不依赖外部资源、可反复执行。这解释了为什么选择模拟而非严谨校对，也是"嵌入优于收网"（见关键架构决策）的前提。防止未来把推演误当严谨校对使用。

注意：**定位词不出现在技能正文中**。"快速""零成本"这类定位词只允许保留在 description 匹配面，正文中使用会造成误导——推演不是零成本的，它的成本是推演者的认知投入。

### 准确复现是总目标

推演的目的 = 为推演材料提供**有指导价值的优化依据**——不为否定而否定，也不附和。优化方向是**准确复现**：材料在全新状态（无作者上下文）下被重新阅读时，读者复现的理解与编写时的理解相同。复现质量从四个方向检查：**劣化、偏差、过度、重复**（各自定义在通用论述首章，此处只锚定目标本身）。

偏离发现时，是材料的问题，还是设计意图本身需要修正——不要偷改意图来让推演"合格"，偏离的发现恰恰是盲区。

### 推演止于评估

推演的作用是**提供指导性评估**，不是修改并完善材料。是否修改、如何修改、是否通过、如何交付，都不在推演技能的工作范畴内——评估整理（P5）是推演的终点，之后的事属于材料所有者。

理由：推演是"检查"，不是"修理工"；把修改、通过判定纳入推演，会让推演滑向工作流设计（与"提示性框架"定位冲突），并且推演者常是作者本人——修改决策应基于推演依据独立做出，推演只提供依据不代做决策。这也是通用论述不设"通过标准"、P5 止于评估整理的原因。

## 关键架构决策

每个决策记录：方向、理由、不变量。这些是修改时不可破坏的约束。通用组织规范（references 如何组织、description 怎么写）见 AGENTS.md §4.6/§4.7，此处只记录 rehearsal 的具体落实。

### 三层文件结构：通用论述 + 场景文档 + 补充参考

**方向**：推演内容按三层组织——通用论述（方法全貌，必读入口）、场景文档（按载体类型特化）、补充参考（跨场景小块知识）。

**理由**：

- 推演适用载体极多（文档、提示词、交互流程、API 设计、设计方法论、知识库、逻辑链路、计划文档…），每个载体的推演信号和检查重点差异大，单份文档无法承载也不该承载——需要按载体特化
- 但推演方法骨架必须唯一：如果每个场景文档各自定义一套推演步骤，会出现多份互相偏离的方法定义。因此场景文档**不发明新步骤**，只在骨架内补充本载体的特殊信号——这是本技能区别于"每个载体一套方法"的设计选择
- 补充参考（缺陷分类法、批量执行）是跨载体的情境知识，不绑定载体

**不变量**：

- 场景文档假设读者已读通用论述；补充参考假设读者已读对应的通用论述/场景文档
- 新增场景文档必须同步注册到通用论述末尾的路由表；移除场景文档必须移除路由项
- 场景文档不包含跨场景的通用知识——引用补充参考，不重复补充参考

### description 的设计

**方向**：当前 description 采用「中英双名 + 载体列举 + 双路径触发 + 反向一条」的结构。每个构成元素都有本技能特有的理由：

- **中英双名必须同时出现在首句**：技能名是英文 rehearsal，但用户（中文语境）用「推演」触发——「推演(rehearsal)：」保证两个名字都是正向命中，不依赖偶然的字符碰撞
- **载体列举是匹配面的主体**：rehearsal 的触发场景是"任何给别人看的交付物"——列举文档/提示词/API/UI/计划等让"交付物类型"类问法也能命中，而不是只依赖"推演"这个动词
- **触发词必须双路径**：用户提问用语（推演/验一下/检查/能不能走通/过一遍）与 agent 自问用语（能不能被没上下文的人读懂/交付出去会不会卡住）是两种不同的触发来源，缺一就漏一半场景
- **反向条件只留一条（仅改错别字、错标点、纯格式调整）**：触发面越宽，反向条件越稀释匹配面；"仅改错别字"是唯一的高频误触发场景，其余反向判定写入 SKILL.md 正文
- **不指向 references 下的场景文档**：references 下的文件不是独立可加载技能（如 logic-chain 场景文档曾被误当独立技能指向过，造成 agent 漏触发本技能）——本技能不重复这个错误

**不变量**：description 的任何改写必须维持上述五个构成元素；触发判定细则的展开在 SKILL.md 正文「触发条件」节，不在 description 中重复。

### 评估整理不是打分机制

**方向**：评估整理环节不采用固定评分。★ 1-5 只是严重程度判定的**格式选项之一**（且仅用于跨版本量化追踪，不是通用严重程度格式）。

**理由**：

- 打分暗示量化产出——名称暗示推演者必须产出 ★ 评分，但实际目的是将发现转化为可行动的评估（归类、排序、覆盖检查）
- 载体不等价——文档推演需要量化对比，逻辑链路推演需要二元判定（OK/异常），设计方法论推演需要可行动分类（阻塞/缺陷/建议），同一个"打分"无法覆盖
- 发现与评估分离——模拟过程已完成缺陷发现，评估整理的角色是整理和判断，不是二次发现

**不变量**：严重程度格式由载体类型决定，场景文档显式声明该载体的推荐格式。

### 嵌入优于收网

**方向**：将推演拆成阶段性进行（每完成一段/一章就做一次短推演）比一次性做完整推演更高效。

**理由**：缺陷发现得越早，修复成本越低——来自实践经验。

**不变量**：阶段性推演取代不了最终的全景推演——跨模块交互问题往往只在全景推演中暴露。

### 元语境渗漏：锚定作者身份框架 + 修复三分

**方向**：缺陷分类法以「元语境渗漏」（英文对照 Context Leak）为统一术语，指作者身份的语境（设计意图、讨论背景、写作时的自我定位）泄漏进材料。锚定技能既有的「作者身份/读者身份」框架——判定标准是读者身份检验（这段内容是读者身份需要的，还是只有作者身份才懂、才在乎的），不引入独立的语境模型。保留两类观察形态——悬空参照（无法解析，归偏差方向）与身份边界错位（能解析但读者身份不需要，归过度方向），共享同一判定与修复框架。修复方向三分（删除/归位/转化），转化必须保持约束强度同档。新增「不正确的暗示」缺陷类型（偏差方向）：材料通过结构/顺序/标题/措辞暗示作者未意图的关系。

**理由**：
- 复用既有框架优于引入新模型：rehearsal 已以「作者身份/读者身份」为骨架（P1S2 解离、P2 划掉、P3「材料只应承载读者身份的内容」），「元语境」作为「作者身份携带的语境」锚定其上，避免两套平行框架的认知负担
- 形式信号不可靠：作者现身措辞既非充分也非必要，引用类渗漏（悬空 §N 编号、陈旧内部术语）无信号词、文字形式完全合法——信号清单覆盖不到，读者身份检验是唯一判定
- 只删除会丢信息：渗漏内容并非全无价值——设计意图是设计文档类载体读者需要的（归位）、作者许可中含读者需要的操作事实（转化）。三分已穷尽，无需第四类
- 保留两条目而非合并：悬空参照与身份边界错位的观察信号不同（解析受阻 vs 能解析但噪声），分开归类更直接，且不破坏四向骨架
- 「不正确的暗示」独立于元语境渗漏：渗漏是多了不该有的显式文字，暗示是显式内容之外的结构/措辞误导读者推断——根因与修复都不同
- 修复三分属于评估产出的优化依据，不违反「推演止于评估」——推演者给修复方向，不执行修复

**不变量**：
- 判定标准只有读者身份检验一条；任何信号清单扩展不得成为替代判定
- 修复方向不再新增第四类（三分已穷尽）
- 「元语境渗漏」在技能内容中统一使用，英文对照 Context Leak；「悬空参照」「身份边界错位」作为形态名保留
- 不引入「元语境/文字语境」「写过程/读过程」等独立语境模型术语——语境概念一律通过「作者身份/读者身份」表述
- 不显式区分「内容完整/表述准确」两个操作层面——推演一次性完成两层检查，显式分层会制造「分别对待」的错误暗示

### 完成判据操作化：可检查但不机制化

**方向**：推演各步骤补充可检查的完成判据（P1 准备完成标志、P3 留意清单收束、P4 边界尝试与「边界覆盖」维度挂钩、执行策略的停止条件），但保持提示语气——判据是「推演者自行判断这一步是否做完」的依据，不是「必须产出记录」的强制项。

**理由**：
- 模糊判据招致过早完成：P1S3 意图清单是 P5S1 复现对照的唯一基准，清单残缺时对照在残缺基准上进行，且推演者无法自知——因此准备阶段停笔标准从严
- 留意清单无收束则静默遗漏不可拦截：P5S4 覆盖检查针对评估维度表，与 P3 留意清单不重叠，需各自闭环
- 与「提示性框架」定位的边界：判据指向「何时算做完」的判断，不引入「每个模式必须有记录」类强制项——后者让推演者为满足形式而编造内容，违反准确复现
- 「上游已保证」类排除条款必须操作化：无判定标准的排除是漏测与范围膨胀的双向风险源

**不变量**：
- 完成判据表述为可检查条件，不引入强制记录要求
- 「上游已保证」必须有显式声明位置（材料中声明由谁负责或前置步骤产出，读者能找到声明处）
- 边界尝试除载体确无边界可言外是 P5「边界覆盖」维度的输入，不可跳过


## 措辞风格约定

- 使用**「接收方」**而非「用户」——技术语境中「用户」有专指（最终用户），而推演模拟的读者可以是 agent、学生、顾客等
- 渗漏类缺陷统一使用「**元语境渗漏**」（英文对照 Context Leak）；「悬空参照」「身份边界错位」仅作为两种观察形态的名称使用

## 维护注意事项

- **缺陷分类法是活的体系**：随着在不同载体类型上的实践可以扩展缺陷类别；但扩展时不得引入"因为载体差异导致的伪类别"
- **评估维度表是活的体系**：实践积累允许添加新的推荐维度组合；但已验证维度不应轻易移除。新增维度应先在通用论述中定义，场景文档可扩展本场景的特殊维度
