# API 设计推演
> 场景文档 — 配合推演通用论述（`../rehearsal-guide.md`）参考使用，补充 API 接口契约载体的特化内容。

将推演方法应用于 API 设计的接口契约验证。适用于：
- REST/GraphQL API 端点设计
- 函数签名和公共库的导出接口
- 配置文件的字段和格式设计
- 任何"调用者通过规范文档接入"的契约

## 本载体的核心差异：接口契约边界

API 是接口契约——定义了调用者和实现之间的边界。本载体的推演范围（P1S1 范围确定的具体化）**严格限制在接口层面**：

**在范围内：**
- 接口的命名是否一致和自解释
- 参数和返回值的类型和默认值是否合理
- 错误信息是否可被调用者理解和处理
- 单个接口和组合接口是否覆盖了调用者的需求
- 版本变更时的向后兼容性
- 限流/配额行为是否有清晰定义（错误码、重试语义）

**不在范围内：**
- 接口背后的实现逻辑是否高效
- 数据库 schema 是否合理
- 认证/授权的内部机制是否正确
- 运行时的并发安全性

实现相关的问题见 [logic-chain-rehearsal.md](logic-chain-rehearsal.md)。API 推演只管"调用者看到什么，怎么用"。

### 接口层面的推演焦点

不同于文档推演（关注理解和可跟踪性），API 推演关注三个核心问题：

1. **接口覆盖面**：调用者需要完成的任务序列中，每一步是否有对应的端点？
2. **命名一致的语义模型**：调用者理解了一个端点能否自然推断其它端点的用法？
3. **组合使用的可操作性**：多个端点按业务逻辑组合时，一个端点的输出能否直接映射到下游端点的输入？

三焦点是模拟阅读时主动追问的核心问题；评估维度表（见评估整理）是 P5S2 整理发现的完整清单，包含三焦点未列出的维度（错误信息可操作性、默认值合理性、契约完整性、版本语义一致性等）。

## 调用者定位（P2 身份设定的要点）

API 的调用者——正在理解 API 文档并尝试构造一次正确的调用的开发者。已知其自身业务的场景和需求，但从未读过这份 API 文档。

初始状态：
- 知道要完成的目标（例如"获取用户列表，过滤活跃用户"）
- 有基础的 HTTP/编程知识
- 没有本 API 的特殊约定或术语

P2 身份转换时特别需要划掉的设计者知识：不知道「这个端点之后还会有 `/users?admin=true` 的变体」，不知道「返回的 `next_token` 带 null 就表示最后一页」——除非文档明确说明。不知道设计过程中的取舍和未来的扩展计划。

## 模拟阅读的特有信号（P3 补充）

按调用者阅读文档的顺序逐段走（API 文档的"阅读顺序"即调用者构造调用的顺序），记录信号：

| 信号 | 含义 |
|------|------|
| "不知道这个端点干什么" | 名称不够自解释，或路径层次不清 |
| "参数名相似但含义不同" | 不同端点的相似参数名表示不同概念——命名一致性被破坏 |
| "返回值文档中未完整定义" | 覆盖缺口——调用者不知道接收到什么 |
| "从前一个端点的输出到下一个的输入有摩擦" | 字段名不一致或结构不匹配——组合使用有摩擦 |
| "这个错误码没有对应修复指导" | 错误信息不可操作——调用者只能重试或放弃 |
| "默认值不符合我最常见的场景" | 默认值没覆盖高频用法——每个调用都需显式设置 |

## 边界与异常场景（P4 补充）

API 载体值得主动尝试的异常场景：

| 场景 | 检查目标 |
|------|---------|
| 翻页到达末尾 | `next_token` 为空或不存在时的行为是否明确 |
| 并发修改 | 两个调用者同时修改同一资源的冲突处理是否定义（只查冲突语义是否在契约中声明——如 409 响应、If-Match 语义；不查内部并发实现） |
| 请求体过大/过小 | 边界值和默认值的行为——文档是否说明了限制 |
| 缺失必选参数 | 错误信息是否包含"需要什么"而非仅"缺少参数" |
| 不支持的 HTTP Method | 是 405 Method Not Allowed 还是无文档的 404 |
| 版本不匹配 | API 版本变更时调用者的迁移路径是否清晰 |
| 超大响应 | 是否支持分页、过滤、字段选择来限制响应规模 |
| 从示例/中间章节进入 | 调用者从示例代码或搜索结果直接进入文档中部——示例是否自包含、是否标注依赖的前置定义 |

## 评估整理（P5 的要点）

**严重程度格式：** 阻塞/缺陷/建议。三级定义：

- **阻塞**：调用者无法完成必要操作（如缺失端点覆盖）
- **缺陷**：调用者能接入但体验受影响（如命名不一致、摩擦）
- **建议**：文档或命名微调

**评估维度提示（在通用论述评估维度表 API 行 4 项基础上扩展为 7 项；额外提示，非硬性指标）：**

| 评估维度 | 含义 |
|------|------|
| 命名一致性 | 同一概念在不同端点中命名一致，不同概念不会混淆 |
| 默认值合理性 | 可选参数的默认值是否覆盖了最常见的场景 |
| 错误信息可操作性 | 错误响应是否包含可指导修复的信息（不只是 400） |
| 缺失端点覆盖 | 调用者需要的操作是否有对应的端点 |
| 组合流畅性 | 多个端点按业务逻辑组合时，响应到请求的映射是否自然 |
| 契约完整性 | 每个端点的参数、返回值、错误码、限流行为是否完整定义 |
| 版本语义一致性 | 同一版本号标注的契约在不同环境/修订间保持一致（区别于跨版本变更的向后兼容性） |

**复现对照注意（P5S1）：** 回到 P1S3 整理的作者意图（编写时的理解），按四向对照复现理解。API 的意图偏差常见于设计者假设调用者知道某个约定但文档未显式说明。整理作者意图时可列出端点清单、参数契约、错误码表作为逐条对照的基准。

**错误模式搜索候选（P5S5）：**

- **命名语义漂移** — 同一概念在不同端点中命名不同（如 `user_id` vs `userId` vs `uid`）
- **错误信息不可操作** — 只返回 HTTP 状态码不告诉调用者怎么修
- **组合使用摩擦** — 端点 A 的输出字段名/结构不能直接映射到端点 B 的输入

## 与其它推演的关系

- 与 [doc-guide-rehearsal.md](doc-guide-rehearsal.md)：API 文档本身也是文档——其可读性、可跟踪性（读者能否顺畅读完并理解）归文档推演；本场景只管契约正确性。两者可叠加使用：先按文档推演检查 API 文档的可读性，再按本场景检查契约层面
- 与 [logic-chain-rehearsal.md](logic-chain-rehearsal.md)：API 只管表面契约。实现层面的控制流、状态一致性、资源生命周期归逻辑链路管
- 与 [interaction-rehearsal.md](interaction-rehearsal.md)：交互推演关注的是操作者在界面/命令层的体验，API 推演关注的是调用者在规范文档层的接入体验——前者是"点哪里"，后者是"调哪个端点"
- 与 [prompt-instruction-rehearsal.md](prompt-instruction-rehearsal.md)：API 文档的措辞精确性同样重要——调用者对 API 的理解完全依赖文档。但 API 推演的核心判断维度是接口覆盖面和一致性，措辞是辅助项

## 常见陷阱

- **推到实现层去论证**：讨论"这个端点在数据库里是 O(N)"——这不是 API 推演的范畴
- **用已知的其他 API 模式填补空缺**：调用者不知道 Stripe 或 GitHub 的 API 是什么样子——不要用已知模式填补缺失的文档
- **忽略组合使用场景**：一次调用成功不算完成——检查调用者的业务流可能需要 3-5 个端点协同
