# Rehearsal（推演）— 通用论述

## 推演是什么

**Rehearsal（推演）= 暂停作者身份，完整走一遍另一个视角的「首次接触 → 理解 → 决策」链路。**

它和载体无关——可以推演文档、代码、UI 流程、API 设计、教学大纲、定价页、演讲脚本、审查清单。
它和客体也无关——客体可以是 AI 模型、真实用户、读者、学生、顾客、新人同事。

## 为什么推演管用

作者有一个致命盲区：**你知道"应该得到什么结论"，所以你看不到"得不到的人会在哪里卡住"。**

Rehearsal 就是强制切除"设计者知识"。你假装不知道——然后走一遍。哪里卡住了，哪里就是设计有问题。

## 局限性

Rehearsal 是**同体模拟**——你在模拟一个和你推理结构相似的客体。如果你的推理结构和客体差异大（比如你在模拟一个 7B 小模型，或一个完全不了解你领域的用户），准确性会下降。

对低同构性的客体，rehearsal 仍然有价值（暴露明显的结构问题），但不应被视为精确的可用性测试。

## 与其它方法的区别

- **Rehearsal ≠ 测试**：测试需要真实客体（真实用户、真实模型）。Rehearsal 是模拟，零成本。
- **Rehearsal ≠ 自查**：自查是"我再看一遍有没有错别字"。Rehearsal 是"我假装不是作者再走一遍"。
- **Rehearsal ≠ 同行评审**：同行评审有另一个真人参与。Rehearsal 是你在自己的脑子里跑另一个人的模拟。

## 核心方法

### 三个不变元素

| 元素 | 含义 | 自问 |
|------|------|------|
| **客体** | 你要模拟谁的视角 | 他知道什么？不知道什么？期望什么？怕什么？ |
| **载体** | 被推演的产物 | 它是什么形式？客体按什么顺序消费它？ |
| **链路** | 从接触到完成目标的完整路径 | 第一步是什么？哪里可能停？哪里可能跳？哪里可能误解？ |

### 四步流程

核心流程包含四步（1-4），第 0 步是推演前的准备工作——在进入核心流程前先明确设计意图。
**0. 作者视角**

先以作者身份回答三个问题。写下答案——不是想一想，是写下来：

1. **这份材料的目标读者是谁？** 他有什么背景知识？他期望从这份材料中得到什么？
2. **阅读完成后，他应该知道什么、能做什么、感觉到什么？** 这是你的设计意图——推演评估时将用它对照实际接收效果。
3. **你的前置假设是什么？** 你假定了读者已经知道哪些事、手边有哪些工具、处于什么状态？

跳过这一步的典型后果是 Context Leak——你写下的参照点只有你自己知道，读者看到的是悬空指针。这种缺陷的识别和修复见[缺陷分类法](supplementary/defect-taxonomy.md)中的 Context Leak 条目。

这三个答案构成推演的**设计意图基线**。推演结束后，回到这些答案，逐条确认客体的实际接收是否与意图一致。中间偏离意图的不一定是问题（也许是更好的路径），但偏离意图而你没想到的——那就是盲区。

**1. 清空**

扔掉所有作者记忆。不是「假装不知道」——是显式地写下你**不再拥有**的东西：

- 作者意图：「这份材料想达到的目的是……」——划掉。客体不知道目的。
- 隐含上下文：「读者应该知道 X 是 Y 的别名」——划掉。没写 = 不存在。
- 设计过程中的取舍：「这个方案是因为 Z 约束才选的」——划掉。客体只看到最终结果。

然后显式设定你的阅读身份：

- 我是 [ 客体描述 ]，我此刻的状态是 [ 初始状态 ]
- 我手里有 [ 材料名称 ]，除此之外没有任何其他参考
- 我的目标是 [ 读完后要做什么 / 决定什么 ]

身份设定越精确，推演越有效。模糊的身份（「我是一个用户」）产生的信号也模糊（「这里有点 confusing」）。精确的身份（「我是一个刚入职两周的开发者，第一次读部署文档」）产生可操作的信号（「读到第三步时我不知道 `deploy-key` 在哪里找——文档没有说明生成位置」）。

**2. 逐帧跟**

按客体消费的顺序逐段走，记录每步的心理反应。不要跳到结论——瓶颈往往在中间某一步，不是最后。

记录格式（内心独白）：

- "这里停顿了" → 信息密度过高或措辞模糊
- "这里被吓到了" → 警告/限制过多，客体可能放弃
- "这里跳过了" → 结构上没有抓住注意力
- "这里误解了" → 措辞有歧义
- "这里不知道该做什么" → 缺少明确的下一步

**3. 边界刨**

故意走非正常路径。至少覆盖三类常见模式：

- **信息缺失**：客体缺少某条前置知识，或跳过了某个章节
- **错误输入**：客体做了错误操作，或误解了某条指令
- **跨模块跳转**：客体从中间进入，或从另一条路绕过来
- **责任边界错位**：边界条件超出被推演载体的责任范围。上游阶段已验证的条件不属于本载体的推演漏洞——那是上游的问题。推演前先明确"这个载体负责什么、不负责什么"

**边界范围约束**：每个边界条件必须在载体的**自身责任范围**内。不测试上游阶段或依赖已经保证的条件。有效的边界是载体自身可以预料并处理的合理变化（如极简/极繁输入、大量分支、不确定步骤、并行链路）。超出责任范围的边界暴露的是上游问题，不是载体的问题。

### 4. 评估整理

将前三步的发现整理为结构化的评估结果——告诉你发现了什么、多严重、先修哪个、有没有遗漏。

**4a. 意图对照**

回到步骤 0（作者视角）写下的三条答案。逐条检查：

- 推演结果是否与意图一致？ → 一致 / 偏离 / 超出意图
- 偏离意图的地方：是指令/文档的问题，还是你的设计意图本身需要修正？
- 不要偷改意图来让推演"合格"——偏离意图的发现恰恰是盲区

**4b. 发现归类**

将步骤 2（逐帧跟）和步骤 3（边界刨）产出的原始信号填入评估维度。每条发现记录四个要素：

| 要素 | 说明 |
|------|------|
| 评估维度 | 该发现属于哪个评估维度 |
| 实际效果 | 推演中观察到的实际接收/行为（来自步骤 2-3 的原始信号） |
| 预期效果 | 此处应该达到的效果——因为未达到才成为问题 |
| 严重程度 | 按 4c 的格式判定 |

"预期效果"是关键：推演发现的问题之所以是问题，是因为实际效果偏离了应有的效果。写出预期效果让修复者知道目标状态是什么，而不只是"这里有问题"。

同时为每条发现标注缺陷类型（参见 `defect-taxonomy.md` 中的分类体系）。同一缺陷类型出现 2 次以上 = 结构性缺陷，需要从载体架构层面修复而非逐处修补。

维度根据载体类型选择（见下方评估维度表）。每个维度必须有记录——"没有发现"不等于"没有问题"，需要确认是你检查过了还是没检查到。

**4c. 严重程度判定**

根据载体类型推荐的格式，判定每个发现的严重程度：

| 格式 | 适用场景 | 示例 |
|------|---------|------|
| 阻塞/缺陷/建议 | 通用格式（可排序、无虚假精度、直接映射修复优先级） | 文档、提示词、交互流程、API 设计、设计方法论 |
| ★ 1-5 | 仅用于跨版本量化追踪（测量工具，非严重程度格式） | 知识库 |
| OK/异常 | 二元判定——行为要么符合预期要么不符合 | 逻辑链路 |

**4d. 修复优先级与覆盖检查**

根据严重程度排序修复优先级。排序依据：

1. 阻塞级发现最先修——它们直接导致客体无法完成目标
2. 影响核心链路的发现优先于边缘场景
3. 同一缺陷类型的多个发现合并修复比逐个修更高效

最后检查覆盖完整性：审视评估维度表，是否每个维度都有记录？空维度需要回答——"确实没有问题"还是"这个维度我没有检查"？

**4e. 错误模式提取**

完成 4a-4d 后，审视全部发现，寻找重复出现的根因：

- 多条发现是否源于同一个写作/设计习惯？（例如：多处"路径末端无收束"→ 作者习惯在提供信息后忘记给出下一步引导）
- 同一缺陷类型是否出现了 2 次以上？（`defect-taxonomy.md` 的分类可作为起点）
- 能否抽象出一条可复用的规则？（例如："每条约束必须附带'否则'的后果描述"）

错误模式是面向**未来写作**的产出——修复当前载体是治标，识别并避免错误模式是治本。模式提取不是强制产出：简单载体的推演可能没有重复模式，此时本节记录"未发现重复模式"即可。

**评估维度表**（按载体类型推荐）：

| 载体 | 评估维度 |
|------|---------|
| 提示词/指令 | 因果方向清晰度、违规模式覆盖、自检可执行性、后果说服力、边界覆盖 |
| 文档/教程 | 入口明确性、术语一致性、步骤可跟踪性、缺失场景覆盖 |
| 交互流程（UI/CLI） | 首次可执行性、困惑点密度、放弃率预估、错误恢复路径 |
| API 设计 | 命名一致性、默认值合理性、错误信息可操作性、缺失 endpoint 覆盖 |
| 逻辑链路 | 控制流正确性、边界条件覆盖、状态一致性、资源生命周期、异常安全 |
| 计划文档 | 背景充分性、意图完整性、逆向排除度、步骤可判定性、粒度一致性、依赖可见性、边界清晰度、异常覆盖、执行策略充分性 |


## 推演者定位

推演的核心是站在评估者位置，模拟客体视角——不是变成客体。推演者需要同时维持两层观察：**内容表达层**（措辞是否准确、语义是否清晰）和**逻辑执行层**（按规则走下去得到什么结果）。每步自问"我现在是评估者还是客体"，不要滑入客体角色放弃对载体的判断。

这条原则在所有场景文档中成立，在提示词/指令集推演（`scenarios/prompt-instruction-rehearsal.md`）中尤为关键——读着读着就真的去执行了，是推演中最常见的滑落。保持评估者定位的同时尽量客观，是推演质量的前提。

## 执行策略

### 嵌入优于收网

推演不必积攒到最终一次性做。每完成一段时做一次短推演（只测刚完成的部分），比最后做一次全量推演更有效——缺陷发现得越早，修复成本越低。但阶段性推演只解决"有没有明显问题"，取代不了最终的全景推演（跨模块交互问题往往只在全景推演中暴露）。

## 示例：推演一个指令集章节

以下是一次真实的推演记录（内容已脱敏）。

```
客体：第一次接触工作流程的执行者
载体：操作规范文档中的「文档先行原则」章节
```

### 逐帧跟（节选）

读到 `[文档] → [代码]` 箭头图 → 执行者停顿了一拍。三个短句都指向同一件事。规则存入高优先级槽位。

读到"唯一合法动因" → 执行者建立了清晰的门控规则。如果修改代码的理由不是"文档说了不同的话"，就是违规。

读到三个典型案例 → 执行者的内心独白匹配到了自己以前的模式。常见的"顺便更新""统一补文档"被标记为违规。

读到"沉默的技术债务" + "主动误导下一次决策" → 威胁感知激活。不只是"过期"，是**主动伤害**。

读到自检问题 → 执行者获得一个可执行的门控：单一问题、二元答案。

### 边界刨

**场景：纯重构（行为不变）**
执行者决定拆模块 → 自检：「文档描述了我的目标状态吗？」→ 目标状态和现有文档一致 → "是" → 自检通过。合理。

**场景：文档不存在**
执行者要加功能但没有对应文档 → 自检失败 → 但不知道该创建在哪个目录、叫什么名字 → **问题发现**：缺少"找不到对应文档时怎么办"的指引。

**场景：文档与主 README 矛盾**
新原则说"文档是契约"，README 第 74 行说"以代码为准" → 执行者困惑 → **问题发现**：README 需要同步修复。

### 评估整理

**4a. 意图对照：**
- 意图 1："让执行者严格遵循文档先行" → 推演确认：箭头图 + 三重锁定有效传达 ✓
- 意图 2："覆盖常见违规场景" → 偏离：缺少"不知道改哪个文档"的引导 ✗
- 意图 3："提供可执行的自检手段" → 确认：单一问题二元答案 ✓

**4b-4c. 发现归类与严重程度：**

| 维度 | 实际效果 | 预期效果 | 缺陷类型 | 严重程度 |
|------|---------|---------|---------|---------|
| 因果方向清晰度 | 箭头图 + 永不反转 + 唯一合法动因，三重锁定 | 执行者建立清晰的门控规则 | — | — |
| 违规模式覆盖 | 三个典型案例覆盖了常见违规 | 应覆盖"不知道该改哪个文档"的边界场景 | 覆盖不完整 | 缺陷 |
| 自检可执行性 | 单一问题二元答案，不留模糊空间 | 执行者可自行判断是否违规 | — | — |
| 后果说服力 | "沉默技术债务" + "主动误导" | 执行者感受到威胁而非建议 | — | — |
| 边界覆盖 | README 第 74 行与新原则矛盾；缺文档不存在时的指引 | 边界场景有明确处理路径 | 信息不一致 + 覆盖不完整 | 阻塞 |

**4d. 修复优先级：**
1. 同步 README 第 74 行与新原则的矛盾（边界覆盖，阻塞级）
2. 补充"找不到对应文档时怎么办"的指引（边界覆盖，阻塞级）

**覆盖检查：** 五个维度均有记录，无遗漏维度。

## 场景特化参考

四步流程适用于所有载体类型，无需额外判断。以下常见载体类型另有特化文档，可在推演对应类型时作为参考，获取更具体的指导（客体定位调整、评估维度偏重、该载体特有的边界场景范本）：

- 推演目标为总体介绍文档，如项目文档、行动指南、方法教程等时，可阅读[文档/指南质量验证推演](scenarios/doc-guide-rehearsal.md)（单文档推演 + 全流程跨文档推演，五维度评估标准）
- 推演目标为设计方法论文档（读者按方法论执行设计，而非具体操作）时，可阅读[设计方法论文档验证推演](scenarios/design-doc-rehearsal.md)（四维验证框架：逻辑正确、线索清晰、前后一致、可复现深刻理解）
- 推演目标为多文件知识库（需跨文档决策判断）时，可阅读[多场景知识库验证推演](scenarios/knowledge-base-rehearsal.md)（多角色×多路径推演，适配决策树分支消费模式）
- 推演目标为提示词、系统指令或任务指令时，可阅读[提示词/指令集推演](scenarios/prompt-instruction-rehearsal.md)（双维度推演：内容表达层 + 逻辑执行层；委派推演机制）
- 推演目标为交互流程（UI/CLI/表单等操作链路）时，可阅读[交互流程推演](scenarios/interaction-rehearsal.md)（操作链路的首次可执行性、困惑点密度、放弃率预估维度）
- 推演目标为 API 接口契约时，可阅读[API 设计推演](scenarios/api-design-rehearsal.md)（命名一致性、默认值合理性、错误信息可操作性、缺失端点覆盖维度）
- 推演目标为逻辑链路（代码逻辑、规则流程等确定性执行路径）时，可阅读[逻辑链路推演](scenarios/logic-chain-rehearsal.md)（控制流正确性、边界条件覆盖、状态一致性等维度）
- 推演目标为实现计划、实施方案（告知执行者按指定步骤达成某目标）时，可阅读[计划文档推演](scenarios/plan-rehearsal.md)（执行路径完整性、依赖可见性、异常覆盖等 9 项评估维度）

**这些特化文档是提示，不是替代。推演的骨架始终来自本文件的四步流程。**
