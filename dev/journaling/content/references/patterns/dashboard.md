# Dashboard 设计模式

> 一种将 INDEX 分级组织、把多种领域（话题、专题、项目）的索引信息分层整理的方法。在笔记库内容庞杂时，有效降低 INDEX 的内容负担，并降低领域外信息对当前任务的干扰。

## 核心方法

设定领域后，为领域单独设置 dashboard 文档。dashboard 相当于一种"次级 INDEX"——定位和做法与 INDEX 类似，但覆盖范围是一个领域。dashboard 被其上级（INDEX）引导；INDEX 中不再直接呈现其内部内容。

这里的"领域"指话题、专题、项目等有明确边界的内容集合。dashboard 承载该领域的索引信息（条目指引、状态），INDEX 只保留到 dashboard 的引导——领域内部内容从 INDEX 中移出，INDEX 的负担随之下降，读到无关领域信息的概率也随之下降。

## 层级化与引导链路

INDEX 仍是笔记库的入口，其中引导至 dashboard，形成 dashboard 的加载路径。INDEX → dashboard，整个过程形成**渐进式索引内容披露**——每次读取只加载当前需要的层级，大幅降低读取负担。

在领域内，dashboard 和 INDEX 的定位相同，所以可参考 `design-index.md` 进行设计。dashboard 内部仍可细分领域，形成下一级 dashboard。虽然从定位上看天然允许多层级设计，但不建议设置过多层级——每多一层就多一次跳转，披露收益递减。

## 领域 vs 分类

领域化内容不等同于笔记文档分类——两者完全无关。将领域纳入笔记文件分类考量是可以的，但非必须：dashboard 模式天然支持**网状链接**具体笔记条目——比如一份知识笔记可以同时关联至两个领域（它的文件位置只有一个分类，但可以被多个 dashboard 链接）。

不一定所有的笔记都被"领域化"——领域只是集约某个专题内容，INDEX 中完全可以保留不属于任何领域（或任何已设领域）的零散笔记。也可以理解为：整个笔记库是一个"全局领域"。

## 从自然需求生长

dashboard 不是初始化预设——它从实际使用中生长出来：某个领域的内容多到 INDEX.md 无法清晰呈现时，为它建立领域索引页的需求自然出现，dashboard 随之产生。

生长的完整过程：需求出现（领域庞杂、INDEX 承载不下）→ 建立 dashboard → 随领域进展持续更新（内容与状态）→ 领域结束，不再更新，成为历史参考。整个过程由使用驱动，不由模式或模板驱动。

dashboard 与笔记条目文件之间没有双向绑定：dashboard 只是为条目的内容做"领域化组织"（通过链接指引），不占有条目——条目被某个 dashboard 链接，不意味着它依附于该领域。当领域消失时（项目结束、话题不再跟进），dashboard 随之消散（不再更新、成为历史参考），但具体笔记的去留独立判断——它可能有独立价值（经验、知识），保留在原分类继续被检索；也可能随领域一起归档。自然产生的领域自然地消散，条目的寿命由自身价值决定，不由所属领域的寿命决定。

模式不规定这个页面的名称——dashboard、领域 INDEX、项目面板都可以，名称由使用时自然决定。为了"用上这个模式"而建页面、为了"看起来规范"而强行叫 dashboard，是需求不存在时的生硬套用。

## 一种可能的做法

这是一种做法参考，不要生硬照搬。

### 规则设计

为笔记库增加这样的规则：

1. 新增分类 `[dashboard]`，所有 dashboard 文件存入此类别
2. INDEX 结构中设置 `[dashboard]` 板块，记录各个一级 dashboard 和简短说明

为笔记库增加这样的约定：

1. 展开论述各个领域的具体范畴
2. 编写完成后，依照上下文或印象，登记到对应的 dashboard 或 INDEX

### 呈现效果

**笔记库文件组织**：dashboard 文件集中存放于 dashboard 类别：

```
journal-root/
├── INDEX.md
├── dashboard/
│   ├── project-a.md
│   └── topic-b.md
└── 各领域条目按分类存放
```

**INDEX 中的效果**：协议声明后出现 `[dashboard]` 板块，每个一级 dashboard 一行（名称 + 简短说明 + 链接）；领域内部的具体条目不在 INDEX 中展开：

```
## 领域索引

- 项目 A：一句话状态 —— [dashboard](dashboard/project-a.md)
- 话题 B：一句话状态 —— [dashboard](dashboard/topic-b.md)
```
