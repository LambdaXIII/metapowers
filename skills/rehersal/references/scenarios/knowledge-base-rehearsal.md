# 多场景知识库验证推演
> 场景文档 — 载体符合时必读。按 `../rehearsal-guide.md` 的路由指引加载。


将全流程推演适配到知识库（含多文件决策树）的验证场景。适用于知识库重构后或新建后的完整性检查。

---

## 与全景推演的区别

全景推演（见 通用论述 `../rehearsal-guide.md`）假设载体是**线性工作流**（模块 A → 模块 B → 模块 C）。知识库的消费模式不同——接收方按**决策树分支**选择路径，而非线性阅读全部文件。

因此需要在全景推演基础上叠加 **多角色 × 多路径** 设计。

---

## 方法

### 设计角色矩阵

找 4-6 个典型使用场景。每个场景定义：
- **角色**：什么身份、什么知识水平、什么目标
- **路径**：在入口文档的决策树中走哪条分支、依次加载哪些参考文件

设计原则：
- 覆盖决策树的**每条主要分支**
- 至少 1 个场景是跨文件的（需要从文件 A 跳转到文件 B 才能完成目标）
- 至少 1 个场景是诊断/修复类的（执行者带着问题来，需要先定位再修复）
- 至少 1 个边界场景（信息缺失、误解、跳过某步）


### 1. 清空（每场景执行前）

参照通用论述的「作者视角」和「清空」步骤。**知识库推演中，每切换一个场景就需要重新清空**——因为不同场景的执行者身份不同：

1. **回看作者视角**：确认你为当前场景已写下「这个场景的执行者是谁、期望达到什么效果」。
2. **设定阅读身份**：用当前场景的角色描述精确设定你的身份——使用角色矩阵中为该场景定义的身份。
3. **显式清空**：扔掉知识库作者的知识。不知道参考文件之间的依赖关系、不知道为什么某个文件放在这个目录、不知道术语 A 和术语 B 是同一概念的替代名。只带入口文档和该角色的初始状态进入。
### 2. 逐场景推演

对每个角色，走完整链路：

```
入口文档（主文件）
 ↓ 读到决策树，选择分支
 ↓
参考文件 A（加载、阅读）
 ↓ [交叉引用应该在此触发]
 ↓
参考文件 B（跳转）
 ↓
模板目录（复制使用）
```

记录每步的停顿、误解、卡死。

**重点检查两类信号：**

| 信号 | 含义 |
|------|------|
| "这里需要跳到 X，但文档没告诉我" | 交叉引用断裂 |
| "这个概念在文件 A 和文件 B 用了不同名字" | 术语不一致 |
| "我读完了但不知道下一步该做什么" | 缺少回链或退出指引 |
| "这两段话在说同一件事，但我不知道哪个是权威" | 内容重叠无分工 |

### 3. 边界刨

| 异常场景 | 检查目标 |
|---------|---------|
| 跳过某个参考文件直接到下一步 | 承载"跳过的文件"中的关键知识的后续文件还能站住吗？ |
| 从中间进入（直接从参考文件开始，没读主入口） | 参考文件自包含吗？还是依赖主入口的上下文？ |
| 误解关键术语 | 术语是否在首次出现时有定义？跨文件是否一致？ |
| 参考文件和模板同时存在同一主题 | 分工明确吗？执行者知道先读哪个吗？ |

### 4. 打分

推荐五维度 ★1-5：

| 维度 | 含义 |
|------|------|
| 全流程可执行性 | 从入口到完成目标，按指引走能完整走通吗？ |
| 模块流转清晰度 | 每个文件的输入/输出/交叉引用清晰吗？ |
| 术语全局统一 | 关键概念在所有文件中名称一致、定义一致吗？ |
| 覆盖完整性 | 决策树的每条分支都有足够的 depth 支撑吗？ |
| 异常容错 | 跳步、误解、从中间进入时能 recover 吗？ |

## 示例

某设计方法论文档的 10 场景推演：

| # | 场景 | 角色 | 路径 |
|---|------|------|------|
| 1 | 从零开始设计 | 中级工程师，第一次使用这套方法论 | 入口 → 结构设计 → 内容写作 → 工具设计 → 模板 |
| 2 | 诊断行为异常 | 维护者，产出上线后不按预期工作 | 入口 → 反模式诊断 → 定位问题 → 对应参考 |
| 3 | 安全审查 | 审查者，上线前审核 | 入口 → 安全相关 → 运维相关 |
| 4 | 特定模型优化 | 高级开发者，为特定推理模型定制 | 入口 → 模型特定 → 推理优化 |
| 5 | 跨环境迁移 | 团队负责人，从环境 A 迁移到环境 B | 入口 → 模型特定 → 内容写作 |

**发现 12 个缺陷**，其中 8 个有效（4 个结构 + 4 个方法论），4 个因超出方法论文档自身范畴而移除。

**关键教训**：
- 知识库推演中，"交叉引用断裂"是最常见的缺陷类型——比全景推演更高发，因为参考文件独立性强但互联性弱。
- 参考文件和模板的内容重叠是一个常见问题类型，全景推演不会覆盖。

## 多轮迭代修复验证

单轮推演只能发现问题，不能验证修复是否引入了新问题。对于重构幅度大或缺陷数量多的知识库，应采用多轮验证：

### 轮次角色

| 轮次 | 角色 | 测试用例类型 |
|------|------|-------------|
| **Round 1** | 发现基线 | 全新场景，覆盖所有决策树分支 |
| **Round 2** | 验证修复 + 暴露新问题 | 60% 回归（重新走 Round 1 中最弱场景）+ 40% 新场景（覆盖本轮新增特性的验证点） |
| **Round 3+** | 收敛确认 | 仅回归修复项 + 1-2 个新增边界场景 |

### 回归测试用例设计

回归场景的核心要求：**与原始场景同角色、同路径，但验证点全量更换为本轮修复点。**

例如 Round 1 S10（跳过入口直接进入参考文件）得 17/25——Round 2 S11（同角色同路径）验证了文件自标识、收束区块、替代路径等 5 个本轮修复点，得 24/25（+41%）。这是判断修复是否生效的唯一可靠信号。

### 得分追踪

跨轮次对比同一维度的得分变化：

```
Round 1 平均: 3.74/5（异常容错 2.9/5 最弱）
Round 2 平均: 4.52/5（异常容错 3.6/5，+24%）
Round 3 平均: 4.53/5（持平，新增缺陷全为外观级）
```

**收敛信号**：当两轮之间的平均分变化 < 0.1 且无新增中/高优先级缺陷时，可以停止迭代。继续修复低优先级缺陷的边际收益递减。

### 何时停止

- ✅ 上一轮所有高/中优先级缺陷已关闭
- ✅ 本轮新发现缺陷全为低优先级或外观级
- ✅ 平均分 ≥ 4.3/5（★★★★½）
- 三个条件同时满足 → 停止迭代，将剩余低优先级缺陷记录到已知限制中
