# Rehearsal — 设计锚定文档

## 本文档的定位

这是 rehearsal 技能的**设计锚定文档**。它的读者是接手维护这个技能的开发者——不是在寻找技能使用说明（那在 SKILL.md 和 references/ 中），而是在理解：

- 这个技能为什么这样设计
- 修改时哪些约束不可破坏
- 新增功能时如何保持一致性

本文档记录**设计决策及其理由**。操作日志（改了哪个文件、删了什么内容）属于 CHANGELOG。技能使用说明属于 SKILL.md 和 references/。

与相关文档的边界：
- **SKILL.md**：技能入口——触发条件 + 核心指令。不展开设计理由。
- **CHANGELOG.md**：逻辑变更记录——按版本号组织。不记录设计理由。
- **AGENTS.md**：项目规范——定义 SKILL-DESIGN 的格式要求。不包含具体技能的设计。

## 起源

本技能源自 Hermes 生态中的 `tuiyan` 技能（中文名"推演"）。原技能诞生于为 Agent 提示词和文档做质量验证的实际需求——作者无法感知自己写的文档在第一次阅读者眼中是什么样子。推演方法被证明有效，但原技能深度绑定了 Hermes 项目生态（delegate_task、L1/L2/L3 层次结构、Skill 概念等）。

## 命名理由

**rehearsal**（彩排/预演）：

- 跨语言可读：英语中 rehearsal 不带有任何特定行业或框架的联想
- 跨载体通用：可以用于文档、代码、UI、API、会议脚本、教学大纲等任何交付物
- 本质贴合：rehearsal 的核心是"在正式演出前走一遍流程，找出问题"
- 动作感强：作为技能名易于触发，读者能直观理解其功能

候选排除：
- `first-contact-simulation` — 过长，且过于强调"首次"忽略了推演也适用于非首次场景
- `perspective-audit` — 过于抽象，不易理解
- `dry-run` — 在工程语境中已有特定含义（测试不含实际效果的代码运行），易混淆

## 设计意图

这个技能解决什么问题？**任何人在生产"给别人看/用的东西"时都无法感知接收方的第一视角体验。** 作者知道自己想表达什么、目的是什么，因此看不到"不知道目的的人会在哪里卡住"。

rehearsal 就是强制切除"作者知识"的方法——让作者或评估者在脑子模拟一次接收方的首次接触→理解→决策过程。

## 关键架构决策

### 1. 三元素 vs 四步流程

推演方法的核心是**两个层次的拆分**：静态的三元素（客体、载体、链路）定义推演的对象和范围，动态的四步流程（清空、逐帧跟、边界刨、打分）定义执行步骤。这种两层次拆分是必要的：

- 三元素是"推演前必须明确的三个问题"——如果不知道模拟谁的视角、什么载体、什么链路，推演无法开始
- 四步流程是"推演中怎么操作"——一旦三元素明确了，如何执行

**不变量**：边界范围约束——每个边界条件必须在载体的自身责任范围内。不测试上游阶段或依赖已经保证的条件。有效的边界是载体自身可以预料并处理的合理变化。超出责任范围的边界暴露的是上游问题，不是载体的问题。

### 2. 参考文件三层组织 + 目录分组

参考文件按三级组织，阅读逻辑由"必读 → 载体符合时必读 → 按需参考"驱动：

| 级别 | 阅读策略 | 内容定位 | 举例 |
|------|---------|---------|------|
| **必读入口** | 入口，必读 | 方法的完整阐述（原理、三元素、四步流程、原则、局限），末尾按载体类型路由到对应场景文档 | `rehearsal-guide.md` |
| **场景文档** | **载体符合时必读** | 针对一个具体目标对象（载体类型）的推演操作指导。聚焦"在这个场景下具体怎么做" | `doc-guide-rehearsal.md` |
| **补充参考** | **按需参考** | 不限场景的小块知识（缺陷分类法、批量执行模式等），被通用论述或场景文档显式引用时加载 | `defect-taxonomy.md` |

SKILL.md 的核心指令单一：**阅读通用论述并按照其中的流程进行推演**。不展开方法细节，不承载操作指导。

**目录分组**（v1.3.0 引入）：场景文档和补充参考在物理目录上分离——`references/scenarios/` 和 `references/supplementary/`。分目而非平铺的理由：两者触发机制不同（载体匹配 vs 情境加载），物理隔离防止路由混乱。未来新增文件时，按触发机制判断归属——不按主题、不按编号。这两个目录不得合并。

**命名约定**：
- 必读入口 = `rehearsal-guide.md`
- 场景文档 = `<target-object>-rehearsal.md`（如 `doc-guide-rehearsal.md`）
- 补充参考按内容意取名，无需编号前缀

**动态扩展机制**：
- 场景文档和补充参考可以随时新增。新增场景文档后同步在通用论述末尾的路由表中注册
- 移除一个场景文档或补充参考不影响其他文件的完整性
- 新增场景文档或补充参考不需要修改 SKILL.md——SKILL.md 只指向通用论述，通用论述管理路由

**不变量**：
- 所有场景文档的操作方法必须服从通用论述定义的四步流程。场景文档不发明新的推演步骤，只在步骤内补充本载体的特殊信号和检查重点
- 通用论述自身必须独立站住——不假设读者已读过任何其他文件。场景文档假设读者已读过通用论述（载体符合时在路由指引下加载）。补充参考假设读者已读过对应的通用论述/场景文档
- 通用论述末尾必须维护一张路由表，将任务分流到场景文档。新增场景文档必须同步更新路由表。移除场景文档必须移除路由项
- 层级通过目录结构体现，不是文件名。文件名中不出现级别前缀，避免重命名代价
- 场景文档不包含跨场景的通用知识——引用补充参考，不重复补充参考
- 补充参考文件自身要独立站住，但假设读者已在上下文中知道推演方法

### 3. 嵌入优于收网

将推演拆成阶段性进行（每完成一段/一章就做一次短推演）比一次性做完整推演更高效。但阶段性推演不能替代最终的全景推演。这个原则来自实践经验——缺陷发现得越早，修复成本越低；但跨模块交互的问题只在全景推演中暴露。

### 4. 场景文档：载体针对性的执行指导

场景文档解决一个特定目标对象（文档、知识库、UI 流程等）的推演应用。每个载体类型的操作细节差异大，不适合合并或嵌入 SKILL.md。SKILL.md（极简简介 + 触发条件）和通用论述提供方法基础，场景文档在需要时加载——不占主上下文。

这延续了原版"references 是具体化延伸"的设计，但在新体系下明确了场景文档只装"载体针对性的执行操作"，与通用论述（通用方法全貌）和补充参考（跨场景知识）形成三级分层。

### 5. 场景文档的四种新增

Phase 2 填补 Phase 1 重组后通用论述路由表与打分维度表之间的缺口。四个新增场景文档按客体系分组：

- prompt-instruction-rehearsal：唯一需要同时维持内容表达层和逻辑执行层双重视角的载体。引入「推演者的双重定位」原则——不要变成作者也不要变成模型，保持在中间评估通信的观察者位置。
- interaction-rehearsal：合并 UI 和 CLI 为统一的交互流程推演。共享的步骤（清空/逐帧跟/边界刨/打分）保持一致，在逐帧跟和边界刨中按模式（UI/CLI）分支补充特定信号。
- api-design-rehearsal：严格限定在接口契约层面——不涉及实现细节。引入「API 边界」节明确在范围内/外的标准。新增「组合流畅性」「契约完整性」两个维度。
- logic-chain-rehearsal：泛化「代码运行时逻辑」为「任何预定逻辑流程」。是唯一一个客体非「人」的场景文档——客体是执行引擎（计算机/解释器/规则引擎），不需要模拟人物心理，只需模拟机械执行。

不变量的保持：每个新场景文档的四步流程节仍在通用论述框架内填充，不发明新的推演步骤。通用论述路由表从 3 个扩展到 7 个。通用论述打分维度表新增逻辑链路行；UI 流程泛化为交互流程。

### 6. L0/L1/L2 是开发速记，不在技能中呈现

在开发讨论中使用 L0/L1/L2 作为内部速记——指代明确、沟通高效。但**这些代号不得出现在技能内容（`content/`）中**。

理由：技能的运行时读者是 agent。agent 看到 L0/L1/L2 时不理解它们指代什么——不传达语义，只会造成困惑。技能内容中使用自然语言替代：

- L0 → 通用论述、必读入口
- L1 → 场景文档
- L2 → 补充参考

目录结构本身已经表达了分层（`references/` > `scenarios/` / `supplementary/`），不再需要代号前缀。如果未来在 `content/` 中发现 L0/L1/L2 代号——那是 bug，修复它。

此原则已记录在通用论述的「维护者须知」节中，确保维护该技能的开发者不会误将速记泄漏到技能内容。

### 7. 打分维度的动态选择

不固定一套打分维度，而是根据载体类型推荐不同的维度集。因为"文档好不好"和"UI 流不流畅"的评价标准差异太大，强制统一维度会导致不相关的评价。

**不变量**：打分维度表是活的——随着实践积累，应该允许添加新的推荐维度组合。但推荐维度已经过广泛验证，不应轻易移除。新增维度应先在通用论述中定义，场景文档可扩展本场景的特殊维度。

## 措辞风格约定

- 使用"接收方"（recipient）而非"用户"（user）——后者在技术语境中有专指（最终用户），而推演的客体可以是 agent、读者、学生、顾客等
- 缺陷分类文件（`defect-taxonomy.md`）作为补充参考，应该被视为活的分类体系：随着在不同载体类型上的实践，可以扩展缺陷类别。但扩展时要注意不要引入"因为载体差异导致的伪类别"
- 更新各类文件时，只在各自范围内修改。不因补充参考的改动而修改通用论述或场景文档（除非是路由表或引用提示变更）
