# multi-ask

使用者（agent）通过这个技能把一批已成形的待决问题组装成一份**问卷**（markdown 文档，含论述段落与问题块），向用户一次性批量征集裁决；用户在脚本渲染的交互页上作答提交后，产出一份**答卷**（append-only 的 JSON 记录），agent 读取答卷继续推进。技能存在的理由是：在对话里逐题追问，用户每答一句都要重新拼一次背景，回答的质量取决于背景是否还在手边；问卷把充分论述与问题一起呈上，用户按自己的节奏读完、答完，一次交回。

## 技能扮演什么角色

### 技能把用户当作裁决者而非信息源

技能只把用户裁决物——偏好、价值取舍、影响用户且不可逆的选择、只有用户知道的事实——收进问卷；agent 凭现有信息可裁定的自行裁定，可查证的先查证，不得把可裁决项打包甩给用户。这条约束划定了技能的适用边界：优化「向用户征集裁决」的过程，不优化「向用户转嫁判断责任」的行为。

## 技能定死了什么

### 技能以单文件脚本为核心资产

技能的核心资产是一个本地脚本：校验问卷、渲染交互页、收集提交、产出答卷、拼装回读。除这个脚本外，技能不构建任何流程机制或工件模板。agent 应当能够凭技能内容完成出题、运行脚本、读回答卷的完整闭环。

### 问答的价值来自论述充分，而不是题量

每道题之前交代作出裁决所需的背景：约束是什么、每条路的代价落在哪儿、为什么这件事只能由用户定。论述写足是本技能的核心，用户读完一题即可作答，也可反驳。题量由待决点决定，不为「少开一次问卷」而并入尚未成形的问题。agent 应当能够判断一道题现在是否该问，以及它的论述是否够用。

### 出题载体与题型定死为最小集合

出题载体定死为 markdown 问卷，问题块用语言标记 fenced 块表达，无脚本时降级为普通可读文本；题型收敛为单选、多选、判断三种，零选项即开放题。自由输入与整卷总评不占块结构，由渲染层恒定提供。格式契约完整记在单份参考文档里，agent 按入口路由取到它即可写出可校验的问卷。

### 问卷与答卷分离，各为单一权威

问卷是 agent 所有的论述载体，单轮内不可变，承载全部背景论述与题目；题目文本的唯一权威在问卷，答卷不回显题干。答卷只增不改，同一份问卷可回收多份答卷。agent 应当能够在不读问卷的情况下凭答卷定位题目、在不读答卷的情况下凭问卷重现全部问题。

### 校验先于交互，错误反馈必须可执行

脚本在开放交互页前完成静态校验，不通过即终止并逐条反馈；每条错误携带修复指引，告诉 agent 怎么改，而非仅报错。校验的覆盖面（结构规则、id 作用域、标签白名单等）由脚本用法的参考文档定死；校验查不出来的内容规则，同处声明。agent 应当能够仅凭错误反馈完成修正，无需猜测判定标准。

### 拼装答卷是现算的派生视图

脚本提供拼装能力：读答卷、按其中的问卷引用读问卷、将问题块替换为作答结果、输出完整文档。拼装视图按需生成、不落存储，服务人工审读与 agent 跨会话回读。

### 脚本以零安装依赖交付

脚本以单一文件交付，仅用宿主通用运行时的标准库，不依赖网络服务与包管理器安装，使技能满足仓库的通用性门槛：装上即用，不绑定特定平台或生态。

## 技能怎么被加载

### 技能以双入口加载

技能同时覆盖两种触发：agent 在攒起多个待决问题时自主加载，以及用户显式要求批量提问时加载。description 须同时表达「向用户批量征集裁决」的语义，并与「替用户向第三方征集知识」的问卷类技能划清边界。

## 技能正文怎么写

### 入口只写是什么、为什么与参考路由

SKILL.md 只写三节：技能是什么、为什么需要它、按情形读哪份参考文档；格式契约、脚本用法、问题的组织与写法全部后置到 `references/`，由入口路由到达。agent 应当读完入口即知道自己该打开哪份参考，并据参考写出结构合法且组织得当的问卷。

### 方法参考只给判断，不立细则

组织问题与写题的参考文档只收录有真实案例支撑的判断（如依赖链问题不进同一批、上下文压缩到决策相关、判断题文本须为完整命题、单选项问题应改写为判断题或多选题），写成判据与自问句，不写成规范或限制；取舍标准是「agent 仅凭文字能否避免犯错」，不收常识。

### 操作文档写清边界与失败形态

格式契约与脚本用法只记可执行的事实，且每条格式规则都要交代写错之后的形态：报错、被静默按正文处理，还是不进入答卷。运行前提（在哪执行、谁来操作、进程活多久）写进文档，不默认读者与作者处于同一环境。
