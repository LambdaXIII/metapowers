# 技能开放标准规范册（standards）

> 本文档是 skill-master 技能 general 分册的规范册：中立转述技能开放标准
> （Open Agent Skills）对技能包的格式规定——目录结构、frontmatter 约束、
> 渐进式披露与校验。读者前提：默认已读 SKILL.md 的前提节《什么是一个好的
> 技能》。本册只回答「一个目录怎样打包才是可被加载器正确识别的技能包」，
> 不写任何仓库内部约定（发布流程、分支策略等由运行环境与仓库规则提供），
> 也不写组织与编写方法——文本类编写方法在 ../documents/ 各册、脚本类在
> ../scripts/ 各册、description 的措辞方法论见同册 disclosure.md。

## 定位

设计、修改、审查三种工作都要碰同一个底线问题：技能包按什么格式打包，加载器
与分发渠道才认。标准的规定是不可协商的部分——不满足就不是合法技能包；底线
之上如何组织、如何写得准，是各工作论述的发挥空间，本册不越界。

- **中立转述，只立基线**：本册内容是外部开放标准的转述，不是本技能或本
  仓库的自创约定。仓库确实有追加约束（比如 metadata 必填子字段、目录树从
  技能根展示），那些以仓库与运行环境规则为权威，与本册的基线分开维护——
  一份技能包文档要同时满足两套约束，但两套约束各有出处，读者不必在本册
  找仓库追加项。
- **覆盖与不覆盖**：目录、字段、加载模型、可机械校验的项是本册内容；
  「这段正文按什么形态写」在 documents/、scripts/ 各编写册；「description
  怎么措辞才命中、命名怎么定」在 disclosure.md。本册只转述字段约束本身，
  例如 description 有多长、必须含触发词，至于触发词怎么选不是标准问题。
- **打包与编写两轴正交**：一个成品放哪个目录（本册 + 运行环境目录约定）
  与它按什么形态编写（documents/、scripts/ 各册）是两回事。工作流文档
  即便作为 asset 打包，其编写方法仍按工作流册，不因放置位置改变——按打包
  位置找编写方法是常见错路。

## 目录结构

- 技能是一个目录，目录名与 frontmatter 的 `name` 字段一致，加载器按目录
  发现技能。最小合法结构只有一个文件：技能根的 `SKILL.md`。
- 标准允许的可选支撑目录：

| 目录 | 存放什么 | 标准要求 |
|---|---|---|
| `scripts/` | 可执行代码 | 自包含或显式写出依赖；含友好报错；优雅处理边界情形 |
| `references/` | 按需阅读的文档 | 每份聚焦单一主题、尽量小 |
| `assets/` | 静态资源（模板、图片、查表数据） | 供查阅的客观资料，不是主阅读路径 |

- `templates/`、`examples/` 等扩展目录不在标准统一清单里，是否被识别是
  运行环境的事：环境不认识的目录名等于不存在，其内容永远不会被加载。
  目录名以目标环境约定为准，内容放哪才是设计者的组织决策——先确认环境
  认哪些目录名，再谈内容归属。

## frontmatter 约束

SKILL.md 由 YAML frontmatter 与 Markdown 正文组成。标准只约束 frontmatter；
正文写任何能帮助 agent 完成任务的内容都不受格式限制。

| 字段 | 必须 | 约束 |
|---|---|---|
| `name` | 是 | 1–64 字符；仅小写字母、数字、连字符；不得以连字符开头或结尾；不得含连续连字符；须等于父目录名 |
| `description` | 是 | 非空且不超过 1024 字符；同时说明技能做什么与何时用；含帮助匹配任务的触发词 |
| `license` | 否 | 许可证名，或对技能包内许可证文件的引用 |
| `compatibility` | 否 | 不超过 500 字符；环境需求（目标产品、系统包、网络等）；多数技能不需要 |
| `metadata` | 否 | 字符串键值映射；容纳标准未定义的附加属性（版本、作者等） |
| `allowed-tools` | 否 | 空格分隔的预批准工具列表；实验性，实现间支持度不一 |

- `name` 与目录名双向一致的含义：技能名同时是加载器标识与用户的称呼核心，
  改名牵动目录、字段与文档引用多处——技能交付后改名是结构性变更，不是
  字段编辑，所以命名在写 description 之前就应定稳。
- `description` 的「含触发词」是字段层面的要求；触发词怎么选、写多少是
  disclosure.md 的方法论。两册分工：标准规定字段必须有什么，披露论述规定
  措辞怎么命中。
- 标准没有定义的附加属性走 `metadata`，标准不禁止——前提是加载器不依赖
  这些属性做识别，识别只看 `name` 与 `description`。

## 渐进式披露

标准按上下文成本把技能内容分成三层，组织必须与加载行为对齐：

1. **元数据层**：全部已发现技能的 `name` + `description` 在会话期常驻，
   是所有技能常驻上下文的全部——匹配与选择只发生在这层。
2. **指令层**：技能被命中后，SKILL.md 正文一次性全量加载。
3. **资源层**：references/、scripts/、assets/ 等被链接的文件需要时才读。

- 三层的成本形态不同：常驻层每个 token 全程付费，资源层每个字节只在真正
  需要时付费。组织方向随之确定——匹配信号留在元数据，决策依据放 SKILL.md，
  长论述后置到资源层，按需读取。
- 规模指引（标准的建议而非硬限）：SKILL.md 正文不超过约 5000 tokens、500
  行；支撑文件每份聚焦单一主题、尽量小——文件越小，按需读取时浪费越少。
- 文件引用纪律：技能内引用一律从技能根用相对路径写；引用深度保持一层
  （SKILL.md → 支撑文件），避免深层引用链。每多一层链就多一次「要不要
  追读」的决策和一个断链点，一层深度保证任何内容从 SKILL.md 出发一跳可达。

## 校验

- 结构合规是机械问题，可检查项有三类，都不依赖主观判断：
  - **frontmatter 完整性**：必填字段齐全，`name` 满足命名约定且与目录名
    一致；
  - **引用无断链**：正文指向技能内文件的相对路径，其目标确实存在；
  - **目录合法**：技能内只出现标准允许（或被目标环境识别）的目录名。
- 标准生态提供官方校验器，机械检查 frontmatter 合法性与命名约定——交付前
  跑机器校验，不靠自觉：设计过程靠判断，越接近交付越该让机器兜底。
- 断链的失效形态是静默的：技能被加载后，指向不存在文件的引用让该部分
  知识在需要时不可达，且作者收不到任何报错信号——机器校验是在交付前
  发现它的可靠手段。
