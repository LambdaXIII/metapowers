# 让技能被正确命中

技能被命中之前，agent 看不到它的正文——手里只有 `name` 与 `description` 这两段常驻文本。这两段加上技能名，构成技能的**披露**：它向加载器与用户呈现自己的方式。正文质量决定加载之后好不好用，披露决定会不会被加载、被谁加载。

这一册讲披露背后的机制，以及由机制推出来的判据。判据怎么落到一个具体的 `description` 上、定稿流程与回归怎么跑，见[写入口文件](../documents/skill-md-writing.md)；字段层面的长度与必含内容见[让技能包合规](standards.md)。

读这一册的时机：判断某个词该留还是该删、决定这个技能要不要交给模型自主触发、定技能名、或找出一个技能的问题时查它的触发面。

## 加载器实际怎么工作

以下三条是机制事实，触发设计的所有推论都建立在它们之上：

- **全量常驻**：所有已发现技能的 `name` + `description` 在会话期整体驻留上下文。因此 `description` 里每个词都是净成本——全程占窗口，全程参与与其他技能的相互遮蔽。方法论展开、流程清单、能力罗列都不属于这一层。
- **纯语义判断，无检索兜底**：命中是模型拿 `description` 与当前任务做语义匹配的结果，没有向量检索、没有关键词索引兜底。判断质量取决于 `description` 是否「有意义」，选择时它是模型唯一可见的技能接口。
- **选择在全部候选之间同时进行**：某个技能的词与相邻技能重叠越多，无关任务越容易按表面相似选中它。宽泛词的成本不只属于自己——它抬高相邻技能的误选率。

一项针对两百余个技能库的退化研究发现，技能库从少量扩到两百个，任务通过率最多下降两成；把退化拆成「选错技能」与「上下文膨胀」两个机制后，**选错占退化近七成，是唯一统计显著项，上下文膨胀与噪声不可区分**。机制解释正好对上上面的第三条：选错技能会把「表面合理但错误」的推理注入执行流，且被当作权威使用——不像工具调用错了会报错，这个错误无声。

推论：披露的目标不是「短」，是「精准」——正匹配信号足、与相邻技能区分度高、常驻成本小，三者同时成立。

## 可见性决策先于措辞

- 先在环境层面决定这个技能要不要交给模型自主触发。需要模型自主到达（用户不会点名它）、或需要被其他技能引用，才值得常驻；只会被手动调用的技能，部分运行环境支持把它从模型视野剥离（`disable-model-invocation` 一类机制），代价是调用方得记得它存在。两种负载是不同货币：常驻付的是每轮上下文税，剥离付的是调用方的记忆税。
- 顺序不能颠倒：先定可见性，再写 `description`。被剥离的技能，`description` 是给人看的一句话摘要，不需要触发动词与匹配面；常驻技能才适用本册下面所有方法。
- 技能堆积到调用方记不住时，用一个路由技能（自身也可剥离）命名其他技能及各自触发时机，把「记住 N 个技能」降成「记住 1 个入口」，代价是多一跳转发。

## 逐词判断：正匹配信号 vs 遮蔽源

写 `description` 时对每个词问一句：**它是正匹配信号，还是遮蔽源？** 这两类的处置方向相反，判错方向的代价也不对称。

**正匹配信号**（保留，删了才伤匹配）：

- **核心名的中英双面** —— 用户可能用中文名或英文名指代同一件事，双名各占一条匹配通道；缺一面，该语言侧的触发路径等于失明。
- **贴近用户说法的触发动词** —— 用户首话怎么说，这里就怎么写。作者完成时态（「写完」「已生成」）不贴近任何人的提问用语；口语化的职责动词（「验一下」「看看对不对」「走一遍」）与语义判断的相关性最高。
- **一句自然的 when-to-use** —— 用完整句子说清「什么情形下该用」，让模型判断当前任务是否落在这个场景里。

**遮蔽源**（收敛，删了是安全收益）：

- **宽泛适用面声明**（「任何涉及 X 的场景均可使用」）—— 与相邻技能大面积重叠，只贡献误选。
- **方法论名词**（阶段名、框架名、流程行话）—— 用户不这么说话，同领域的技能往往也这么宣称，只有遮蔽贡献没有命中贡献。
- **触发词穷举** —— 罗列几十个近义动词，边际命中收益趋零，却实打实地叠加重叠面与常驻成本。

**安全边界**：退化风险只存在于删掉正匹配信号。拿不准一个词属于哪类，问「用户或 agent 会自然说出它吗」——会，是信号；不会，是作者行话。

## 两条触发路径

- 命中来自两条路，`description` 必须同时给两条留信号：**用户路径**（用户首话点名技能、说出职责动词、描述场景）与 **agent 路径**（agent 执行中自问「现在该不该动用这类职责」，典型是交付物完成后的自我检查）。
- 只覆盖一条是最常见的漏触发形态。实证案例：某技能的触发场景全部以「写完 X 之后」开头，预设产出已就绪，结果 agent 交付后自问的那一刻无词可呼应，用户明说技能名也不触发。
- 检验方法：把 `description` 里的触发动词分两组列出来，一组归属用户会说的话，一组归属 agent 会自问的话。任一为空，就存在一整条漏掉的路径。

## 反向条件最小化

- 反向条件（何时不使用）对命中面没有贡献，还有反作用：核心词出现在「不使用」的语境里，语义命中也会被带偏判负。把技能名写进反向句，等于亲手把命中信号改成拒绝信号——有技能因此出现「用户明说技能名仍不触发」。
- `description` 里至多保留一句反向条件，选最关键的那一条误触发场景；完整的合触发 / 不合触发 / 边界判定放进 `SKILL.md` 正文——命中之后才加载，不占匹配面。

## 不误指向

- 不指向不存在的独立技能。`references/` 下的文件不是技能，不能被加载器加载；写成「详见 XX 技能」，agent 会去找另一个技能，从而漏触发本技能——这是反向误导，比不写指针更糟。
- 给读者指路时给同一技能内的正文位置或功能描述。同样原则适用于 `description`：它声明的能力必须是技能真实提供的，命中后兑现不了的声明与遮蔽是同一种病。
- 点名**真实存在**的相邻技能不在此列，反而是有用的边界信息：写清「把技能文字整理成给人读的文档归另一个技能」能让两边的调用者各就各位。判断标准是那个名字能不能被加载器真的加载。

## 命名

- 技能名是披露的第三面：目录名、`name` 字段、正文称呼共用同一个核心名，兼作加载器标识与用户称呼。改名要三处同步并动摇用户习惯，涟漪比任何正文编辑都大——命名当作身份决定处理，先于 `description` 措辞稳定下来。
- 官方指南推荐动名词形式（`processing-pdfs`）或名词短语，避免 `helper` / `utils` / `tools` 这类无内容指向的词，也避免同一技能库内命名模式不一致。理由是可引用性：命名模式一致时，名字本身能预告技能做什么。字段级约束见[让技能包合规](standards.md)。
