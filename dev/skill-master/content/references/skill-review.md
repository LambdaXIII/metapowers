# 技能审查（skill-review）

> 本文档是 skill-master 技能的审查工作论述：给定一个技能成品，产出质量判定。
> 读者默认已读 SKILL.md 的前提部分；本册只写审查这一件事——两种输入形态、七
> 个审查维度、判定与产出的纪律。审查只读不修，发现的问题交给修改工作执行；
> 它与验证的分工在开篇展开。

## 定位与边界

审查工作回答一个问题：这个技能写得对不对。判定围绕两套依据——技能自己的承
诺（它声明的定位、边界与每条约束）与通用标准（内容质量四标准、开放标准的
结构要求）。注意方向：审查的对象是文字承载的判断依据与结构，不是运行时的
行为——技能是文档，加载后 agent 的行为表现是文字质量的下游，行为不对往往是
文字不对的征兆，这条线索归症状排查形态。

审查只读不修。发现问题不代为修复，修复转修改工作。机制：审查与修改是两种
注意模式——审查需要全局逐维扫过，修改需要局部逐处处理；看到问题就动手，剩
下的面就没人扫了，产出也从「完整的问题图景」退化成「修到一半的补丁」。审查的产
出是问题清单，不是修改后的文件。

与验证的分工各管一问：审查判「写得对不对」，验证判「零上下文用不用得起」。验证
的做法是让一个没有上下文的 agent 只凭技能文档走一遍目标操作、收集卡点，它查
的是「写全了没有」；审查逐维读文字，查的是「写对了没有」。验证发现的卡点，常是
审查维度里某个失守的具体表现，反过来作为审查的输入。

审查判定需要锚点：一处内容算不算缺陷，先对照技能的设计意图再判。设计意图
的落点是技能的配套设计文档（存在的话），或 SKILL.md 自己声明的定位——技能
明确说「不管什么」的范围里没做，不是缺陷；宣称的承诺没兑现，才是。没有锚点的
审查，输出的是审查者自己的口味。

## 两种输入形态

审查有两条入口。第一条是全量评判：给定一个技能，按七个维度过一遍，输出整
体的质量判定。它用于交付前体检、重大改动后的复查、或周期性维护——没有具体
症状，但要回答「这个技能现在到底怎么样」。

第二条是症状排查：从「行为与预期不符」倒推根因。技能的行为是文字驱动的，行为
不对通常是写得不对的表现——某个宣称没被兑现、某处路由漏了、某段判据误导了
动作。排查的走法：锁定症状（什么输入、期望什么、实际得到什么）→ 沿触发链
追——description 的宣称 → SKILL.md 的路由 → 具体论述段的依据——追到可疑文
字 → 回到审查维度给根因定性。排查的产出是定位与依据，不是补丁：定位到根因
后转修改工作执行，修复本属修改。

两条形态共用同一组审查维度，只是走法不同：全量评判按维度过一遍，撒网找问
题；症状排查先锁症状再沿链追根，最后用维度给根因定性。场景：用户报告「照技
能说明操作，第二步说的判据根本没法检查」——这是症状；沿文档链追到第二步所在
的小节，发现该处用了主观模糊词而没有可检查的判据，归入零歧义维度定性，输
出定位后转修改。

## 审查维度

七个维度构成一张完整的检查面。它们不是串行步骤，而是走查时心里要过的七盏
灯；每盏灯亮起，都要能指出具体位置与判据。

**合规**：结构与元信息是否符合开放标准——该有的文件在不在、frontmatter 字
段全不全、披露是否按层渐进、引用是否一层深；可机械检查的细项见
general/standards.md。为什么先查合规：不合规的结构会让技能在别的环境加载失
败或披露失序，文字写得再好也到不了读者眼前。场景：references 下的册子文件
带了 YAML frontmatter，或 SKILL.md 里塞进了本应放在 references 的整段正文。

**一致性**：引用文件实际存在——断链的引用点进去是空，读者会以为内容丢失；
术语跨文件一致、概念定义唯一——同一概念在两处定义，日后改动只改一处，两处
就开始漂移；自符合——声明的每条约束自己做得到。场景：SKILL.md 的路由指向的
册子已更名，引用还挂着旧名，而宣称「不设状态行」的册子自己在状态行里写「本文是
提纲稿」。

**触发面**：逐词扫 description——正匹配信号足不足：核心能力词在不在、贴用
户说法的触发动词在不在；遮蔽源多不多：宽泛适用面声明、方法论名词、触发词
穷举——它们看似扩大命中面，实际增加遮蔽重叠，让 description 与无关请求互相
抢占。判据与方法论见 general/disclosure.md。场景：description 通篇是「元认知」
「知识工程」这类方法论名词，用户说「帮我改一下这个技能」，触发词对不上，技能根
本没机会被加载。

**零歧义**：主观模糊词有没有量化或判据——「优雅地组织」「合理即可」让读者无法
检查自己做到没有；隐含假设有没有——默认读者知道项目内情、前次讨论的结论；
术语有没有就地定义——用了术语却不解释，读者只能猜。机制：技能读者是零上下
文，文档自身是唯一语境。场景：正文写「对成品做披露分层」，成品与披露都没有就
地定义——只有参与过设计的人才读得懂这句话。

**化石**：成品格式化石——一次实务交付的报告形态与个案规律冒充方法论；判别
问句是「这段是给未来执行者的判断原则，还是我上一次交付物的残片」，无数据的经
验比较表属于修辞不是依据。委托边界泄漏——写委托机制时把不该下发的内容下发：
判定维度、预期路径全交给执行者，等于告诉它哪里有坑，把接收者变成评审员，
摧毁委派换来的隔离；判别问句是「读者知道这条后行为怎么变」「这篇文档论证过隔
离是为了什么吗」。场景：一份讲委派机制的参考文档里，一整节是某次推演用的评
估矩阵模板，外加「某维度几乎必然最低分」这种个案规律。

**no-op**：逐句做「删了行为变吗」——删了读者行为不变，这句就不挣它的篇幅；
弱引导词（「请注意」「务必理解」）如果没承载行为变化，只是噪声。句子级判定标准
在 documents/writing-craft.md，这里应用它。场景：句子「需要注意的是，一个概
念应该只有一个定义」——去掉引导词内容没变；再删整句，若读者本来无从执行「定
义唯一」，这句才是活句。

**结构**：层次是否挣存在——这个标题、这一层小节、这册文件去掉后，内容是否
更直接；能否更少文件、更少层——文件与目录的层级由内容重量支撑，还是继承自
旧框架与模板。机制：结构是导航成本，每个层次都要换回可读性收益。场景：一个
只有三句话的主题配了两级子标题；或一组册子各自重复同一大段引言，本可收敛
到母册一处。

## 判定与产出

问题清单按严重度分级，三级够用：阻断——直接误导读者行动或让技能整体失信
（自相矛盾、断链、宣称未兑现）；显著——某个维度局部失守，妨碍理解但可绕行；
轻微——措辞与呈现层面的瑕疵。为什么分级：修改工作按严重度决定投入顺序，阻
断项先修；不分级的问题清单只是倾倒，把修改工作的注意力平均摊薄。

问题与修法分离陈述。审查报告写三样：哪里、是什么问题、为什么是问题（依据
哪条判据或哪个锚点）；修法留给修改工作。机制：修法要结合上下文设计，审查者
没有动手语境；报告直接给具体修法，作者要么盲从、要么争辩，两者都偏离问题
本身。结构性方向可以给——「这一段按化石维度清理，留洞察删模板」是方向，「把第
三段改成某某」是代修。

「缺陷还是设计如此」先对照设计意图再判，判定还要过一道三档过滤：本质原因
（有对错，报）、美观偏好（无对错，最多标注「偏好」）、习惯（无对错，不报）。
把一次审查里的个人喜好写成缺陷，是审查最常见的失真——判据是问自己「这条有正
确与错误之分吗」。结论要能落到具体维度与判据：「总体还需打磨」是无法验证的空
话，等于没有判定。

## Gotchas

验证者偏见：审查者倾向放过自己能理解的设计——读懂了就觉得没问题，而「我能读
懂」恰好说明我自带作者同款上下文，技能真正的读者没有。机制：看懂一段话需要
补足的隐含假设，读者读不出来时，审查者也常补得无声无息。对策：逐句问「零上
下文读者到这里会卡吗」，或把判定交给独立子代理、给它全新的上下文。场景：审
到某段「秒懂」——秒懂不是绿灯，是警报。

过度纠错：系统性把设计如此或正确的选择误报为缺陷，而且要求每条报告都配解
释会加重误报。机制：审查维度与设计锚点之外没有第三条判据来源，报不出判据
的 flag 是审查者口味。对策：报每条前自问「它违反七维里哪一条、违背哪个锚点」，
答不上来就收回。

抓小放大：把精力耗在措辞与格式上，漏掉结构层的病灶——层次冗余、内容错位、
口径分裂。对策：走查时先看骨架（结构、合规、一致性）再看局部（no-op、零歧
义），细节留给第二遍。场景：盯着一处用词争论半天，同一册子里三个小节的组织
形态不一致却没看见。
