# 审查一个技能

技能写得对不对，靠逐维读文字判定；零上下文 agent 能不能用起来，靠[设计](skill-design.md)的验证环节走一遍判定。两者分工固定：审查判「对不对」，验证判「全不全」。验证发现的卡点常是某维度失守的具体表现，可反过来作为审查的输入。

## 边界与产出

- 判定围绕两套依据：**技能自己的承诺**（声明的边界、每条约束、锚定结论）与**通用标准**（内容质量四标准、开放标准的结构要求）。只用一套会系统性出错：只用通用标准，会把设计如此报成缺陷；只用技能承诺，会把共同底线当成可选。
- 需要锚点才能判：先对照技能的设计意图（配套设计文档，或 SKILL.md 声明的边界）再下判断。**「不管什么」的范围里没做，不是缺陷；宣称的承诺没兑现，才是。** 没有锚点的审查，输出的是审查者自己的口味。
- 审查只读不修，产出是问题清单，不是改好的文件；修复转[修改](skill-modify.md)。机制：审查与修改是两种注意模式，看到问题就动手，剩下的面就没人扫了——修完前三处，后半份文档等于没审。
- 产出分两块写：**问题**（在哪里、是什么问题、为什么是问题）与**结构性方向**（如果有）。具体改法留给修改工作——改法要结合动手时的语境，审查者没有那个语境，写出来就是代修。

## 两种输入形态

- **全量评判**：按七个维度过一遍，输出整体质量判定。用于交付前体检、重大改动后复查、周期性维护。
- **症状排查**：从「行为与预期不符」倒推根因。走法：锁定症状（什么输入、期望什么、实际得到什么）→ 沿触发链追 → 回到审查维度给根因定性。产出是定位与依据，不是补丁；定位之后转修改执行。
- 两条形态共用同一组维度，只是走法不同：撒网找问题 vs 先锁症状再沿链追。排查的意义在于它比全量快得多，且能给出「为什么会这样」的链条；怀疑整体质量时，仍要走全量。

### 症状排查：沿触发链追

行为不对时按这条链从上往下查，第一处断裂就是根因所在：

- `description` 里核心名是否以中英双面出现、且处在正向语境（不在反向条件里）。
- 两条触发路径是否都有词汇面（用户首话 / agent 自问），缺一侧就整条路径失明。
- 是否存在误指向——指向了不存在的独立技能，agent 去找别的技能而漏掉本技能。
- `SKILL.md` 的路由指向的文件是否真实存在（断链是静默失效，无报错）。
- 路由到的论述段是否真的给了判断依据，还是只有承诺（「详见 X」而 X 里没有这个方法）。
- 依据本身是否精确——模糊判据会让读者停在「看起来差不多」，表现像「技能没起作用」。

表现与根因常常隔了两层：症状是「不触发」，根因可能是「触发路径只写了一条」；症状是「执行得不对」，根因可能是「判据模糊导致过早完成」。

## 审查维度

七个维度是走查时要过的七盏灯。每盏灯亮起都要能指出**具体位置**（哪个文件、哪一节、哪一句）与**判据**（违反了什么）——指不出位置的判定无法被修改工作消费。

- **合规**：结构与元信息符合开放标准——文件在不在、frontmatter 全不全、披露是否渐进、引用是否一层深。机械细项见[打包规范](general/standards.md)。不合规的结构让技能在别的环境加载失败，文字再好也到不了读者眼前。
- **一致性**：引用文件实际存在；术语跨文件一致、概念定义唯一；**自符合**——声明的每条约束自己做得到。自符合有边界：十条做到八条是合理状态，剩下两条标为迭代目标写进文档即可，不必因做不到就删掉规范；但没做到的要在文档里说出来，否则就是虚假承诺。
- **触发面**：逐词扫 `description`——正匹配信号足不足、遮蔽源多不多（宽泛适用面声明、方法论名词、触发词穷举）。判据与方法论见[设计技能的披露](general/disclosure.md)。
- **零歧义**：主观模糊词有量化或判据；无隐含假设（默认读者知道项目内情、前次讨论结论）；术语就地定义。机制：技能读者是零上下文，文档自身是唯一语境，歧义处只能靠猜，而猜错不会被报告。
- **化石**：两类。一是成品格式化石——一次交付的形态与个案规律冒充方法论，判别问句：**这是给未来执行者的判断原则，还是上次交付物的残片**；二是委托边界泄漏——把判定维度、预期路径交给执行者，摧毁委派换来的隔离，判别问句：**读者知道这条之后行为会怎么变**。无数据的定性比较（「耗时数小时 vs 显著缩短」）属于修辞不是依据，直接删。
- **no-op**：逐句问「删了行为变吗」。但 no-op 检验必要不充分——有行为效应而功能错位的句子（替作者辩解、结论句压缩判据）同样该删。正面判据是功能归属：这句对应读者哪个动作、需要什么判断。句子级标准在[编写手艺](documents/writing-craft.md)，这里应用它。
- **结构**：层次挣不挣存在——标题、小节、文件去掉后内容是否更直接；文件与层级是由内容重量支撑，还是继承自旧框架。后者表现为「这一节没什么内容但它在」「这份文件只有一小节」——结构在替已经不存在的理由占位置。

## 判定与产出

- 问题清单按严重度三级分级，理由是修改工作要按严重度排投入顺序，不分级的问题是倾倒：
  - **阻断** —— 直接误导行动或让技能整体失信：自相矛盾、断链、宣称未兑现。
  - **显著** —— 某一维度局部失守，读者可绕行但有代价。
  - **轻微** —— 措辞与呈现层面的问题。
- 「缺陷还是设计如此」过三档过滤，判据是**这条有正确与错误之分吗**：
  - **本质原因**（有对错）→ 报，落到具体维度与判据。
  - **美观偏好**（无对错）→ 最多标注「偏好」，不进问题清单。
  - **习惯**（只是与我的写法不同）→ 不报。
- 结论要落到具体维度与判据。「总体还需打磨」「质量有待提高」是无法验证的空话，读者无法据此行动，也无法判断改没改好。

## Gotchas

- **验证者偏见**：「我能读懂」说明的是我自带作者同款上下文——秒懂不是绿灯，是警报。对策：逐句问「零上下文读者到这里会卡吗」，或交独立子代理用全新上下文审一遍。作者盲区无法自纠：我知道该写什么，所以看不到没上下文的人会卡在哪。
- **过度纠错**：把设计如此误报成缺陷。对策：报每条之前自问它违反七维里哪一条、违背哪个锚点，答不上来就收回。另有一类高发误报是把「没做到 100% 自符合」当缺陷——见一致性维度的边界。
- **抓小放大**：精力耗在措辞上，漏掉结构层病灶。对策：先看骨架（结构、合规、一致性）再看局部（no-op、零歧义），细节留第二遍。
- **审查者即被污染者**：审查自己写的东西时，自己的指纹从内部看就是「事情本来的样子」。结构性盲区看不出的问题，外部视角一遍就能看出——这是委派独立子代理审查的理由，不是可选项。
