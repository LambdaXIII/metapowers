# Design

## Context

动机与变更清单见 proposal.md（Why / What Changes）。这里只记实施所需的现状事实与约束：

- 现状引用面（已 grep 核实）：「非只读/操作参考/厚薄」一族称呼散布 SKILL.md、protocal-operations.md、protocal-write.md、protocal-maintenance.md、protocal-init.md、design-discovery-contract.md、spec-note.md、spec-rules.md 共 8 个文件；文件路径引用散布 SKILL.md 协议表与清单、maintenance 相关参考节、init P3/P4。
- 头部自述共 9 处（4 份 design/protocal 文档 blockquote、write「## 定位」、maintenance「## 概述」、spec-note/spec-rules/spec-frontmatter/script-tools 头部）。每处自述承载的功能不同：术语定义（design-rules 的「组织方式」）、分工路由（spec-rules↔design-rules、spec-note↔protocol-write）、可调整声明（种子 RULES）。
- design-discovery-contract.md 与 init P3 存在事实双重定义：有效条件↔要素覆盖检查、合约已存在的情况↔已有合约的检测、回退模板（P3 内嵌）↔ Step 3 模板、权限禁令两处各写一遍。
- 契约目标见 specs/journaling/spec.md delta（协议条目与加载指引、操作协议、发现合约论述与步骤的分工、内容边界、读者路由、维护的价值主轴）。
- 仓库规范约束：技能内容零歧义、设计内容分离、文档自包含（禁会话引用）；原子修改（备份→写入→比对→删备份）用于整文件重写。

## Goals / Non-Goals

**Goals:**

- 冷读者旅程端到端可读：加载 → SKILL.md 定位（此刻要做什么、何时读什么）→ 协议 → 论述，任何一跳不依赖项目历史知识。
- 事实单处承载：模板、要素清单、族义务、术语定义各定义一次，其余位置引用。
- 每处删除都有功能承接：自述删除前其承载的功能（定义、路由、判据）先归位。

**Non-Goals:**

- 不改 scripts/ 的任何行为与文案实质（脚本语义无变更）。
- 不重写 spec-note / spec-frontmatter / spec-index / spec-rules 的实质内容——只清头部自述并把其承载的信息归位。
- 不动其他技能与 skill-package / skill-grouping 规格；跨技能同类病灶另行提案。
- 不迁移、不改写任何 journal 本体内容。

## Decisions

**D1 合并去处：`protocol-operations.md` 承载唯一全族协议，命名「操作协议」（Operations），`protocal-write.md` 退役。**
用户裁定两件事：其一，「收录、编辑、删除、新建本就共享同一套逻辑」，厚薄切分废除；其二，伞名不得取「write」——协议名即路由，实测 agent 因「write」窄义把编辑、移除误归维护协议，而维护是边界最敏感的专项协议（用户触发、独立流程），名称误导直接侵蚀该边界。伞名取「操作协议」：与域定义「改变 journal 状态的操作」同名同义，覆盖声明写进名字，配合加载指引触发时机明示「新建/编辑/移动/删除归此协议」。备选「写入协议」被弃（误导实证）；备选「条目操作协议」被弃——操作族措辞不必绑定「条目」，且名字更长。文档内部组织为「共同逻辑（族义务、价值与归属判断、关联一致、INDEX 反映）＋ 各操作差异指引（新建/补充、收录、移动、删除各一小节）」；维护仍是独立协议；删除语义照旧归 journal 规则。description 的「Write operations」触发措辞不动——「触发语义」契约钉的是技能加载面（何时加载技能），不是协议路由面（加载后走哪个协议）。

**D2 发现合约文档归位：保留 `design-discovery-contract.md` 文件名，全文重写为论述。**
该文档的身份就是「设计发现合约」的论述——design-* 族即设计某物的启发/论述（design-rules、design-index 同族同身份），名字与归位后的身份一致，重写的是内容与语气。备选 A「改名去 design- 前缀」被弃：单改它破坏族一致性，分类可读性由 SKILL.md 目录注解解决（D4）。备选 B「并入 init P3」被弃：P3 膨胀且违反「发现合约论述与步骤的分工」契约。事实归置：注入文本模板、要素清单、检测清单只在论述中定义一次；P3 删内嵌模板副本与方法细节，改为引用论述。

**D3 init P3 收敛为纯步骤：目标（可发现态）、禁令（不得自行写入宿主提示词）、动作序列（检查现有合约 → 载体清查 → 评估 → 推荐呈报 → 回退触发）、完成条件（可发现态检查）。**
「为什么需要发现合约」「有效条件」「方案讨论」等论述并入论述文档；P3 的「合约已存在的情况」简化为引用论述的检测节。

**D4 路由承载面（SKILL.md）：章节顺序 原则 → 脚本 → 参考目录；目录更名 References 并分组注解。**
协议表保持三行（Init / Operations / Maintenance），Operations 行的 Trigger/Operation 覆盖全族操作（明示新建/编辑/移动/删除归此行、不归维护）；References 清单按功能分组（协议 / 设计启发 / 规范 / 工具与模板 / 模式），逐条一行加载时机注解（回答「何时读」）。备选「平铺清单只加注解」被弃：18 条平铺下时机注解可读性差；备选「删清单、由协议表承载全部路由」被弃：「读者路由」契约要求每篇参考文档从加载指引可发现。脚本节补一句：按需取用，主线任务时不必专门跑检查验证。

**D5 文件名拼写修正：`protocal-*.md` → `protocol-*.md`（init/maintenance/operations 三文件改名；write 文件退役不改名）。**
protocal 非英文词，是读者旅程上的可见瑕疵；本次重写波及全部引用，是成本最低的时点。备选「保持现名」被弃：与 References 更名的命名可读性目标不一致。风险见下。

**D6 头部自述清扫的统一手法：先归位、后删除。**
文档开头直接进入读者的操作或判断内容（skill-master 域已有同源口径）。三类信息的归位去处：术语首现定义（如「组织方式」）并入正文首段；文档分工/路由由 SKILL.md References 注解与标题承担；「可调整」类操作事实（种子 RULES）改写为正文句保留。design-discovery-contract 的「有意冗余——保留此重复」：冗余本身保留（合约与 INDEX 协议声明各自完整陈述读写规则），删设计理由句。「评估示例（仅作格式参考）」表删除，评估判据（三个过滤问题）保留为论述内容。design-index 的「源自一次真实的 dashboard 退化事件（2026-05-29……）」删日期与事件叙事，板块建议及其判据保留。

**D7 maintenance 换轴的落法：概述重写为「核心命题 ＋ 触发边界」，检查重心沿主轴重排。**
核心命题（维护的重点是真正整理、沉淀、优化知识，不是把文件改得「所谓的合规」）锚定文首；「交付检查」重组为两层——主检（知识沉淀质量：沉淀是否充分、冗余是否收敛、链路是否可用）与底线（形式合规：frontmatter、链接、格式）；删「本协议定义维护的全过程，分为三部分」结构自述，硬性/启发区分由 `<rules>` 块既有开头承担。

**D8 patterns/*.md 的 summary 块保留渐进披露功能，改写语气。**
读者靠摘要决定读不读全文，这是真实读者功能；从「本模式提供……」式自述改为「何时用、解决什么」的判据式摘要。备选「删 summary」被弃：丢掉渐进披露。

**D9 称呼统一与概念清零。**
全 content 统一称呼：「操作协议」（全族）、「发现合约论述」（design-discovery-contract.md）、「初始化协议 / 维护协议」。「非只读操作参考」「操作族参考」「厚操作/薄操作」「写入协议」（协议名）、「Non-read-only operations reference」全部清零。方法：按受影响概念清单（而非关键词）逐个 grep 验证，含 spec-note、spec-rules、design-discovery-contract 内的「非只读操作前加载」等衍生措辞。

**D10 版本与记录。**
dev/journaling/CHANGELOG.md 一条逻辑变更记录（合并、归位、清扫、改名）；版本号按仓库纪律在功能完成后统一确定，不在本设计预定。

## Risks / Trade-offs

- [术语级联遗漏，留下旧称呼/断链] → 概念清单法逐项 grep 清零；收尾跑一次链接完整性检查（解析 content 内全部相对链接逐个落点核对）。
- [清扫自述时误删承载信息（定义/路由/判据）] → 每处删除前先回答「这段承载什么功能、归位到哪」，未归位不删；冷读推演复核导航完整性。
- [P3 简化后可执行性下降] → P3 保留动作序列、禁令与完成条件；推演「从 init P3 链入论述整体读」的体验作为验收项。
- [合并文档过长影响检索] → 差异指引按操作分节保持最小；若单文件明显超长，允许把「各操作差异指引」降为文内附录节，不拆回两个文档。
- [改名断外部引用] → 已核实 journal 内容引用的是文档标题而非文件路径；CHANGELOG 记录改名映射；git 分支整体可回滚（feature 分支 + no-ff 合并）。

## Migration Plan

实施顺序（依赖驱动）：① 全族协议合并与文件改名（结构骨架先立）→ ② 发现合约重写与 init P3 收敛（事实归置一次到位）→ ③ 其余文档自述清扫与 maintenance 换轴 → ④ SKILL.md 路由承载面与种子 RULES → ⑤ 称呼统一清零、CHANGELOG、验证。回滚：feature 分支整体回退，main 零触碰。
