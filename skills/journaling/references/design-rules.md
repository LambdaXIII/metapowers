# 组织方式设计提示

> 本文提供设计 journal 组织方式的提示。组织方式 = 笔记库的整体形态：内容如何放置、命名、被找到，有哪些约定。规则文档（RULES.md）是把组织方式记录下来的载体——设计对象是组织方式本身，不是 RULES 文件。
> 规范层（规则编写的原则、规则设计的提醒）见 `spec-rules.md`；本文只给设计提示。

---

## 组织方式：不仅仅是编写 RULES

组织方式不是"规则文档里写了什么"——规则文档只是记录。组织方式是笔记库实际运作的形态：一条新内容进来时会发生什么、一条旧内容需要时怎么被找到、维护时从哪入手。设计组织方式，就是设计这些实际发生的路径，而不是设计一份文档的板块。

组织方式可以很简单——内容很少的笔记库，可能只需要"全部放根目录，按名字找"。也可以很复杂。复杂度由笔记库自身的使用方式决定，不由任何模板或模式决定。

## 设计提醒：以读写关系为线索

设计组织方式时，不要直接字面思考"我要什么分类、什么标签、什么板块"——分类、标签、索引、约定都只是手段。组织方式落定为规则（约定）集合，规则本质上是规范**写的过程**的：内容放哪、怎么命名、打什么标签、写什么摘要。而整个写的过程是为**读**服务的——写时做对的每一件事，都在保证读时能被高效、高质量地找到和理解。规则设计要平衡的，是写过程的摩擦：规则越重，写摩擦越大；规则越轻，读的质量失去保证。

### 读：写服务的目的

读是高频的——每次 session 启动、每次检索都在发生。读的效率和质量的构成：

- **高效发现**：需要一条内容时能被找到——靠机制而不是靠记忆（目录、命名、标签、索引、链接的一致性）
- **理解质量**：找到之后，上下文足以理解它（摘要、关联）
- 读的摩擦信号：需要旧笔记时靠记忆而不是检索找到它；查询成本持续上升——这是写时欠账的体现

### 写：被规则规范的过程

写是低频的——但每一次写都在为读做铺垫，规则直接规范写的行为：

- **归属**：判断"放哪"的成本——规则是否简单到写入时不假思索？
- **附加操作**：更新入口、打标签等——是否值得？
- 写摩擦信号：反复犹豫"放哪"——规则过重；跳过分类步骤——规则与内容脱节（写时图省事，读时讨还）

### 规则分量的平衡

读的质量要求决定规则**内容**（写要做对什么）；写摩擦决定规则**分量**（做到什么程度值得）。规则设计就是在这两端找平衡——为读的质量而设计，为写的摩擦而克制。

## 多种设计模式参考

设计模式是对笔记库组织方式某个层面或方面的构思框架——局部或整体。以下是 `patterns/` 收集的模式参考（每个文件以摘要开头，先读摘要判断是否需要全文）：

- `classification-systems/` — 内容归类的模式集合（6 种，见 `classification-systems/about.md`）
- `dashboard.md` — 领域级次级 INDEX：索引信息按领域分层，渐进式披露
- `note-tags.md` — 笔记标签：tags 字段编写格式、庞杂时启用注册表
- `maintenance-memo.md` — 维护备忘录：独立文档记录延后操作、维护时统一处理
- `layered-rules.md` — 分层规则：条件性遵循的规则分入规则子集，按需加载

模式是参考不是规范——是否采用、如何适配由 journal 自己决定。

每个模式的具体内容见对应文件——先读摘要判断问题是否匹配，匹配再读全文。
