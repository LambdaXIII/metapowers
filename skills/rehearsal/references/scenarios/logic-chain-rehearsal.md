# 逻辑链路推演
> 场景文档 — 配合推演通用论述（`../rehearsal-guide.md`）参考使用，补充逻辑链路载体的特化内容。

将推演方法应用于任何**预定逻辑流程**的验证。适用于：
- 代码运行时逻辑：程序按语句逐行执行的结果
- 配置规则：多层配置的优先级、合并、覆盖行为
- 决策树/规则引擎：输入数据按规则匹配后到达的叶子节点
- 数据转换管道：数据从源头经多步变换后的输出
- 工作流编排：步骤的分支流转和条件判断

不适用：文档内容 → [doc-guide-rehearsal.md](doc-guide-rehearsal.md)、交互体验 → [interaction-rehearsal.md](interaction-rehearsal.md)、接口契约 → [api-design-rehearsal.md](api-design-rehearsal.md)、知识库 → [knowledge-base-rehearsal.md](knowledge-base-rehearsal.md)、提示词 → [prompt-instruction-rehearsal.md](prompt-instruction-rehearsal.md)、计划文档 → [plan-rehearsal.md](plan-rehearsal.md)、设计方法论 → [design-doc-rehearsal.md](design-doc-rehearsal.md)。

## 本载体的核心差异：读者是执行引擎

本载体模拟的读者是**执行引擎**——对给定的逻辑/规则/代码进行**机械执行**的实体。它没有判断、不会纠错、不理解意图——只执行定义，不看注释。

执行引擎的特征：
- 精确执行：每一步按语义定义走，从不断章取义
- 不填补缺口：未定义的路径就是真正未定义的行为
- 不宽容：输入格式偏差、类型错误、除零立刻抛出（对非代码载体相应表现为：规则不匹配即拒绝、路径无定义即失败、分支未声明即终止）
- 无上下文暗示：不会因为一个值在语义上"不应为负数"就自动纠正

逻辑链路推演是唯一模拟**无理解、无判断、纯机械精确执行**的读者（区别于计划文档的 agent 执行者——它有上下文内的目标与查证能力；区别于提示词的模型读者——其行为受措辞影响、存在理解偏差）——不需要模拟"这个人物会怎么想"，而是模拟"这段定义会怎么执行"。正因为如此，逻辑链路通常可以更客观、更可重复。

### 与其它推演的区别

| | 逻辑链路 | API 设计 | 交互流程 | 计划文档 |
|---|---|---|---|---|
| 模拟对象 | 执行引擎 | 调用者 | 操作者 | 执行者（人/新 agent） |
| 发现 | 行为与意图的偏差 | 契约覆盖/命名/可操作性 | 体验障碍 | 执行路径通/不通 |
| 关注点 | 控制流、状态、资源 | 接口表面 | 困惑点、放弃率 | 步骤可判定、依赖、异常预案 |
| 粒度 | 语句/规则级 | 端点级 | 步骤/操作级 | 步骤级 |

与计划文档的边界：计划执行者（新 agent）"按字面执行、不推断"容易与执行引擎混淆。区别在于——执行引擎无背景知识、无上下文内查证能力，只按定义机械执行；计划执行者从计划文档背景段获知目标，可在上下文内查证。规则/配置/代码的机械执行归逻辑链路；"告知执行者按步骤达成目标"的计划归 plan-rehearsal。

## 执行引擎定位（P2 身份设定的要点）

P2 身份转换时：你是执行引擎——不会说「也许设计者的意思是...」，只按照代码/规则/配置的**字面定义**机械执行。

特别需要划掉的设计意图：不知道「这个值在这里永远是正数」、不知道「这个分支之后会加处理」、不知道「注释说返回非 null 所以肯定是非 null」。只看定义，不猜意图。

## 模拟阅读的特有信号（P3 补充）

按执行顺序逐语句/逐规则跟踪（"阅读顺序"即执行顺序），记录信号：

| 信号 | 含义 |
|------|------|
| "条件未完整覆盖" | 某些输入走入了未预期的分支——条件逻辑有空洞 |
| "状态修改打破后续假设" | 某处修改了变量/字段，后面代码仍假设旧值 |
| "隐式依赖未满足" | 依赖的变量在上面的分支中没有初始化——某些路径下崩溃 |
| "类型转换丢失信息" | 截断、舍入、精度丢失——数据已损坏 |
| "资源不对称管理" | 获取和释放不在同一层次——有的路径泄漏 |
| "时序不确定性" | 并发操作的不确定顺序——结果依赖调度 |

**记录格式**：逻辑链路的信号记录不是"读者感到困惑"（执行引擎不是人），而是"执行引擎在这个输入下的行为与设计意图偏差在于..."。推演者自己对比"定义会导致什么"与"设计意图应该是什么"。

示例（配置规则推演的记录片段）：

```
规则："rate > 0.5 时拒绝请求"
输入：rate = 0.5
行为：未拒绝（条件 > 不含等号）
意图：阈值边界应含等号——设计者以为 0.5 也被拒
记录：条件未完整覆盖——边界值 0.5 走入了未预期分支（偏差：行为与意图不一致）
判定：异常
```

## 边界与异常场景（P4 补充）

| 场景 | 检查目标 |
|------|---------|
| 零值、最大值、负值 | 边界输入下行为是否合理——除零、溢出、负数表示 |
| 空集合、单元素集合、巨型集合 | 极端规模下的行为正确性与资源消耗行为（推演是模拟，只能评估复杂度行为，不能实测性能） |
| 并发/交错的时序变化 | 竞态条件下不变量是否保持 |
| 异常路径中的状态 | 异常抛出那一刻调用栈各层的状态是否一致 |
| 资源耗尽 | 文件句柄耗尽、内存耗尽、超时——降级行为是否存在 |
| 类型边界 | 浮点精度边缘、整数溢出、字符编码问题 |

## 评估整理（P5 的要点）

**严重程度格式：** OK/异常（逻辑链路是确定性执行，二元判定比连续量表更合适）。定义：

- **异常**：执行引擎的字面行为与设计意图不一致——需要修复
- **OK**：行为与意图一致

**评估维度提示（在通用论述评估维度表逻辑链路行 5 项基础上扩展为 6 项；额外提示，非硬性指标）：**

| 评估维度 | 含义 |
|------|------|
| 控制流正确性 | 在给定输入范围内，执行是否按预期走正确的分支 |
| 边界条件覆盖 | 边界/极端值输入下是否有未处理或未预期的行为 |
| 状态一致性 | 数据/状态在操作序列中始终满足不变量 |
| 资源生命周期 | 资源（内存、文件句柄、连接、锁）的获取/使用/释放是否完全配对 |
| 异常安全 | 异常路径中是否有状态腐败或资源泄漏 |
| 隐式假设可见性 | 依赖的前提（如"这个值一定不为 null"）是否被显式声明或验证 |

**复现对照注意（P5S1）：** 回到 P1S3 整理的作者意图（编写时的理解），按四向对照。逻辑链路的「意图」是设计者的预期行为，「实际」是执行引擎的字面行为——两者之间的任何偏差即为缺陷。

**错误模式搜索候选（P5S5）：** 信号表中的六类信号（条件未完整覆盖、状态修改打破后续假设、隐式依赖未满足、类型转换丢失信息、资源不对称管理、时序不确定性，定义见上表）反复出现时即为错误模式——尤其留意前三类，它们是常见的结构性根因。

## 与提示词推演的逻辑层关系

提示词推演（[prompt-instruction-rehearsal.md](prompt-instruction-rehearsal.md)）的「逻辑执行层」本质上就是一次逻辑链路推演——将模型理解的指令作为"定义"，跟踪其执行链路。关键区别是逻辑链路推演的"定义"是精确的（代码/规则），而提示词推演的"定义"是模糊语义——模型可能理解错误。

如果推演提示词时发现了逻辑链路层面的缺陷，可以引用本文件的方法分别推演"被理解的逻辑本身"是否有漏洞。两个推演分开执行——先确定表达层的问题，再确定逻辑层的问题。

## 常见陷阱

- **带入意图而非只看定义**：代码写着 `if x > 0`，但你知道"x 在这里永远是正数"所以跳过验证——盲区
- **只走正常路径**：最高频的 bug 在"从未想过会发生"的路径
- **忽略时序/并发**：单线程逻辑完美，两个并发操作在同一数据上就是随机结果
- **把注释当契约**：注释说"返回非 null"，某个分支返回了 null——执行引擎只看代码
