# skill-master Specification

## Purpose

本域是技能工作元技能 skill-master：对象是一个技能的全部工作——从值不值得做、怎么组织怎么写、为什么行为不对、够不够好、别人能不能用起来，到该不该改与怎么改。定位由名字界定，不由清单界定：边界只划在**对象**上——对象不是技能的事不归本域；凡是技能的事，不因为尚未写到就划出去。已成文的论述是当前覆盖范围，不是能力边界。

技能的工作有两类委托方：**制作侧**（把它做出来、修好、审对、验能用）与**使用侧**（决定用不用、选哪个、刚用完回顾）。本技能让零上下文 agent 独立走完技能工作的全程。性格是**指导支持而非规范限制**：以要点提示为主、辅以简单推荐流程、给足发挥空间。

## Requirements

### Requirement: 对象边界
本域的对象边界 MUST 只由「对象是技能」划定。对象不是技能的工作 MUST NOT 归入本域：把技能内容改写为人类可读说明文（技能阐述的范畴）、编写 agent 系统提示词、对任意交付物做推演检查。MUST NOT 因某项技能工作尚未有成文论述就将其划出边界。六工作是当前覆盖范围，MUST NOT 表述为能力边界。「技能是实践的沉淀物」这一世界观 MUST NOT 写进技能正文。

#### Scenario: 非技能对象不承接
- GIVEN 请求把某技能改写为给人读的教学材料
- WHEN 判定归属
- THEN 不属本域工作——对象是技能但工作是阐述，归技能阐述

#### Scenario: 未写到不等于划出
- GIVEN 某项对象是技能的工作尚无对应成文论述
- WHEN 判断边界
- THEN 仍在本域范围内，只是当前覆盖未及

### Requirement: 工作域与立场分界
六工作 MUST 分两组：制作侧——设计、修改、审查、快速测试；使用侧——预评估、后评估。分界 MUST 由委托方立场判定：接下来要改它的是制作侧，要用它、刚用过的是使用侧；两侧判据同源（内容四判据）。各工作职责 MUST 保持：设计（从实践到技能——值不值得做、为谁做什么、怎么组织怎么写、怎么交付）；修改（结构内的改动——该不该改与怎么改，改动沿引用链传播）；审查（判「写得对不对、说的和做的是不是一回事」，主线是三源交叉比对；症状排查是第二进入方式——从「行为与预期不符」沿触发链倒推，产出定位并转修改）；快速测试（判「零上下文 agent 能不能理解、走通、用起来」，推演不执行；生命周期独立环节——交付闸与修改后回归）。审查与修改 MUST 保持为两种注意模式而非固定工序链，审查可在任何时点切入。

#### Scenario: 立场判归属
- GIVEN 维护者要找出技能哪里不对、与使用者评估未用过的技能两个请求
- WHEN 判定工作归属
- THEN 前者是审查（制作侧），后者是预评估（使用侧），不互指

#### Scenario: 症状排查转修改
- GIVEN 某技能行为与预期不符，沿触发链倒推到根因
- WHEN 输出排查结果
- THEN 产出定位清单并转为修改工作，排查不自行修复

### Requirement: 使用侧评估边界
预评估 MUST 凭手头证据给出可辩护的评估结论（方向七条：内容、来源、活跃度、知名度、合身、已有、代价——手头已有什么证据就用什么），供采纳决定作输入；MUST NOT 判定技能的实际覆盖面；评估与解读分离——怎么解读结果、采纳与否 MUST NOT 进入评估指导。后评估 MUST 产出洞察记录（什么真的有效、什么不足或错、想改什么——到「缺什么」为止），每条洞察 MUST 带本次实证，印象式结论 MUST NOT 记入；实际执行形态照实记，偏离指引是信号不是过错。后评估 MUST NOT 委派（证据在使用者经历里，委派即丢失）；其翻检问句是入手角度，MUST NOT 升格为逐项工序。两评估 MUST 保持轻论述形态（要点与启发），MUST NOT 加入流程机关、模板或评分表。证据立场：评估方向是提示，取证方法不提示；某方向信息不足时如实记录缺失是预期行为，不是缺陷。

#### Scenario: 评估不越界到解读
- GIVEN 预评估产出了评估结论
- WHEN 检查产出
- THEN 结论含理由，但不包含「所以你该不该用」的采纳决定

#### Scenario: 洞察必须带实证
- GIVEN 后评估记录的一条洞察
- WHEN 检查其依据
- THEN 关联到本次使用中实际发生的事件，无实证的印象式结论不记录

### Requirement: SKILL.md 形态——前提与路由
SKILL.md MUST 是「前提 + 路由」而非纯路由。前提《什么是一个好的技能》MUST 加载即得，其共享背景 MUST 是三项：技能靠三层加载生效、读者是零上下文 agent、内容四判据（有用、全面、准确、清晰）。路由 MUST 按委托方立场分两组：常见情形（使用侧）在前、技能开发（制作侧）在后。入口的索引与路由 MUST 合一：MUST NOT 另设独立目录节——分组路由即全貌；确有未进路由的文件，作为路由的一节补在末尾，MUST NOT 另起清单。

#### Scenario: 前提三项齐备
- GIVEN 本技能的 SKILL.md
- WHEN 检查前提节
- THEN 三层加载机制、零上下文读者、内容四判据三项齐备，工作论述可直接以此为地基

#### Scenario: 目录节不复活
- GIVEN SKILL.md 的文件导航
- WHEN 检查形态
- THEN 只有分组路由一处，无独立目录节重复列出文件

### Requirement: references 组织与命名
支撑文档 MUST 按内容性质分三个次级目录：documents/（文本类家族：各文档形态编写方法 + writing-craft）、scripts/（脚本设计论述 + scripting-craft）、general/（跨类通用：规范册、结构册、披露论述）；快速测试方法细则 MUST 按工作名分组进 quick-test/，不属内容性质轴。打包/编写 MUST 分离：目标技能的打包目录是放置规范（由 general/ 规范册转述），编写论述的分组与之正交——工作流文档打包成静态资源不改变其编写论述归属。文档形态 MUST 收敛为三：知识（静态客观资料，是查的不是读的）、工作流（照着走）、论述（读了懂自己发挥）；提示是论述的笔法，MUST NOT 作为独立形态。编写手艺（craft）MUST 随服务对象走：writing-craft 归 documents/、scripting-craft 归 scripts/。入口文件（SKILL.md）的编写方法 MUST 单设一册（documents/skill-md-writing.md）；披露 MUST 拆两篇——general/disclosure.md 收机制与判据，skill-md-writing.md 收 description 定稿流程与回归；组织知识 MUST 拆为 general/standards.md（标准与环境约束的转述与核对，约束按「标准」「环境」两列标注）与 general/structure.md（地板之上的结构设计方法）。分册命名 MUST 遵守：工作论述带 skill- 前缀、craft 以 *-craft 命名、论述与规范册用职能名。扩展 MUST 在次级目录内进行，顶层工作论述保持稳定；MUST NOT 为单册设顶层目录；新文档形态出现时先有内容、再定分组，MUST NOT 预造框架。

#### Scenario: 打包轴与编写轴不混
- GIVEN 一份工作流文档打包在目标技能的静态资源目录
- WHEN 查找其编写论述
- THEN 归 documents/ 的 workflow-writing，不按打包位置另设论述

#### Scenario: 命名模式区分文档身份
- GIVEN 新增一份工作论述或 craft 文档
- WHEN 检查文件名
- THEN 工作论述为 skill-<work>.md 形式，craft 为 <object>-craft.md 形式

### Requirement: 论述形态与流程刚性
工作论述 MUST 以要点并列组织（每要点讲清是什么、为什么、给个具体场景），整体路径只轻轻带过，MUST NOT 设阶段门禁——仅内容本身是程序时才用流程形态。快速测试册 MUST 保持流程刚性不软化：流程图、门禁、中止判据、报告格式是硬约束。审查册的七类 MUST 保持为病灶分类（根因定性——判别问句 + 指回权威册的指针），MUST NOT 作为逐项扫描检查项使用。机械项（合规判据）MUST 单独成节并逐字段对表——环境不明时标「待核实」进清单，MUST NOT 降级放掉也 MUST NOT 硬判。锚点 MUST NOT 自动豁免：三源（设计文档、技能正文、支撑论述）互为基准，锚点内部不一致时先报出，再作基准。审查的执行 MUST 固化为委派，委派契约 MUST 要求执行者写明「明知该查而没查的是哪几类」。测试委派 MUST 遵守隔离铁律：测试子代理 MUST NOT 知道预期效果、其他测试单元的存在、baseline/实验组区分或任何对比信息。推演中的能力模拟协议字面量（`[能力模拟] [类型] → 动作 → 推演结果`）MUST 保持中文原样，MUST NOT 单方面英化。

#### Scenario: 病灶不作扫描清单
- GIVEN 审查册的病灶七类
- WHEN 使用它们
- THEN 在比对发现不一致之后归类根因，不拿着七类逐项扫描

#### Scenario: 环境不明不硬判
- GIVEN 某机械项的合规判据依赖环境规则，而当前环境不明
- WHEN 处理该项
- THEN 标「待核实」进入清单，不降级放掉、不硬判违规

#### Scenario: 测试子代理零预期
- GIVEN 快速测试的委派下发
- WHEN 检查子代理收到的内容
- THEN 不含预期效果、其他测试单元、分组区分或对比信息

### Requirement: 判据权威单一
判据 MUST 只在权威位置维护一份，MUST NOT 复制到多处（description 的逐词判据只在披露册维护）。MUST 禁止双份权威：与其他文档重复的内容直接引用现有的，独有而有意义的融入共享文档并互设指针。技能内容 MUST NOT 复制仓库特有的工程纪律（发布流程、分支策略等）；例外是与结构直接相关的环境条目（白名单目录、metadata 必填等），它们 MUST 在组织册内出现并标注来源。静态资源的放置 MUST 表述为「进静态资源目录（以目标环境白名单为准）」，MUST NOT 无条件写具体目录名。

#### Scenario: 判据不复制
- GIVEN 某判据已在权威册中维护
- WHEN 其他文档需要引用
- THEN 以指针指回权威册，不在本处复制判据文本

### Requirement: 内容编写纪律
每句正文 MUST 无来源不落笔——来源只能是真实机制或被走通的实践，「对话里出现过」不是来源；输入 MUST 先分类（决策/方向/启发素材/事实观察），启发素材的产物是设计不是文本。判断依据 MUST 给足理由（机制或判据），断言不悬空。成文 MUST 先有节级设计（这个阅读位置的读者需要什么、依据哪些真实素材）再展开；未完成设计的节保持要点态。错误模式清单与同类经验清单 MUST 只增不减——某模式长期未触发 ≠ 没用；每行 MUST 泛化、MUST NOT 绑定具体技能；每次实践后的可泛化发现补入对应清单。修改审查方法时 MUST 沿用两版并行验证法（两版并行跑同一被测对象 → 比对执行过程而不只比结果 → 融合），未核实原文的结论不落笔。

#### Scenario: 无来源句不落笔
- GIVEN 一条要写入论述的断言
- WHEN 追问其来源
- THEN 能指认真实机制或被走通的实践；来源只是讨论中出现过的，不写入

#### Scenario: 经验清单只增不减
- GIVEN 某错误模式长期未在测试中触发
- WHEN 维护错误模式清单
- THEN 该模式保留，每行保持泛化表述

### Requirement: 术语表述——工作与论述组
术语 MUST 统一指称，正文用词 MUST NOT 漂移到禁用同义词：**工作 (Work)**（六类工作领域，分两组）——Avoid 任务、阶段、流程、验证；**论述 (Discourse)**（对一种工作或一类内容编写方法的完整知识呈现，要点提示形态）——Avoid 教程、手册、指南；**前提 (Premise)**（所有工作共享的背景判断）——Avoid 理念、原则；**症状排查**（审查的第二进入方式）——Avoid 调试；**病灶 (Defect class)**（根因定性的七个高发类别：转发、自违、占位、空转、悬空、断链、化石）——Avoid 维度；**审查 (Review)**——Avoid 走查；**快速测试 (quick test)**——Avoid 验证；**预评估 (pre-assessment)**——Avoid 审查、审计、评分、选购；**后评估 (post-assessment)**——Avoid 复盘、总结；**推演**（不实际执行被测技能的检验方式）——Avoid 实测、执行；**被测技能**（快速测试的对象）；**能力模拟**（推演中对外部能力的模拟执行与假设记录）；**推演中止**（同类系统性失败的判据）；**测试单元**（一次独立推演场景）与**触发测试单元**（测触发面语义匹配的盲测单元）；**隔离铁律**。「验证」不是术语——该词随其历史指代退出正文。

#### Scenario: 禁用同义词不出现
- GIVEN 技能正文与支撑文档
- WHEN 检查术语用词
- THEN 各概念用统一指称，未出现对应 Avoid 词指代该概念

### Requirement: 术语表述——成品、形态与设计词汇
术语 MUST 统一指称，正文用词 MUST NOT 漂移到禁用同义词：**成品 (Artifact)**（技能装载的内容产物：SKILL.md、description、参考文档、模板、脚本、静态资源）——Avoid 材料、素材；**知识（成品形态）**（静态客观供查阅的资料）——Avoid 参考资料；**工作流（文档形态）**（分步骤照着执行）；**论述（文档形态）**（供阅读获得判断依据）；**提示（笔法）**（论述的书写方式，非独立形态）；**编写手艺 (craft)**——Avoid 笔法；**入口文件 (Entry file)**（技能中唯一必须存在的 SKILL.md）——Avoid 主文件、包规范文件；**分层 (Layering)**（内容按加载成本在层间分配 + 资源层内部层级结构）——Avoid 渐进式披露（专指三层加载机制，是依据不是分层本身）；**锚定 (Anchoring)**（设计起点——确定提供什么、指导什么、不管什么，并判定价值与可行性）——Avoid 定位、需求分析；**披露 (Disclosure)**（技能向加载器与用户呈现自身的方式）；**触发面**（description 与触发词共同决定的被语义匹配命中的词汇面）；**打包/编写分离**（放置与编写方法是正交关注点）。

#### Scenario: 分层与渐进式披露不混用
- GIVEN 技能内容讨论内容在层间的分配取舍
- WHEN 检查用词
- THEN 用「分层」指称该设计，「渐进式披露」只指三层加载机制

### Requirement: 措辞风格
正文 MUST 用确定性陈述——MUST NOT 出现「待定 / 开放问题 / 将来可考虑」。术语 MUST 以术语定义为单一权威，正文首次出现时按需就地定义。开发讨论的速记/代号 MUST NOT 进入正文。标题 MUST 表述读者的工作（如「设计一个技能」），MUST NOT 宣布文件身份；宣布式开头（「本文档是……」「读者默认已读……」）MUST NOT 出现。写前 MUST 推算读者的信息状态：按加载序列判断此位置读者已知什么，已披露不重述、未披露不依赖。

#### Scenario: 宣布式开头不出现
- GIVEN 任一论述文档的开头
- WHEN 检查首段
- THEN 直接进入读者的工作或判断内容，无「本文档是……」式自我定位

### Requirement: 触发语义
description MUST 保持盲测定稿的形态骨架：对象界说职责句（任何对象是技能的工作）、工作枚举降为动词面、中文核心名别名「技能」、业务措辞骨架 + 两条自问信号（交付后一条、用后一条）、反向条件一条（真实执行测试类不合触发；快速测试（推演）在本技能内）、中英双面词汇。MUST NOT 使用触发词穷举或 `Triggers:` 类结构化标签——穷举只贡献常驻成本与重叠面。改动 description 前 MUST 先过披露册的逐词判据：正匹配信号（核心名中英双面、贴用户说法的触发动词、自然措辞的 when-to-use）删之伤匹配；遮蔽源（宽泛适用面、方法论名词、触发词穷举）删之是安全收益。

#### Scenario: 形态骨架维持
- GIVEN 本技能的 description
- WHEN 逐项检查形态
- THEN 对象界说职责句、动词面工作枚举、中文别名、两条自问信号、一条反向条件齐备，无触发词穷举与结构化标签

#### Scenario: 改前先过逐词判据
- GIVEN 计划修改 description 的某个短语
- WHEN 执行修改
- THEN 先在披露册逐词判据下判定该短语是正匹配信号还是遮蔽源，再决定删改
