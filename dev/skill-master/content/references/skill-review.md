# 审查一个技能

## 定位与边界

- 审查回答一个问题：这个技能写得对不对。判定围绕两套依据——技能自己的
  承诺（声明的边界、每条约束与锚定结论）与通用标准（内容质量四标准、开放
  标准的结构要求）。
- 审查对象是文字承载的判断依据与结构，不是运行时行为——行为不对往往是
  文字不对的征兆，这条线索归症状排查形态。
- 审查只读不修，产出是问题清单，不是修改后的文件；修复转修改工作。机制：
  审查与修改是两种注意模式，看到问题就动手，剩下的面就没人扫了。
- 与验证的分工：审查判「写得对不对」（逐维读文字），验证判「零上下文用
  不用得起」（无上下文 agent 走一遍、查「写全了没有」）；验证发现的卡点
  常是某维度失守的具体表现，作为审查输入。
- 判定需要锚点：先对照技能的设计意图（配套设计文档或 SKILL.md 声明的
  边界）再判——「不管什么」的范围里没做不是缺陷，宣称的承诺没兑现才是。
  没有锚点的审查输出的是审查者自己的口味。

## 两种输入形态

- **全量评判**：给定技能，按七个维度过一遍，输出整体质量判定。用于交付
  前体检、重大改动后复查、周期性维护。
- **症状排查**：从「行为与预期不符」倒推根因。走法：锁定症状（什么输入、
  期望什么、实际得到什么）→ 沿触发链追（description 宣称 → SKILL.md
  路由 → 论述段依据）→ 回到审查维度给根因定性。产出是定位与依据，不是
  补丁；定位后转修改执行。
- 两条形态共用同一组审查维度，只是走法不同：撒网找问题 vs 先锁症状再沿
  链追根。

## 审查维度

七个维度是走查时要过的七盏灯，每盏灯亮起都要能指出具体位置与判据：

- **合规**：结构与元信息符合开放标准——文件在不在、frontmatter 全不全、
  披露是否渐进、引用是否一层深；机械细项见
  [standards.md](general/standards.md)。不合规的结构让技能在别的环境加载
  失败，文字再好也到不了读者眼前。
- **一致性**：引用文件实际存在；术语跨文件一致、概念定义唯一；自符合——
  声明的每条约束自己做得到。
- **触发面**：逐词扫 description——正匹配信号足不足、遮蔽源多不多（宽泛
  适用面声明、方法论名词、触发词穷举）；判据与方法论见
  [disclosure.md](general/disclosure.md)。
- **零歧义**：主观模糊词有量化或判据；无隐含假设（默认读者知道项目内情、
  前次讨论结论）；术语就地定义。机制：技能读者是零上下文，文档自身是唯一
  语境。
- **化石**：成品格式化石（一次交付形态与个案规律冒充方法论——判别问句：
  这是给未来执行者的判断原则，还是上次交付物的残片）；委托边界泄漏（把
  判定维度、预期路径交给执行者，摧毁委派换来的隔离——判别问句：读者知道
  这条后行为怎么变）。
- **no-op**：逐句问「删了行为变吗」；弱引导词（请注意、务必理解）不承载
  行为变化就是噪声。句子级判定标准在
  [writing-craft.md](documents/writing-craft.md)，这里应用它。
- **结构**：层次挣不挣存在——标题、小节、文件去掉后内容是否更直接；文件
  与层级由内容重量支撑还是继承自旧框架。

## 判定与产出

- 问题清单按严重度三级分级：阻断（直接误导行动或技能整体失信：自相矛盾、
  断链、宣称未兑现）、显著（某维度局部失守，可绕行）、轻微（措辞呈现）。
  分级理由：修改工作按严重度排投入顺序，不分级的问题是倾倒。
- 问题与修法分离陈述：报告写哪里、是什么问题、为什么是问题；修法留给修改
  工作（修法要结合动手语境，审查者没有）。结构性方向可以给，具体改法是
  代修。
- 「缺陷还是设计如此」过三档过滤：本质原因（有对错，报）、美观偏好（最多
  标注「偏好」）、习惯（不报）。判据：这条有正确与错误之分吗。结论要落到
  具体维度与判据，「总体还需打磨」是无法验证的空话。

## Gotchas

- **验证者偏见**：「我能读懂」说明我自带作者同款上下文；秒懂不是绿灯是
  警报。对策：逐句问「零上下文读者到这里会卡吗」，或交独立子代理全新
  上下文。
- **过度纠错**：把设计如此误报为缺陷。对策：报每条前自问它违反七维里哪
  一条、违背哪个锚点，答不上来就收回。
- **抓小放大**：精力耗在措辞上，漏掉结构层病灶。对策：先看骨架（结构、
  合规、一致性）再看局部（no-op、零歧义），细节留第二遍。
