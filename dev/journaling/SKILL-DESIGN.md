# journaling 设计锚定文档

## 本文档的定位

这是 journaling 技能的**设计锚定文档**——记录这个技能为什么这样设计、修改时哪些约束不可破坏。读者是接手维护这个技能的开发者，不是寻找技能使用说明（那在 SKILL.md 和 references/ 中）。

本文档遵循 AGENTS.md §2.5/§4.2：只锚定本技能特有的设计方向、原则、目标及其理由；不记录通用技能设计方法论（AGENTS.md 已固化）、不记录技能内容（SKILL.md/references 职责）、不记录历史（CHANGELOG 职责）。

更新时机：仅当本技能的设计意图或方向变化时更新。局部实现、措辞、bugfix 不触发更新。

## 设计意图

这个技能解决什么问题？**Agent 是跨 session 的，但记忆不跨 session。** 每个新 session 从零开始：不知道之前积累了什么经验、做过什么决策、踩过什么坑。没有结构化长期记忆的 agent 每轮都在重新学习。

journaling 为 agent 建立一套结构化的长期记忆笔记系统：有入口（INDEX.md）、有条目规范、有维护周期。它解决的四个具体问题：

- **"写了不读"**：经验记下来了，但下次遇到相关任务时不会先查阅
- **"写了找不到"**：信息存在但无法在需要时快速定位
- **"写了变噪音"**：INDEX.md 膨胀，信号被淹没在日志中
- **"写了不维护"**：条目过期、标签蔓延、结构腐化，但无人清理

## 设计目标

**指导 agent 自发形成一套持续演进的长期记忆笔记系统**——在日常工作中自然地沉淀经验、决策与知识，系统随使用持续演化，使每个新 session 都能从先前状态继续，不需要从头积累。

"自发"是关键：技能不是规定 agent 必须记笔记，而是让记笔记成为自然行为；"持续演进"：不是一次性建好系统，而是系统随内容生长。

## 关键架构决策

每个决策记录：方向、理由、不变量。这些是修改时不可破坏的约束。

### 1. 读写非对称——读不加载，写才加载

**方向**：读取 journal（浏览 INDEX.md、查阅条目、搜索内容）不需要加载本技能；只有写入或维护时才需要加载。

**理由**：journal 是 agent 每轮启动都要读取的——INDEX.md 是启动协议的第一步。如果每次读 journal 都要加载技能，上下文成本不可接受。读写分离让"读取"保持零成本（INDEX.md 是自描述的状态封面），把技能的全部复杂性推到"写入"侧——写入时才需要规范，维护时才需要协议。

**不变量**：INDEX.md 的协议声明行必须标注"读此文件不需要加载 skill · 写入或维护时必须加载"。若技能未来为读取增加加载要求，违反本决策。

### 2. 内容自管理——规则文档单入口 + 方法论，journal 自演化

**方向**：分类、标签、约定等内容组织规则由每个 journal 自管理——统一落在规则文档（RULES.md，技能绑定的唯一规则入口）中；技能只提供种子和设计方法论，不预设框架。

**理由**：技能预设的框架（分类、标签）服务于设计者自己的使用模式，不适用于其他 journal。把"你该用什么分类"固化为技能要求 = 把特定 journal 的经验强加给所有使用者。技能提供的是"如何设计规则"的方法论（design-rules.md），让每个 journal 从自己的内容推导出适合的结构，在维护中演化。规则统一单入口（而非多文件）是为了让写入/维护协议只面对一个入口，规则如何内部组织（多文件/板块）由 journal 自定。

**不变量**：技能不得固化任何 journal 特定的分类方案、标签集或目录结构作为强制要求。种子（RULES.md 初始分类/tag/字段方案）是可改默认值，不是规范；规则文档入口名（RULES.md）由机制绑定，其内容自定、可自组织为多文件。

技能内容中仅以下 5 条硬性可确保存在：INDEX 可发现性保证（发现合约）、读取/写入技能不对称加载、INDEX 作入口、RULES 作规则纪录（单入口、必读、必须存在）、笔记文件必须含 YAML 段。除此之外的任何机制（分类、标签、字段、目录、INDEX 板块、维护信息等）均为引导性建议——技能表述不得假定其在真实场景中存在（如点名 INDEX 具体板块、要求必填字段、断言种子目录存在），否则破坏表述一致性。新增或修改技能内容时以本清单为边界。

### 3. 删除即归档——delete 不是合法操作

**方向**：journal 中不存在"删除"操作。所有"应该删除"的信号执行"移入 archive/"。包括日常操作与维护期间（维护协议的操作规范明令：整个维护过程中不删除任何文件）。

**理由**：删除是不可逆操作，与 journal "可逆维护" 的设计原则冲突。archive/ 提供等价出口——保留历史信息同时移出活跃区域。agent 的执行可能出错，删除无法回退，归档永远可回退。

**不变量**：任何文档中"删除"的表述都指向"移入 archive"。不存在"冷却期后硬删除"的路径——文件一旦移入 archive 即永久保留。若发现"硬删除""冷却期后删除"等残留表述，是设计回归。

### 4. 信息依赖优于规则闸门

**方向**：让 agent 从信息缺口中得出行动依据，而不是靠规则条文约束。"将必须读 INDEX.md 写为规则"时 agent 可选择跳过；"将 INDEX.md 中有什么写为事实陈述"时，跳过意味着承认自己在信息缺失中操作——这需要更高的认知成本来合理化。

**三层信息依赖结构**：
1. **description**（加载决策点）：操作边界——"什么操作需要我"
2. **SKILL.md 正文**（技能加载后）：信息依赖声明——"我需要 INDEX.md 中的什么"
3. **INDEX.md**（读取时）：价值自述——"我包含什么，跳过我的代价"

**不变量**：技能靠信息缺口驱动 agent 行动，不靠惩罚条款。维护协议中质量检查的必要性通过论述传达，不写"违反的代价"。

### 5. description 是操作范围约束，不是场景枚举

**方向**：description 声明操作边界——"什么类型的操作需要本技能"（任何 journal-root 写入性操作），而非枚举触发场景（"写条目/维护/捕获决策"时加载）。

**理由**：场景白名单必定腐烂——总会有新的说法遗漏。操作边界「任何写入性操作」比场景白名单稳健：不管用户说"归档"还是"把那个移走"，只要操作落到 journal-root 写入范围内，约束生效。操作边界由 agent 的工作方式（调用写入工具）定义，不由用户措辞定义。

**不变量**：description 保持"操作范围约束 + 写入操作示例"结构，不退回场景枚举。

### 6. 维护协议三分离——流程推荐化、红线集中化、启发性独立化

**方向**：维护协议按三个职责分离设计——流程推荐化（流程是默认值，可调整）、红线集中化（硬性要求唯一集中地）、启发性独立化（启发主体）。当前落实为四段结构（概述、推荐流程、操作规范、补充论述），段落形态可随内容调整，三分离不可破坏。

**理由**：维护是技能中唯一承载"演化"的文档，同时包含"流程"（可调整）与"底线"（不可违反）两类约束。若把两类约束混在同一套步骤中，agent 无法分辨"哪些可灵活、哪些是红线"。三分离让流程推荐化（默认值可调整）、红线集中化（操作规范唯一集中地，可审计可演进）、启发性独立化（补充论述承载"怎样跳出框架"）。

**不变量**：
- 硬性要求（"必须/禁止"措辞）只出现在操作规范段，推荐流程中不出现强制措辞
- 推荐流程是默认值而非规范——agent 可理解动机后自行调整
- 维护的启动由 agent 判断或用户要求触发，不是自动流程（无触发信号机制）

### 7. 协议设计方法论——远征型 vs 内嵌型

**方向**：协议文档按操作场景分两类设计。远征型（初始化、维护）：任务独立、步骤多、边界清晰，每步需要 why，强边界约束。内嵌型（写入、导入）：嵌入主线工作、高频率、低延迟，仅开头定位说明，不提供逐步骤 why。

**理由**：两种模式的核心约束不同。用远征型的设计范式套内嵌型不是不够好——是方向错了。设计 protocol 时必须先判断操作场景再落笔。

**不变量**：新增 protocol 时先判定其场景类型（远征/内嵌），再按对应范式设计。

### 8. 理解验证 ≠ 质量检查

**方向**：决策前验证（理解验证）与交付前检查（质量检查）是两个不同环节。

| | 理解验证 | 质量检查 |
|---|---------|---------|
| 时机 | 决策前 | 交付前 |
| 问题 | "我读对了吗" | "我做得对吗" |
| 内容 | 确认数据解读无误 | 确认结构未劣化、内容未遗失、合规、交付完备 |

**理由**：只有交付前检查没有决策前验证——如果决策时数据解读有误，质量检查依然会通过（输出格式正确，但方向错了）。维护协议中，设计阶段前确认扫描数据解读无误，就是理解验证；维护完成后的双重质量检查，是交付检查。

**不变量**：任何含"先理解现状再决策"的流程，都必须保留决策前的理解验证环节。

### 9. 目标前置——协议开头描述完成状态

**方向**：每个 protocol 开头说明"做完这个想达到什么状态"。

**理由**：提供操作终点（知道什么时候算完成）、提供判断依据（以是否朝向目标做取舍）、减少迷失感（序列执行过半时可能忘记为什么做这些步骤）。远征型协议展开为完整节，内嵌型仅保留 2-3 行定位说明。

**不变量**：新增或重写协议时，开头必须有完成状态描述。

## 措辞风格约定

- **第一人称**："我记的，我用的"——journal 是 agent 自己的笔记本，不是外部要求
- **中英混合**：结构性内容（frontmatter、标签）用英文，解释性内容和操作规则用中文
- **元语境渗漏是已知问题**：技能文档中普遍存在把"这段文本是给你的推荐/示例"写进文本本身的模式（如"供你参考""你可以根据实际情况"）。暂不系统性处理，但新增内容注意不强化此模式——默认以陈述句描述做法。

## 维护注意事项

- **操作规则是活文档**：SKILL.md 的 Operating Principles 在遭遇新的操作失败时追加。新增规则用指令式措辞，不夹带历史溯源——历史案例属于 journal 经验条目，不属于技能规范。
- **SKILL.md 的路由表和 Linked Files 要同步**：新增或移除 reference 文件时，两个位置都要更新。
- **泛化与脱敏**：技能从特定运行环境迁移而来。示例用通用占位符，journal 路径用 `<journal-root>` 参数化。维护时保持通用性——不回填特定项目名或硬编码路径。
- **硬性要求只进操作规范**：新增"必须/禁止"类要求时，写入维护协议的操作规范段，不在推荐流程中散落强制措辞（决策 #6 不变量）。
- **删除语义统一**：任何文档中"删除"的表述都指向"移入 archive"（决策 #3 不变量）。
