# 多场景知识库验证推演
> 场景文档 — 配合推演通用论述（`../rehearsal-guide.md`）参考使用，补充知识库载体的特化内容。

将推演方法应用于知识库（多文件决策树）的验证。适用于知识库重构后或新建后的完整性检查。

## 本载体的核心差异

知识库的消费模式是**决策树分支**——执行者按分支选择路径，而非线性阅读全部文件。因此需要在通用论述的推演流程上叠加**多角色 × 多路径**组织方式：一个知识库推演 = 多个独立场景推演的组合，每个场景一个角色、一条路径。

注意区分两个层面：**决策树**是入口文档中的分支导航（消费路径——接收方在入口处选择走哪条分支）；**网状关联**是文件间的链接结构（组织形态——分支路径上的文件之间靠交叉引用衔接）。两者是同一载体的两个层面：分支路径上从一个文件跳到下一个文件，靠的是文件间的网状引用。

与文档库（[doc-guide-rehearsal.md](doc-guide-rehearsal.md)）的区别：文档库针对**单一对象或范畴**（如代码库、技术方案），文档之间通常是**树状且有序**的；知识库包含**多种不同范畴**的知识和实体，文档之间是**网状关联**的。即使两者方法相似，边界场景和信号侧重不同——推演前先确认载体是哪种形态，再决定是否使用本文件。

## 角色矩阵设计（推演场景的组织）

设计 4-6 个典型使用场景（场景数随主要分支数扩展，4-6 为典型规模；分支较多时按需增加），每个场景定义：

- **角色**：什么身份、什么知识水平、什么目标
- **路径**：在入口文档的决策树中走哪条分支、依次加载哪些参考文件
- **验证点**：可逐项判断的具体问题（用于多轮迭代时验证修复是否生效，见下文）

角色矩阵的覆盖要点（提示性，按知识库形态取舍）：

- 覆盖决策树的**每条主要分支**（漏掉的分支 = 漏掉的推演）
- 含跨文件场景——需要从文件 A 跳转到文件 B 才能完成目标（网状关联的典型消费方式）
- 含诊断/修复类场景——执行者带着问题来，需要先定位再修复
- 含边界场景——信息缺失、误解、跳过某步

场景数较多（≥ 5 个）时，按 [batch-execution.md](../supplementary/batch-execution.md) 的批量并行执行方法组织推演。

## 逐场景推演（P2-P3 的执行方式）

每个场景都是独立的一次推演，**每切换一个场景就重新进行 P2 身份转换**——不同场景的执行者身份不同，身份设定用角色矩阵中为该场景定义的角色。

逐场景走完整链路：

```
入口文档（主文件）
 ↓ 读到决策树，选择分支
 ↓
参考文件 A（加载、阅读）
 ↓ [交叉引用应该在此触发]
 ↓
参考文件 B（跳转）
 ↓
模板目录（复制使用）
```

记录每步的停顿、误解、卡死。知识库场景中特别值得留意的信号（P3 留意之处补充）：

| 信号 | 含义 |
|------|------|
| "这里需要跳到 X，但文档没告诉我" | 交叉引用断裂 |
| "这个概念在文件 A 和文件 B 用了不同名字" | 术语不一致 |
| "我读完了但不知道下一步该做什么" | 缺少回链或退出指引 |
| "这两段话在说同一件事，但我不知道哪个是权威" | 内容重叠无分工 |

## 边界与异常场景（P4 补充）

| 异常场景 | 检查目标 |
|---------|---------|
| 跳过某个参考文件直接到下一步 | 承载"跳过的文件"中的关键知识的后续文件还能站住吗？ |
| 从中间进入（直接从参考文件开始，没读主入口） | 参考文件自包含吗？还是依赖主入口的上下文？ |
| 误解关键术语 | 术语是否在首次出现时有定义？跨文件是否一致？ |
| 参考文件和模板同时存在同一主题 | 分工明确吗？执行者知道先读哪个吗？ |

## 评估整理（P5 的要点）

**严重程度格式：** 阻塞/缺陷/建议。三级定义：

- **阻塞**：执行者无法完成目标（如全流程卡死点）
- **缺陷**：执行者能走完但质量受影响（如交叉引用断裂——若断裂发生在完成目标的必经路径上，导致读者无法继续，则属阻塞）
- **建议**：文件结构或措辞改进

**跨版本测量工具：** ★ 1-5 仅用于多轮推演中的量化追踪（见下文「多轮迭代修复验证」），**不是严重程度格式**。

**评估维度提示（额外提示，非硬性指标）：**

| 评估维度 | 含义 |
|------|------|
| 全流程可执行性 | 从入口到完成目标，按指引走能完整走通吗？ |
| 模块流转清晰度 | 每个文件的输入/输出/交叉引用清晰吗？ |
| 术语全局统一 | 关键概念在所有文件中名称一致、定义一致吗？ |
| 覆盖完整性 | 决策树的每条分支都有足够的深度支撑吗？ |
| 异常容错 | 跳步、误解、从中间进入时能 recover 吗？ |

**复现对照注意（P5S1）：** 回到 P1S3 整理的作者意图（编写时的理解），按四向对照每个场景角色的复现理解。同一位置在不同角色推演下表现不一致的发现，往往是结构性缺陷，而非个别文件问题。

**错误模式搜索候选（P5S5）：**

- **交叉引用断裂** — 文件 A 引用文件 B 但链接无效或方向错误（知识库最高频缺陷）
- **内容重叠无分工** — 参考文件和模板覆盖同一主题但分工不明确
- **从中间进入时上下文缺失** — 参考文件不自包含，依赖主入口的上下文

## 多轮迭代修复验证

单轮推演只能发现问题，不能验证修复是否引入了新问题。对于重构幅度大或缺陷数量多的知识库，可以采取多轮推演：修复后重新推演，跨轮次对比。

### 轮次设计

| 轮次 | 角色 | 场景类型 |
|------|------|-------------|
| **Round 1** | 发现基线 | 全新场景，覆盖所有决策树分支 |
| **Round 2** | 验证修复 + 暴露新问题 | 60% 回归（重新走 Round 1 中最弱场景）+ 40% 新场景（覆盖本轮新增特性的验证点） |
| **Round 3+** | 收敛确认 | 仅回归修复项 + 1-2 个新增边界场景 |

### 回归场景设计

回归场景的核心要求：**与原始场景同角色、同路径，但验证点全量更换为本轮修复点**。这是判断修复是否生效的最可靠信号——同角色同路径保证可比性，验证点更换保证测的是修复而非重复旧发现。

### 得分追踪与收敛

跨轮次对比同一维度的评估得分变化（★ 1-5 的用途所在）。打分方法：每轮推演后，对各评估维度按场景汇总给出 ★ 1-5（1=完全不满足，5=完全满足），该轮平均分 = 该轮所有场景各维度分数的均值：

```
Round 1 平均: 3.74/5（异常容错 2.9/5 最弱）
Round 2 平均: 4.52/5（异常容错 3.6/5，+24%）
Round 3 平均: 4.53/5（持平，新增缺陷全为建议级）
```

**收敛信号**：当两轮之间的平均分变化很小（参考阈值：变化 < 0.1）且无新增阻塞/缺陷级发现时，继续迭代的边际收益递减——可以把剩余低优先级缺陷记录到已知限制中，停止迭代。

### 示例：角色矩阵

（对应上文「角色矩阵设计」；多轮迭代的回归场景示例见「回归场景设计」）

某设计方法论文档知识库的 10 场景推演（节选）：

| # | 场景 | 角色 | 路径 |
|---|------|------|------|
| 1 | 从零开始设计 | 中级工程师，第一次使用这套方法论 | 入口 → 结构设计 → 内容写作 → 工具设计 → 模板 |
| 2 | 诊断行为异常 | 维护者，产出上线后不按预期工作 | 入口 → 反模式诊断 → 定位问题 → 对应参考 |
| 3 | 安全审查 | 审查者，上线前审核 | 入口 → 安全相关 → 运维相关 |
| 4 | 跨环境迁移 | 团队负责人，从环境 A 迁移到环境 B | 入口 → 模型特定 → 内容写作 |

关键经验：知识库中"交叉引用断裂"高频的结构性成因是——参考文件独立性强但互联性弱；参考文件和模板的内容重叠则是另一个常见问题类型。
