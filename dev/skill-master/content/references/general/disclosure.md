# 披露设计论述（disclosure）

> 本文档是 skill-master 技能 general 分册的披露设计论述：技能通过
> description、触发面与命名向加载器与用户呈现自身，本册给「怎么呈现才
> 既被命中又命中得准」的判断依据。读者前提：默认已读 SKILL.md 的前提节
> 《什么是一个好的技能》。本册只写披露这一面——description 字段的格式
> 约束见同册 standards.md，句子级手艺见 ../documents/writing-craft.md。

## 披露是什么

- 定义：技能包写得好还不够，还要能被找着、被认对。**披露 (Disclosure)**
  是技能向加载器与用户呈现自身的全部接口：description（匹配面文本）、
  触发面（description 与触发词共同决定的「会被语义匹配命中」的词汇面）、
  命名（目录名与 `name`，兼作中英核心名的称呼通道）。
- 为什么披露值得单独成册：正文质量决定「加载后好不好用」，披露决定
  「会不会被加载、被谁加载」。命中前 agent 看不到正文，只有 description
  可见；命中失败技能等于不存在，命中错误则把一份「表面合理、实际无关」
  的内容注入执行流——比不命中更隐蔽，因为它被当作权威使用。
- 目标不是「短」而是「精准」：正匹配信号足、与相邻技能区分度高、常驻
  成本小，三者同时成立才是好披露。

## 加载器机制

- 加载器在会话开始发现可用技能，把全部技能的 name + description 注入
  上下文；匹配是纯语义判断而非向量检索，description 是选择时唯一可见的
  接口；命中之后正文才被加载。这个机制派生两条直接推论：
  - description 每次会话常驻，每个词都是净成本——它不只在触发那一刻被
    读，而是全程占窗口、全程参与与其他技能的相互遮蔽。所以方法论展开、
    流程清单都不属于这一层，正文只在命中后付费。
  - 选择在全部 description 之间进行：某个技能 description 的词与相邻
    技能重叠越多，无关任务越容易按表面相似选中它——宽泛词的成本不只
    属于自己，还抬高相邻技能的误选率。
- 两条实证划定取舍边界。其一，技能库从少量扩到两百级时，任务通过率最多
  下降约两成，其中约七成可归因于选错技能而非上下文膨胀——选错的技能把
  「表面合理但错误」的推理注入并被当作权威，且不像工具报错那样可检测。
  其二，工具选择准确率随上下文长度对数衰减：即使正确候选项排在最前，
  窗口拉长仍稳定拖低选择准确率。两条合读：常驻层里每个多余词都在两个
  方向同时付费。
- 触发成败由词的性质决定，不由长度决定：全由方法论名词堆成的极短
  description 会漏触发，而由触发者自然语言写成的较长 description 触发
  良好。判断单位是词的性质，不是总长度——这决定了下面的逐词判断框架。

## 逐词判断：正匹配信号 vs 遮蔽源

写 description 时对每个词或句子问：它是正匹配信号，还是遮蔽源？

- **正匹配信号**：帮助正确技能被命中的词，保留——删它才伤匹配，是唯一
  有退化风险的方向。
- **遮蔽源**：看似扩大命中面、实际增加与相邻技能重叠的词，收敛——删它
  降误选、省常驻成本，是安全收益。
- **纯方法论词**：既不贴近用户说法也无区分价值，移入 SKILL.md 正文，
  不占匹配面。

信号类（保留）：

- **核心名中英双面**：用户可能用中文名或英文名指代同一个技能，双名各占
  一条匹配通道；缺一面，该语言侧的整条触发路径就失明。
- **贴用户说法的触发动词**：用户首话怎么说、agent 自问怎么说，description
  就怎么写——口语化的职责动词与语义判断的相关性最高，是命中信号的主体。
- **when-to-use 一句自然措辞**：让模型判断「当前任务正落在本技能的场景」，
  这是选择动作本身要找的东西。

遮蔽源类（收敛）：

- **宽泛适用面声明**（「任何 X 场景均可」）：与相邻技能大面积重叠，任务
  要 A 时，B 的宽泛声明常常比 A 自己的精确说法更「表面像」。
- **方法论名词**（阶段名、框架名、流程清单行话）：用户不这么说话，相邻
  技能往往也这么宣称——重叠词只有遮蔽贡献，没有命中贡献。
- **触发词穷举**：罗列几十个近义动词，边际命中收益趋零，却在每个相邻
  技能的词汇面上叠加重叠与常驻成本。

安全边界一句话：退化风险只存在于删正匹配信号，删宽泛面是安全的；拿不准
一个词属于哪类时，问「用户或 agent 会自然说出它吗」。

## 两条触发路径

- 命中来自两条路径，description 必须同时给两条留信号：
  - **用户路径**：用户在首话直接提需求——点名技能、说出职责动词、描述
    场景。措辞要贴近用户会用的自然说法。
  - **agent 路径**：agent 在执行中自问「现在该不该动用某类职责」，典型
    场景是交付物刚完成后的自我检查。措辞要贴近 agent 面对状态时的自问句。
- 只覆盖一条是常见的漏触发形态：触发场景若全以「做完 X 之后」开头，只
  命中用户路径的成品场景，agent 交付后的自问就无词可呼应。两条路径各配
  各自的中英自然措辞，缺一条就漏掉半边使用场景。

## 反向条件最小化

- 不触发条件对命中面没有贡献，还有反作用：核心词一旦出现在「何时不使用」
  的语境里，语义模型即便字符命中也会被劝退语义带偏而倾向判负——把技能名
  写进反向句，等于亲手把命中信号变成拒绝信号。
- 因此 description 里至多保留一句反向条件，选最关键的单一误触发场景
  （通常是和相邻技能最容易混淆的那一个）；完整的合触发/不合触发/边界判定
  放 SKILL.md 正文——命中后才加载，不占匹配面。

## 不误指向

- 不指向不存在的独立技能：references 下的文件不是技能，不能被加载器
  加载。正文或 description 一旦写成「详见 XX 技能」，agent 会以为另有一个
  可加载的技能而去找它，结果漏触发本技能——这是反向误导的失效形态。
- 需要给读者指路时，给同一技能内的正文位置或功能描述，不给假技能名。
- 同一原则的延伸：description 声明的能力必须是技能真实提供的。命中后
  兑现不了的声明，等于把「表面合理」的期待注入执行——与遮蔽同一种病。

## 与 SKILL.md 的分工

- description 是匹配面，SKILL.md 正文是决策依据：description 常驻、短、
  只放命中所需（做什么、何时用、必要时一句反向）；SKILL.md 命中后全量
  加载，承载展开的触发判定、能力边界与路由。
- description 被命中后也会被当作技能简介读一遍，因此保留一句自然的
  「是什么」兼顾可读；与匹配冲突时匹配优先——但一句自然简介通常同时
  服务两者，冲突没有想象中频繁。
- 检验判据：对 description 里每个词问「命中之后这句话还有用吗」，对
  SKILL.md 每句话问「不命中时它会被读吗」——前者只属于正文，后者只属于
  description。边界由此可机械地扫出来。
- 命名是披露的第三面：目录名、`name` 字段与正文称呼共用同一个核心名，
  改名要三处同步且动摇用户习惯，涟漪比任何正文编辑都大——披露设计把
  命名当作身份决定来处理，先于 description 措辞稳定下来。
