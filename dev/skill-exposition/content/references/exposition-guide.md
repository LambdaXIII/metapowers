# 技能阐述通用论述

> 先读本文件即可完成一次基本阐述——提取基础、陷阱框架、默认结构方案、源一致性裁决齐备；其余参考文件按需加载，提供启发与深化（清单与加载时机见 [SKILL.md](../SKILL.md)）。

---

## 1. 定位与交付物

本技能把技能内容转化为**说明文**——面向人类学习者、以"学会使用"为目标的完整呈现。

**三条硬约束**（从"学会"目的直接推出）：

- **忠实性**：完整、准确；不歪曲、不省略、不劣化源内容。学习者学到的必须就是你设计的技能。
- **可读性**：流畅、有条理，适合人类阅读。材料是教材，不是 agent 指令的复述。
- **自包含性**：产物是学习者的唯一依据——包含理解所需的全部前提与知识（含技能之外但叙述所需的内容，如环境前提、外部概念）；绝不反向链接到技能内部文件（如"详见 SKILL.md 第 X 节"）。

**交付物形态**（由输入范围决定，见第 2 节）：

| 输入 | 输出 |
|------|------|
| 单个技能 / 单个方面 | 单篇说明文 |
| 多个技能（各自完整） | 每技能一篇说明文 |
| 跨技能的某个方面 | 单篇整合说明文（每段标注来源技能，标注方式见 [general/multi-skill.md](general/multi-skill.md)） |

篇幅过大时可拆为章节文件，但保持单篇逻辑整体。

**语言**：与学习者一致；专业术语首次出现时附源语言原文（如「说明文（exposition）」）。源内容本身混排语言时（如中文叙述夹杂英文整节），先识别性质再处理：专业术语 → 保留原文并附学习者语言翻译；行文风格（叙述、句式所用的语言）→ 统一为学习者语言。产物整体语言必须一致。

**行为边界**：只读源文件、不修改；不执行、不测试被阐述的技能；不评价技能好坏。

## 2. 梳理（提取）

### 2.1 确定范围

输入范围由用户指定，**不假定完整技能**：

- 完整技能包
- 技能的部分方面（如"质量检查机制"）
- 多个技能（含跨技能的方面，如"这几个技能的委派机制"）

"技能"判定：含 SKILL.md 的技能包目录。

### 2.2 定位分布

一个方面可能**跨多个源文件分布**。确定范围后，先在源中定位范围内内容涉及的全部位置——SKILL.md 正文、frontmatter、references/、templates/、examples/、CHANGELOG.md 都可能承载范围内的内容。定位不全 = 提取必然遗漏。

### 2.3 提取要素

从定位到的内容中提取：

- **定位与触发**：这个技能解决什么问题、何时用、何时不用
- **能力与流程**：技能做什么、按什么顺序做
- **规则与边界**：阈值、条件、例外、约束
- **示例**：典型用例（场景、输入、输出）。templates/、examples/ 等制式性内容（模板、清单、格式规范）先判断呈现形态：内容价值在**格式本身**（规范性强的模板、清单、格式规范）→ 原样保留；内容价值在**含义**（叙述性示例、场景演示、用例说明）→ 转述为说明文语言
- **设计理由**：源中有则提取；源中没有但可合理推断的，按 3.3 的推断纪律处理

梳理中遇到某类内容时，按需加载对应的提取提醒（工作流程型 / 知识库型 / 规则决策型 / 案例型 / 设计思想型——见 [SKILL.md](../SKILL.md) 的参考文件清单）。

### 2.4 源一致性裁决

检查源文件之间的显式矛盾（同一事项在不同来源中描述互相冲突）：

| 检查项 | 说明 |
|--------|------|
| SKILL.md 内部一致性 | 流程描述与约束声明是否矛盾 |
| frontmatter vs body | description 与正文定位是否一致 |
| SKILL.md vs references/ | 关键信息是否一致 |
| SKILL.md vs templates/ | 模板内容与流程描述是否一致（仅当存在） |
| metadata vs CHANGELOG | 版本号是否对应（仅当存在） |
| 数值/阈值 | 同一数字在不同位置是否一致 |

发现矛盾时的裁决策略：

| 矛盾类型 | 裁决策略 | 理由 |
|----------|----------|------|
| SKILL.md 内部矛盾 | 以约束部分为准 | 约束通常比流程更审慎 |
| frontmatter vs body | 以 body 为准 | description 是摘要，body 是完整表述 |
| SKILL.md vs references/ | 以 SKILL.md 为准 | references/ 是辅助材料 |
| SKILL.md vs templates/ | 以 SKILL.md 为准 | 模板可能滞后 |
| metadata vs CHANGELOG | 以 CHANGELOG 为准 | CHANGELOG 是版本权威 |
| 数值型矛盾 | 并列呈现，标注矛盾来源 | 数值无法自动裁决，不擅自合并 |

无法裁决的矛盾在说明文中**并列呈现并标注**，不替学习者做决定。

## 3. 陷阱四类（框架）

每类给出本质、典型表现、自查句。深化案例见 [general/traps.md](general/traps.md)。

### 3.1 内容失真

**本质**：说明文与源内容不一致——省略、歪曲、劣化、添加源里没有的内容。
**典型表现**：规则缺了例外；阈值被四舍五入；条件丢了兜底分支；"顺手"补了一条源里没有的规则。
**自查句**：源里的每条规则都在说明文里出现了吗？阈值、条件、例外原样吗？有没有哪句是我"补"的？

### 3.2 视角漂移

**本质**：阐述的是技能**处理的主题**，而不是技能**本身**。例如阐述一个安全扫描技能时，写成了安全知识教程。
**典型表现**：大段介绍主题领域的背景知识，技能自身的机制反而模糊。
**自查句**：每一段都在讲"这个技能如何工作"，而不是"这个主题是什么"吗？

### 3.3 推断未标注

**本质**：补充"为什么"时把推断当成原文呈现。
**纪律**：

| 类别 | 处理 |
|------|------|
| 可推断（约束反推 / 行业常识 / 流程逻辑） | 允许补充，必须标注 `[推断: 依据]`，如 `[推断: 基于约束反推]`。约束反推 = 从约束本身推出其存在的理由（如"上限 5000 行"→"防止上下文溢出"） |
| 不可推断（设计者主观取舍 / 需项目上下文 / 超出领域） | 不推断，标注 `[未推断: 原因]` |
| 无法确定是否可推断 | 不推断，标注 `[未推断: 无法确定]` |

### 3.4 语体残留（认知面）

**本质**：把说明文写成了指令复述——"你应该…""第一步：…""禁止…"。注意：这里只指**认知错误**（把"教人理解"做成了"转述指令"）；句式调整属行文层面——确保读到的每一句都是在陈述"是什么 / 为什么"，而非复述指令（启发见 [general/readability.md](general/readability.md)）。
**自查句**：读起来是在陈述"是什么 / 为什么"，还是在复述"你必须做什么"？

## 4. 组织（默认结构模式）

默认采用**学习路径模式**——从"知道是什么"到"知道怎么用"到"知道边界"到"知道为什么"：

1. **这是什么**：一句话定义 + 解决什么问题
2. **怎么用**：能力与流程（配合示例）
3. **边界与规则**：何时不该用、阈值、条件、例外
4. **为什么这样设计**：设计理由（推断按 3.3 标注）

组织原则（知识层，不指导文档层）：

- **知识层**（本技能指导的层面）：知识如何排序、分组利于学习——先概览后细节、相关知识点就近、术语先定义后使用
- **文档层**（不指导）：文件结构、章节划分、篇幅排版等工程细节——确保不妨碍学习者阅读
- 学习路径定义的是**内容块及其顺序**（是什么→怎么用→边界→为什么），不是章节模板：每个内容块内部的展开结构必须由该技能独有的内容决定——不同技能用同一个章节模板 = 说明文没有忠实反映该技能（反模板）

**备选模式**：交付物特征适合其它组织轴时，从 [structure/](structure/) 模式手册中另选（各手册给出完整的结构示意与权衡）。选择判据汇总如下——新模式须组织轴与现有各模式都不同才可加入本表：

| 模式 | 组织轴与适用特征 | 何时不选 |
|------|------------------|----------|
| 学习路径（learning-path，默认） | **学习顺序**：是什么→怎么用→边界→为什么；零基础学习者从头学会，预期通读全文 | 学习者以有经验的查阅者为主、诉求是快速定位某条规则 |
| 原理优先（golden-circle） | **原理顺序**：WHY→HOW→WHAT；学习者要先被说服"值得用"，存在理由是理解其余内容的前提 | 零基础新手对技能毫无概念——先讲 WHY 缺乏抓手 |
| 按知识类型分组（knowledge-types） | **知识类别**：概念/程序/规则/案例/元认知；类别界限分明、体量大，知识库型素材，学习者按需查阅 | 内容是强顺序的流程链——按类别切分会打断步骤之间的依赖 |
| 分层披露（progressive-disclosure） | **披露深度**：L1 约 30 秒 → L4 按需；学习者群体异质，内容量大且深度分级自然 | 内容短小、学习者群体单一——分层是多余的结构负担 |
| 理解深度分层（iceberg） | **理解深度**：现象/行为→模式→结构→心智模型；表层行为可观察，设计思想需前置铺垫才讲得清 | 技能没有深层设计思想——硬凑"心智模型"层会编造源中没有的内容 |
| 学习者场景导向（scenario-driven） | **学习者场景**：入门走查/任务指南/速查/原理说明；学习目的差异大，内容能按"要做什么"切分 | 学习者画像不清晰、场景只能靠想象凑出——先确定典型场景再选 |
| 六维覆盖（5w1h） | **维度覆盖**：What/Why/Who/When/Where/How 六节齐备；完整性优先于阅读顺序，周边信息与核心用法同等重要 | 为凑满六节硬写——维度齐备但内容空洞即模板化 |
| 能力树（functional-decomposition） | **能力层级**：核心能力→主要功能→子功能；能力面宽、模块可互斥切分，学习者要定位"某个功能在哪" | 能力相互纠缠（共享子功能、相互调用成网状）——强行成树会歪曲真实结构 |

示例（假想技能「会议纪要」的说明文骨架）：① 这是什么——"一个把会议结论固化为结构化纪要的技能"；② 怎么用——"三步：现场记录 → 归档 → 分发"；③ 边界与规则——"仅处理文本输入，超过 500 行不处理"；④ 为什么这样设计——"统一格式让跨时区团队结论可追踪 [推断: 基于约束反推]"。

## 5. 效果提及

交付前确保以下效果达成：

- **输出契约**：按第 1 节形态交付说明文（单篇 / 每技能一篇 / 单篇整合），内容完整；直接在回答中给出，篇幅过大或用户要求时写入用户指定位置
- **质量**：内容完整、忠实，不含源中没有的断言
- **行文**：以人类可读的说明文形式呈现（语言规则见第 1 节）
- **收尾**：对照第 3 节陷阱清单自查
