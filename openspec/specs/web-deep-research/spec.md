# web-deep-research Specification

## Purpose

本域是系统化深度网络研究技能，解决「把这个话题研究透——怎么系统地逼近真相」的问题：从明确意图，到收集线索，到交叉比对，到交付一份结论可由读者独立检验的报告。它不解决「怎么搜得快」「怎么用某个工具」「怎么判断单条信息准不准」——那是工具使用与评估方法论的事；它解决研究本身的流程设计。深度研究以彻底性优先于速度。

## Requirements

### Requirement: 行为边界
本技能的边界有三条，同时作为触发判定依据：(1) 不是快速查询工具——单点事实查询不需要本技能的方法结构；(2) 不是工具选择指南——搜索工具的选择不属本技能；(3) 不是纯咨询——没有多信源调查维度的「你觉得我该怎么做」不是研究。技能不控制研究的启动决策——触发与委托决策发生在主会话，技能被加载时研究意图已定；不设置触发闸门，也不按问句形式判定输入。输出形态按问题类型与用户预期缩放——完整报告 / 决策简报 / 精选列表，内部方法流程不随形态变化。搜索方法本身不要求报告落盘为文件——是否保存、存到哪里由使用层判断。

#### Scenario: 单点查询不进入方法结构
- GIVEN 用户只问一个可直接查证的单点事实
- WHEN 判定方法适用性
- THEN 属快速查询边界，不启动深度研究的方法结构

#### Scenario: 决策型问句合法进入
- GIVEN 用户的问句是「该不该换 Rust」这类决策问句
- WHEN 判定输入合法性
- THEN 主会话可将其合法委托为对比研究，技能不按问句形式拒绝；研究主题另行制定

### Requirement: 收集与评估严格分离
收集阶段与评估阶段之间保持硬边界：收集阶段只做线索与来源记录（含 URL），不做采信判断——不因「看起来不可靠」跳过，也不因「听起来有理」当成事实；评估阶段统一按信息性质评估。不边收集边判断。

#### Scenario: 收集期不做采信
- GIVEN 收集阶段遇到一条来源可疑的线索
- WHEN 处理该线索
- THEN 记录线索与来源，采信与否留到评估阶段统一判定

### Requirement: 问题集驱动研究循环
研究循环由问题集驱动：问题（Q）与线索（S）、发现（F）并列，是原子问询。Q 集的演化限于三类——消解（答案经验证转为发现或线索，Q 离开集合）、转化（旧 Q 过时，换成更精确的新 Q）、新增（新线索生出新 Q）；Q 不与答案一同留存。停点判定区分「不可得」（逐个 Q 的可得性事实判定：经实际调查确认无可达来源）与「收束」（问题集稳定的全局停点），两者不交叉使用。

#### Scenario: 答案不留 Q
- GIVEN 某 Q 已找到答案并通过验证
- WHEN 更新问题集
- THEN 答案转为发现（附来源），Q 离开集合，不以「问题 + 答案」形式留存

#### Scenario: 不可得不从收束推断
- GIVEN 研究循环达到收束
- WHEN 处理仍开放的 Q
- THEN 进报告「信息空白」并标注还开放；只有逐 Q 经实际调查确认无可达来源才判「不可得」

### Requirement: 主题制定
用户的提问不等同于调研的主题：主题从问题提炼而来，调研依主题展开，不以用户的原话直接展开。调研结果是针对主题的调研结果，不是问题的解决方案；成果如何解读、如何用于决策，不在本技能的指导范围内。

#### Scenario: 问题先提炼为主题
- GIVEN 用户带着决策意图提问（如「要不要换 X」）
- WHEN 展开调研
- THEN 先从问题提炼出调研主题，再依主题展开，不直接按问题拆解

#### Scenario: 成果不替决策
- GIVEN 调研完成并产出结论
- WHEN 交付
- THEN 结论是针对主题的调研结果，不含「该怎么做」的决策指示

### Requirement: 验证强度与领域规则优先
交叉验证的效力按来源独立性双向判定：差异增强——跨领域、跨语言、跨地区、跨利益立场的一致是强验证；关联削弱——同机构、同作者、同引用源头、共同利益、同测量方法的一致是伪验证，不当作独立佐证。领域特化文档定义的采信规则优先于通用规则；两者冲突时按领域规则执行，不由执行者自行裁决。

#### Scenario: 同源一致不算验证
- GIVEN 同一机构的两份报告方向一致
- WHEN 判定验证强度
- THEN 属关联削弱情形，不构成独立佐证

#### Scenario: 领域规则裁决冲突
- GIVEN 通用规则「单来源不赋置信度」与领域规则「官方原文单源可采信」冲突
- WHEN 执行采信
- THEN 按领域规则执行

### Requirement: 文档组织与编排策略边界
领域特化文档各按其研究对象的知识结构组织，不套统一模板；硬约束与启发参考截然分开（有不可妥协采信规则的领域硬约束单独成文，其余只作启发）；纯背景知识可独立成章；收束方式因领域而异；启发提示用软语气（「可以参考」「试试看」「不是必须步骤」），不写成结构要求。使用层指导（搜索策略——何时委派、拆不拆、怎么整合、跑多深、产出怎么用）与内容层方法分离成选读参考。技能内容零跨技能引用——不硬编码指向其他技能名，任何「何时用本技能」的边界判断自足表述。技能不写 harness 机制——子代理任务书、调用、验收回传不进技能内容，只写编排策略。

#### Scenario: 启发提示不写成要求
- GIVEN 某领域文档中的提示性建议
- WHEN 检查语气形态
- THEN 以软语气呈现，不写成「必须 / 禁止」类结构要求

#### Scenario: 跨技能指向即违规
- GIVEN 技能内容中出现指向另一技能名的依赖表述
- WHEN 检查引用
- THEN 判定违规，边界判断以自足表述给出，不指名其他技能

### Requirement: 触发语义
触发面覆盖深度研究请求：用户问法（查透 / 彻底了解 / 深挖等）与 agent 自问（是否值得深挖）两条路径都命中，中英文问法均在匹配面内。反向条件：单点事实查询（simple fact lookup）不触发本技能。description 不承载方法论流程名——Phase、clue-chain 等只作正文流程名，不占用匹配面（description 是选择层非方法层，纯方法论名词不产生触发信号）。

#### Scenario: 流程名不占匹配面
- GIVEN 本技能的 description
- WHEN 检查词汇构成
- THEN 只含业务措辞与触发面词汇，无 Phase、clue-chain 等方法论名词

#### Scenario: 中文问法可命中
- GIVEN 用户以「帮我查透 X」发起请求
- WHEN 判定触发
- THEN description 中文触发面命中，技能可被语义匹配选中
