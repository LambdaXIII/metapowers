# 设计一个技能

对象还不存在，或既有结构本身要动 —— 走设计。对象已存在且改动能在既有结构内完成时，是[修改](skill-modify.md)而非设计；两者的立足点不同，误判会在后面每一节放大。

## 锚定

- 锚定是设计起点：确定这个技能**提供什么、指导什么、不管什么**（下称锚定三问）。后续每一个设计决定——`description` 收敛到哪里、审查时判「缺陷还是设计如此」、修改时判改动在不在既有结构内——都以它为唯一依据。锚定没做完就动笔，后面所有文字都没有裁判。
- 锚定三问随材料与讨论逐步精确化，第一轮不必完美，但三问都要有答案。**排除项与提供内容同等必须**：没有排除项的定位必然过宽，过宽的定位后面无法收敛成有效的匹配面。排除项日后固化为 SKILL.md 的不触发条件。
- 「提供什么」的定稿形态是能力句：「提供通过 X 实现 Y 的能力」。判据在**时态**：X 必须是已被走通的做法——写成「打算」「将」「希望」时，锚定的还是愿望，能力句就退回了需求描述。
- 值不值得做，三项判据缺一不做：
  - **非一次性** —— 这类任务会重复出现；一次性任务做成技能，第二次没人用。
  - **真知识缺口** —— agent 本来就会的、搜索一次就得到的不算。缺口通常落在可靠性（会做但不稳定）、操作性（知道该做什么但做不完整）、全面性（每次都漏同一类分支）三者之一。
  - **需结构化封装** —— 散落几条笔记就能说清的，不值得一个技能包。
- 可行性看材料：撑得起一个入口（SKILL.md）加至少一份支撑文件，才成立。材料只够写满一页入口文档时，那份内容更适合放在别处（项目文档、日志条目）。
- 设计输入是已被走通、被检验的做法。为推测中的需求设计，产出的每一句都会因为无来源而悬空——这类技能在快速测试中必然卡住，且卡点是补不上的（缺的是实践，不是文字）。
- 不成熟的需求仍然可以设计：不少技能是在设计过程中才逐步清晰的，锚定阶段的产出常常就是「发现原来的需求描述错了」。判据是材料里有没有真实实践，不是需求一开始有多清楚。
- **拆的判据**：一个技能被要求装下三项以上互不依赖的职责、锚定三问已经答不圆时，拆开；拆出的每一半都能独立回答锚定三问，才算拆得动。拆不开说明它们共享一个目的，硬拆会得到两份互相引用、各自不完整的文档。另一个拆的信号是体量：正文逼近词元预算、后置到支撑文件也解决不了——那时不是组织问题，是装载了本该两个技能装的东西。

## 材料从哪来

- 材料来自真实实践，判据是「反复走通、可复现」。推测、个案、搜索即得的内容不算材料——它们进得了文档，撑不起设计。
- 实践材料按形态归位，写法各归对应参考：
  - 客观资料（参数表、规范条目、查表数据）→ 供查阅的知识，进静态资源目录（具体目录以目标环境白名单为准），是查的不是读的。
  - 步骤序列 → 工作流形态，按[写工作流文档](documents/workflow-writing.md)。
  - 判断依据（边界、取舍、判据）→ 论述形态，按[写论述型文档](documents/essay-writing.md)。
  - 稳定输出框架 → 模板，按[写模板](documents/template-writing.md)。
- 弯路与失败尝试不扔：它们构成已知失败条目的素材——失败模式是别人付过学费的浓缩，是技能里性价比最高的一类内容。但失败内容要旁置成清单并给正面对策，不写进正确路径的步骤正文。
- 约束不必一次收全。重要约束会在后续步骤自然重现，只记「不记一定会出错」的关键约束即可——「现在不收集就永远消失」的担心没有依据：为它花的时间换不回等价的信息。

## 组织与打包

- 文件组织受开放标准与运行环境的双重约束：结构怎么设计见[设计一个技能的结构](general/structure.md)（开始摆放文件结构时读），要求什么、交付前怎么核对见[让技能包合规](general/standards.md)（核对合规时读）。
- 打包目录是**放置**问题：SKILL.md 放技能根，内容按性质进 `references/`、`templates/`、`examples/`、`scripts/`（具体白名单以目标环境为准）。
- 打包与编写分离：放哪个目录与按什么方法写是正交的两轴。按打包位置找编写方法是错误路由——一份模板进 `templates/` 还是 `examples/`，写法都一样。
- 组织方向由加载成本决定：判断一句内容该放哪层，问「它每次命中都要用到吗」——不是，就后置。完整的分层判据与 references 内部的层级设计见[设计一个技能的结构](general/structure.md)。

## 编写

- 成文顺序固定：**先写支撑文件，再写 SKILL.md，最后写 description**。入口要指向真实存在、真实装着的内容；触发面在覆盖面确定之前写，必然返工。入口文件怎么组织、`description` 怎么定稿与回归，见[写入口文件](documents/skill-md-writing.md)。
- 内容形态决定写法：工作流、论述、模板各归对应的写法参考取方法，不按打包位置取。
- 句子级手艺——no-op 检验、正向陈述、量化模糊词、指针三要素——见[打磨技能文字](documents/writing-craft.md)，落笔前先过一遍。
- 约束放在它约束的对象旁边，不集中成章节。读者理解就近取材，读到被约束的那条时手里得有它。
- 技能自己声明的规范，自己也不必 100% 做到：十条做到八条是合理状态，剩下两条标为迭代目标写进文档即可。为了「自符合」把做不到的规范删掉，损失的是方向。

## 披露

- 披露由 description、触发面、命名构成；机制与判据见[让技能被正确命中](general/disclosure.md)（判断某个词该留该删、定技能名时读），定稿流程与回归见[写入口文件](documents/skill-md-writing.md)。
- 命名先于 description 定稳。技能名是双重身份：加载器标识 + 用户称呼；改名牵动目录、字段、正文称呼与他人引用，交付后改名是结构性变更。
- `description` 的每个词都是每次会话的常驻成本；覆盖面收敛之前不写它。

## 推荐路径

- 大致走向是 锚定 → 组织 → 编写，但**不是阶段流水线**：设计是发现过程，卡住随时回头。回头时明确回到哪一步、修什么，而不是模糊地「重新想想」——材料不足回实践补积累，范围没钉住回锚定重答三问；卡点修不动、或发现根子在设计意图，也回锚定重答三问——在正文中反复修补修不好的问题，问题不在文字，在锚定本身。
- 交付后的检验是两项独立工作，分属两个文件：[快速测试](skill-quick-test.md)判「零上下文能不能用起来」，[审查](skill-review.md)判「写得对不对」。
- 只有内容本身是程序时才用流程形态；判断依据按需查阅，不做成关卡。简单技能（三五个文件、单一形态）用得上其中几条就用几条，完整流程会产生仪式性工作量而不产生质量。

## Gotchas

- **禁止语悖反**：禁止词让被禁行为更可及，且只划边界不给路。规则正向陈述目标行为；只有无法正面表达的硬护栏才保留禁止，并配对「该做什么」。
- **为推测的需求设计**：没有真实做法支撑的需求不构成设计输入。锚定时先问「这套做法是否已被走通」，答不上就先去走通，或明确这只是个待验证方向。
- **成品格式化石**：一次交付的产出形态冒充方法论。先问形状背后有没有可迁移的结构；有则按[写模板](documents/template-writing.md)拆骨架、换案例试填，没有就留在个案里，不做成技能内容。
- **委托边界泄漏**：委派用的预期与对比信息只留在委派者手里，不进技能文档、不进子代理 context。写委托相关文档时先定义「执行者不知道什么」，再定义「它做什么」——下发内容清单就是污染面清单。
