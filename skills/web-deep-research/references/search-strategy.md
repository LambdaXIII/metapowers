## 总体

### 报告落盘

- **条件**：本次研究需要交付成一份可复用、可留档的报告
- **建议**：让实际执行研究的角色直接把报告**写入文件**（磁盘），不要通过对话把报告内容完整传回主会话
- **理由**：研究报告通常很长，走对话交接会占用主上下文、且容易在转述中丢信息。落盘后主会话按需读取即可

## 执行形态

### 执行模式选择（按顺序判断）

1. **条件**：有明确主线话题、且需要多轮搜索（会干扰主会话）
   - **建议**：**完全委派**——把研究整体交给子代理独立执行
   - **理由**：多轮搜索 + 大量工具调用会拖慢主会话；话题自包含时子代理可独立跑完 Phase 0-4
2. **条件**：话题复杂（多子话题、跨领域），难以一次交代清楚
   - **建议**：**拆分委派**——拆成若干子话题分别研究；可中途调整拆分方式与委派策略，动态响应新发现
   - **理由**：一次交代复杂话题容易遗漏维度；拆分后可逐块推进，新线索出现时能改策略而非推倒重来
3. **条件**：以上都不满足（话题简单 / 高度依赖对话上下文）
   - **建议**：**主会话自行执行**
   - **理由**：委派的开销大于收益；依赖上下文来判断的点，留在有完整上下文的地方做更可靠

### 预拆分子话题

- **条件**：话题可自然拆成多个相互独立的子话题
- **建议**：拆分后逐个子话题研究，最后合并
- **理由**：分块降低单次研究的复杂度，也为"中途改委派策略"留出空间

### 逐问题委派（居中调度）

- **条件**：问题集（Q-set）清晰、每个问题可独立研究
- **建议**：按问题逐个委派研究，主会话居中调度、汇总消解（见 workflow.md 的问题集模型）
- **理由**：问题（Q）是原子研究单元，天然是委派的最小粒度；居中调度保证消解闸门（交叉验证）统一执行，不因分散研究而放松

### 子代理自读技能

- **条件**：把研究委派给子代理
- **建议**：只传**任务描述**，不要把本技能的文件内容转述给子代理；让子代理自己加载技能并按流程执行
- **理由**：技能文档本身就是给执行者的自足指引；转述会丢细节、占用主上下文，还可能让子代理拿到不一致的指令

### 多子话题整合

- **条件**：多个子话题 / 多个问题分别研究完成
- **建议**：合并结果——交叉引用、去重、仲裁矛盾、统一为一份报告
- **理由**：分散研究产生割裂的中间产物，需整合成可独立检验的整体，避免重复与自相矛盾

### 覆盖检查

- **条件**：整合完成、报告初具
- **建议**：对照 Phase 0 的目标清单与问题集，逐条核对是否全部覆盖；发现空白 → 补研究或诚实标注
- **理由**：防止"研究了很多，却没回答原始问题"

## 交付利用

### 结论回灌

- **条件**：报告用于支撑某个决策 / 回答某个上级问题
- **建议**：报告的结论要能**直接回答它被委托时支撑的那个决策问题**，并保留结论 ← 发现 ← 来源的可追溯链路
- **理由**：研究的价值在于支撑决策；若结论不回答原始问题，研究就白做了
