# Rule Design Guide

> 本文件提供设计 journal 规则文档的方法论。规则文档是 journal 侧文件——记录分类、标签、INDEX 结构、笔记元数据字段、写作需求等规则。
> 本文的"建议板块"针对 **RULES.md 结构板块**：每个板块是什么、放什么、如何设计。
> 规则从 journal 的实际内容中生长，不预设框架——以下建议均可按需取舍。

---

## 1. 规则设计的建议

### 分类设计

分类从内容中生长——先扫描内容，再设计规则，而不是先设计规则再套内容。四个动作：

1. **扫描**：列出目标路径下所有条目，记录每条的目的与内容性质
2. **找自然簇**：按自然相似性分组，不强行套分类
3. **命名**：名称反映分类的内部一致性，暗示什么内容该放进去
4. **验证**：正交性（一条内容不应能合理地放进两个分类）+ 覆盖度（所有内容都能放入至少一个分类）

允许一个"不确定"兜底位置——不确定归属的内容可以先放那里，维护时再修正。分类是迭代的：先用不完美的分类开始，在维护中逐步改进。分类的最终验证是"我能否找到想要的笔记"，不是"分类是否美丽"。

### 标签设计

标签是跨目录的检索维度。一个标签值得注册的条件：**同一概念在 3 条以上条目中出现**且无现有标签覆盖——只出现 1 次的概念先用现有标签描述，不注册。

命名规范（hard）：

- 全小写 kebab-case：`design-decision` ✓，`Design-Decision` ✗
- 单数形式：`lesson` ✓，`lessons` ✗
- 不用缩写：`frontend` ✓，`fe` ✗
- 语义明确：另一个 agent 看到标签名能大致猜出含义

注册流程：检查现有标签是否已覆盖 → 命名 → 加入标签注册表 → 使用。生命周期：不再使用的标签（最后使用超 6 个月、仅 1-2 条条目）→ 从注册表移除（历史条目保留标签）；同义标签 → 合并到规范标签。

### 约定设计

约定记录"这里需要特殊处理"：**作用域 + 写入感知步骤**——哪些 scope 在写入时需要额外操作。偏离技能默认行为时说明理由，维护时才能判断偏离是否仍然值得。

## 2. 规则编写的原则

- **不重复**：技能已有的规范不重复记录——规则文档只记录与默认行为不同或额外的事情
- **允许偏离需理由**：规则可以与技能默认行为不同；偏离时说明偏离了什么、为什么、预期收益
- **参考 spec-note 风格**：summary 定义作用域边界、正文写 reasoning 而非 checklist、last_update 跟踪时效
- **规则与笔记分离**：规则文件是规则、条目是条目，检索不互相污染
- **规范变化必须落地**：规则调整后同步到规则文档，不留口头约定

## 3. Pitfalls

从真实使用中提炼的常见错误模式——每条一句话，遇到时对照检查：

1. **分类瘫痪**：每次写笔记都花大量时间决定放哪——用兜底位置 + 简单规则预防，维护时批量修正
2. **分类法崇拜**：花在完善系统上的时间超过使用笔记的时间——分类的验证是"能否找到笔记"而非"分类是否美丽"
3. **标签通胀**：不受控的标签退化为噪声——维护受控标签注册表，定期合并冗余标签
4. **单一系统教条**：盲目遵循某一方法论而不考虑自己的实际内容——所有系统都是起点不是终点
5. **Projects vs Areas 模糊**：无法区分"有时限的任务"与"持续的责任"导致内容反复移动——接受边界模糊为常态，在规则中记录判断标准
6. **衰退信号**：持续感觉分类"不对"、查询成本上升、写笔记时跳过分类步骤——触发规则重新设计

## 4. 建议的板块（含简单示例）

以下板块建议针对 RULES.md 结构板块——每个板块的形态与简单示例。可选用、可自行设计其他板块，无任何硬性规定。

### 分类板块

目录规则：放什么 / 不放什么 / 一句话判断。示例（目录快速参考表）：

| 目录 | 放什么 | 不放什么 | 一句话判断 |
|------|--------|---------|-----------|
| `experience/` | 经验：个人实践产出的教训、决策、方法论 | 外部研究、进行中的任务 | 这来自我的实践吗？→ experience。来自外部？→ knowledge |
| `knowledge/` | 知识：外部来源的研究、文献笔记、参考资料 | 个人经验、活跃任务 | 这是我的原创经验吗？→ experience。来自外部？→ knowledge |

### TAGS 板块

标签注册表：标签 + 一句含义 + 使用规则。示例：

| 标签 | 含义 |
|------|------|
| `lesson` | 教训、经验总结 |
| `research` | 调研、信息搜集与分析 |

### INDEX 结构板块

本 journal 的 INDEX 组织方式（板块选择/同步节奏/维护规则）——**强烈建议参考 `references/design-index.md`** 获取设计启发。

### 笔记元数据字段板块

frontmatter 字段方案：选什么字段、各字段用途。字段格式语法见 `references/spec-frontmatter.md`（通用格式规范），字段设计自由。示例：

| 字段 | 用途 |
|------|------|
| `title` | 条目标题 |
| `summary` | 摘要：定义本条目的范围边界 |

### 自定义写作需求板块

需要特殊处理的 scope + 写入感知步骤。示例：

- **作用域**：项目 X
- **写入感知步骤**：写入前检查项目 X 的 dashboard 是否需同步

### 维护备忘板块

待办队列形态：日常发现的待维护问题逐行记录（INDEX 行过时、条目误分类、未注册标签、主题碎片化等），维护时消费清空。

### 其他

板块可按需自设计——以上均为示例，不是模板。

## 参考示例

完整的分类体系示例见 `examples/classification-systems/`（每个文件以摘要开头，先读摘要判断是否需要全文）：

| 文件 | 一句话摘要 |
|------|-----------|
| `para.md` | 按可行动性分四个容器（Project/Area/Resource/Archive），适合项目驱动型内容 |
| `zettelkasten.md` | 按概念分原子笔记 + 链接网络，适合知识积累与发现 |
| `johnny-decimal.md` | 按有限编号空间（10×10 槽位），适合需要跨工具一致分类 |
| `moc-lyt.md` | 按导航优先（索引笔记替代文件夹），适合大型笔记库 |
| `evergreen.md` | 按演化概念（笔记随时间生长），适合长期知识写作 |
| `gtd-contexts.md` | 按使用场景分上下文（GTD Contexts），适合情境驱动型工作流 |
| `journaling-default.md` | 4 目录种子（inbox/experience/knowledge/active_works）的完整定义，AI agent 日记的起点参考 |

**免责说明**：示例（尤其 journaling-default）含旧设计残留断言（如"inbox 必须存在"）——inbox 存在与否由 journal 自行决定，示例仅作体系参考、不作规范。

成熟的标签集合示例见 `examples/journal-standards/`——作启发参考，不作为模板照抄。
